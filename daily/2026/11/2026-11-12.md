# Daily Knowledge Lesson — 2026-11-12 — Roofline & Arithmetic Intensity（屋顶线模型与算术强度）

## Knowledge Map Position（知识地图定位）

```text
2031 Personal World Model
→ SYSTEM（现代社会系统）
→ Compute Systems（计算系统）
→ Accelerator Performance（加速器性能）
→ Roofline & Arithmetic Intensity（屋顶线模型与算术强度） ← Today
```

昨天，我们已经知道 GPU 只有在软件提供足够的并行工作、合并的数据访问和可调度的 Warp 时，才会把大量算术单元变成有效吞吐。前天则建立了 HBM 的另一条上限：存储器每秒能向计算单元搬多少字节。

今天把这两条上限第一次放进同一个模型。它必须先于 Server & Interconnect（服务器与互连），因为只有先判断单颗加速器内部究竟受计算还是供数限制，才能知道增加 GPU、互连和服务器是否会提高完整任务的速度，还是只会把同一种等待复制得更多。

> **今天如果只记住一件事，就是：程序性能由“计算屋顶”和“带宽 × 算术强度形成的供数屋顶”中更低的那个限制；优化必须抬高正在压住程序的屋顶，或让工作负载越过两条屋顶相交的 Ridge Point（脊点）。**

## 1. Opening Puzzle（开场谜题）

一家云厂商有两种加速器。新卡的峰值计算能力是旧卡的两倍，价格也是两倍。某个矩阵模型迁移后速度接近翻倍；另一个模型只快了 10%。

如果只看 TOPS，你会认为第二个模型的软件写坏了；如果只看显存带宽，你又可能认为所有问题都该通过增加 HBM 解决。但两种判断都缺少一个问题：**每从外部存储搬来一个字节，程序究竟能用它完成多少次有用运算？**

这就是今天要重建的判别框架。

## 2. Follow One Unit（跟随一个最小单位）

先跟随 HBM 中一个 4-byte 数值。

它被内存控制器取出，跨过 HBM 接口进入片上缓存或寄存器，然后被算术单元使用。若程序读一次、只做一次加法就丢掉它，4 bytes 只换来大约 1 次有用运算；若程序把它留在更靠近计算的位置并参与 100 次乘加，搬运同样 4 bytes 就支撑了更多计算。

真正稀缺的不是抽象的“数据”，而是某一层存储边界上每秒能够通过的字节。若 HBM 每秒只能交付固定数量的字节，第一种程序很快把通道占满，算术单元仍会等待；第二种程序会在同一批字节上继续计算，更可能先耗尽算术能力。

因此我们定义：

```text
Arithmetic / Operational Intensity
= Useful Operations ÷ Bytes Moved Across a Named Memory Boundary
```

单位通常是 FLOP/byte、MAC/byte 或 operation/byte。分母必须说明是哪一层边界：HBM、L2、L1，还是片上 SRAM。换一个边界，字节数就可能改变。

原始 Roofline 论文为了把 Cache Reuse（缓存复用）包含进来，把 Cache 与 DRAM 之间的实际流量称为 **Operational Intensity（操作强度）**。现代分析工具常用 Arithmetic Intensity（算术强度）这一名称。今天两者都指向同一纪律：**先固定“有用运算”与“被计数字节”的边界，再计算比率。**

## 3. Name the Core Concept（命名核心概念）

Roofline Model（屋顶线模型）不是一条精确预测线，而是 Bound-and-Bottleneck Analysis（上限与瓶颈分析）：

```text
Attainable Performance
≤ min(Peak Compute,
      Effective Memory Bandwidth × Arithmetic Intensity)
```

第一项是水平的 **Compute Roof（计算屋顶）**。不论数据多么充足，算术单元每秒最多完成这么多运算。

第二项是随强度上升的 **Memory Roof（存储屋顶）**。当每个字节只做少量计算时，带宽限制性能；同一个字节被复用得越多，带宽能够支撑的运算就越多。

两条屋顶的交点叫 **Ridge Point（脊点）**：

```text
Ridge Point = Peak Compute ÷ Effective Memory Bandwidth
```

它的单位是 operation/byte，表示要让计算单元成为主要限制，工作负载至少需要多高的算术强度。脊点左边通常是 Memory-bound（受存储限制），右边通常是 Compute-bound（受计算限制）。

### 一个透明的最小模型

假设一台机器的实测可持续计算屋顶是 100 TFLOP/s，实测 HBM 带宽是 2 TB/s：

```text
Ridge Point = 100 TFLOP/s ÷ 2 TB/s = 50 FLOP/byte
```

Kernel A 的算术强度为 5 FLOP/byte。它的供数屋顶是 `2 TB/s × 5 FLOP/byte = 10 TFLOP/s`，所以即使机器标称 100 TFLOP/s，它最多先看到约 10 TFLOP/s 的带宽上限。

Kernel B 的算术强度为 100 FLOP/byte。它的供数屋顶是 200 TFLOP/s，但计算屋顶只有 100 TFLOP/s，因此计算成为较低屋顶。

若带宽翻倍，A 的上限从 10 变成 20 TFLOP/s，B 仍被 100 TFLOP/s 的计算屋顶压住。若只把计算翻倍，A 几乎不变，脊点反而从 50 移到 100 FLOP/byte。**更强的计算芯片会要求更高的数据复用，才能真正吃满新增算力。**

这些数字是教学模型，不代表任何具体 GPU。

## 4. Roofline 能告诉我们什么，不能告诉我们什么？

它首先告诉你该调查哪一类约束。

如果点落在斜坡区域，增加算术单元通常不会先解决问题。更有希望的动作包括提高真实带宽、改善连续访问、用 Tiling（分块）把数据留在 Cache / SRAM 中重复使用、用 Kernel Fusion（算子融合）减少中间结果写回和重读，或在允许的正确性边界下降低精度以减少字节。

如果点落在平坦区域，继续增加带宽通常不会先解决问题。此时应调查算术单元利用率、指令组合、矩阵形状、分支、同步、并行度和编译器生成的代码。

但“位于计算侧”不等于“已经达到计算屋顶”。真实程序还可能被形状不匹配、依赖、调度、延迟目标、Host 交互、通信或软件空洞压到屋顶下方。Roofline 给出上限和检查顺序，不替代 Profiler（性能分析器）。

也不能为了提高比率而添加无用计算。若人为多做十次无意义乘法，公式中的分子看似变大，用户得到的结果却没有增加。分子应计入完成同一输出所必需的有用工作，分母则应使用同一边界下真实搬动的字节。

最后，营销规格不是唯一屋顶。原始论文强调应使用可持续的实测内存带宽；现代工具还会分别画 HBM、L2、L1 和不同精度的屋顶。FP32、FP16、INT8 和 Tensor 运算不能混用一条 Peak Compute 线。

## 5. Deep Case — Google TPU v1：92 TOPS 为什么既能跑到 86，也能只跑到 2.8？

### Before：推理原本只是数据中心中的一个工作负载

2013 年，Google 估计如果每位用户每天使用语音搜索三分钟，语音识别需求可能使数据中心计算需求翻倍。传统 CPU 和 GPU 可以运行神经网络，但 Google 面对的是线上服务：不仅要处理很多请求，还必须控制用户看到的响应延迟。

这里的最小单位不是“一块芯片”，而是**一个必须在延迟期限内完成的推理请求**。

### Pressure Builds：更大的 Batch 能复用权重，却会让请求等待

神经网络推理会反复读取几百万到上亿个权重。把多个请求组成较大的 Batch（批次），可以让一次读入的权重服务多个样本，从而提高 operation/byte；但收集 Batch 需要等待，用户请求不能无限排队。

论文中的 MLP0 有 7 ms 的 99th-percentile Response-time Limit（99 分位响应时间上限）。因此，吞吐与响应延迟不是同一个目标。为了遵守服务期限，部署时采用的 Batch 可能远小于离线测试中最能吃满硬件的 Batch。

### Turning Point：Google 选择一个极强计算、相对窄供数的专用结构

Google 在约 15 个月内设计、验证并部署了第一代 TPU。它有一个 256 × 256 的 8-bit Matrix Multiply Unit，共 65,536 个乘加单元，峰值约 92 TOPS；片上内存约 28 MiB，外部 Weight Memory 是 8 GiB，论文报告的权重带宽为 34 GB/s。

因此它的关键脊点约为：

```text
92,000 GOP/s ÷ 34 GB/s ≈ 2,706 operations/byte
```

但论文按一次 MAC 的运算计数口径报告 Roofline Ridge Point 为 1,350 MAC operations per weight byte。两者相差约两倍，来自 operation 与 MAC 的计数口径。**这正说明数字只有在单位和分子定义一致时才可比较。**

### Cascade：六种工作负载撞到的屋顶并不相同

论文选取六个生产神经网络应用，它们合计代表当时约 95% 的 TPU 工作负载。

MLP0、MLP1、LSTM0 和 LSTM1 的部署算术强度只有约 64–200 operations per weight byte，远低于 1,350 的脊点，所以它们位于供数斜坡。对应实测吞吐约为 12.3、9.7、3.7 和 2.8 TOPS。92 TOPS 的峰值并没有消失；它只是没有成为当时最低的屋顶。

CNN0 的部署强度约 2,888，跨过脊点，并达到约 86 TOPS，接近 92 TOPS 的计算屋顶。这个结果证明同一硬件在工作形状合适时可以接近峰值。

### Decision：为了可预测延迟，Google 没有只追求最大离线吞吐

TPU 采用确定性较强的执行方式，并围绕推理而非通用图形或训练设计。Google 不能简单地积累任意大的 Batch，因为在线请求受 99 分位延迟目标约束。

因此，一个模型在实验室里通过更大 Batch 获得高算术强度，并不自动等于它在真实服务中也能这样运行。SLA（Service-level Objective，服务级目标）会改变可接受的 Batch、队列和吞吐。

### Outcome：Roofline 找到了主约束，却没有解释所有屋顶下方的距离

最有价值的对照是 CNN1。它的部署强度约 1,750，按 Roofline 已位于计算侧，但实测只有约 14.1 TOPS，远低于 92 TOPS。论文分析显示：它只有不到一半周期用于矩阵运算；较浅的 Feature Depth 使约一半 MAC 位置无用；同时还有约 28.1% 的权重等待，以及读后写依赖等停顿。

所以：

- CNN0 的 86 TOPS 说明计算屋顶可接近；
- CNN1 的 14.1 TOPS 说明“计算侧”只是约束类别，不是性能保证；
- MLP / LSTM 的 2.8–12.3 TOPS 说明高峰值算力无法绕过低算术强度和有限权重带宽。

### Aftermath：改变哪项资源，决定哪类模型受益

论文的硬件模型显示，把权重带宽提高四倍，平均性能约提高三倍；把时钟提高四倍，对 MLP 与 LSTM 几乎没有影响，却让 CNN 大约提高两倍。把 256 × 256 矩阵单元扩大到 512 × 512 甚至略微降低平均性能，因为实际矩阵形状不能总是填满更大的方阵。

另一个假设设计把内存改为更高带宽 GDDR5，脊点从约 1,350 降到 250 operations/byte。论文估计，配合 700 MHz 时钟后，按当时工作负载权重计算的芯片级性能可提高约 3.9 倍；计入 Host Server 交互后约为 3.2 倍。

这不是“内存永远比计算重要”，而是更精确的结论：**当生产工作负载集中在脊点左侧，提高带宽比继续堆计算单元更能抬高当前屋顶。**

## 6. Comparison（比较）：三种“屋顶”不要混在一起

| 层级 | 它回答什么 | 需要什么证据 | 常见误读 |
|---|---|---|---|
| Spec Roof（规格屋顶） | 芯片在规定精度和条件下的理论峰值 | 架构规格、频率、位宽、接口 | 把峰值当应用保证 |
| Empirical Roof（实测屋顶） | 这台系统持续能交付多少计算和带宽 | Microbenchmark、功耗、频率、内存层级 | 把一次实测外推到所有软件 |
| Workload Point（工作负载点） | 指定模型、Batch、精度和软件实际在哪里 | Profiler、真实流量、SLA、端到端时间 | 只因位于计算侧就认为已吃满算力 |

现代 NVIDIA Nsight Compute 和 Google XProf 都把 Roofline 用作定位工具，并允许查看不同内存层级或算子。距离屋顶越远，意味着仍有利用率或软件优化空间；但哪一种优化有效，必须结合更细的性能计数器，而不是只凭图上位置猜测。

## 7. Industry Apprenticeship：云客户应该买 TOPS，还是买结果？

今天只回答一个行业问题：**当峰值 TOPS 与每小时价格指向不同选择时，云客户应该怎样比较加速器？**

Cloud Provider（云服务商）购买服务器和加速器，承担资本、机房、电力、维护和闲置风险，再按实例时间、预留容量或托管服务收费。客户最终需要的是一个训练完成、一个请求在 SLA 内返回，或一批结果被正确产出，而不是芯片内部发生了多少理论运算。

因此第一阶比较应是：

- **Time to Solution（完成时间）**：同一模型、精度、Batch、软件版本和正确性边界下完成任务要多久。
- **Cost per Useful Output（每单位有效产出成本）**：云时费、运行时间和成功输出共同决定，而不是只看每小时标价。
- **SLA / Tail Latency（服务目标 / 尾部延迟）**：平均吞吐不能替代 99 分位响应时间。
- **Measured Utilization（实测利用率）**：计算、HBM、Cache、互连和 Host 分别有多少时间在做有用工作。
- **Porting and Qualification（移植与资格化）**：Library、Compiler、数值结果和部署流程要付出多少一次性与持续工程成本。

一个纯教学的价格例子：加速器 A 每小时 4 美元，任务用 5 小时，总计算费 20 美元。加速器 B 每小时 8 美元：若同一计算受限任务在 B 上只用 2 小时，总费 16 美元；但若另一个供数受限任务在 B 上仍需 4.5 小时，总费 36 美元。更贵的实例可能更便宜，也可能更贵，取决于工作负载点是否真的利用了它抬高的屋顶。

Google 的 TPU 论文没有公布真实芯片价格，明确说价格受谈判影响，因此用 Performance per Watt 作为数据中心 TCO 的代理。这个证据边界很重要：公开的性能和功耗可以比较某些技术方向，却不能还原采购折扣、利用率、机房、电力、网络、闲置、移植和机会成本。

## 8. Fact、Interpretation、Inference 与 Hypothesis

> **Fact（事实）**：原始 Roofline 论文给出 `min(Peak Compute, Peak Memory Bandwidth × Operational Intensity)` 的上限形式，并建议使用可持续实测带宽。Google TPU v1 论文记录 92 TOPS、34 GB/s 权重带宽、1,350 operations/byte 脊点，以及六个生产工作负载的强度和吞吐。

> **Interpretation（解释）**：Roofline 把 HBM 的字节供给与 GPU / TPU 的运算供给放到同一单位体系中，让我们先判断哪一类资源的边际改善更可能提高吞吐。

> **Inference（推断）**：云客户若只按 Peak TOPS 或每小时价格选择设备，可能在供数受限、形状不匹配或 SLA 约束下购买无法转成有效产出的能力；更稳健的单位是同边界下的时间、成本与有效输出。

> **Hypothesis（仍需验证的假设）**：某个现代 AI 模型在某款 GPU 上主要受 HBM、Tensor Compute、互连或软件约束。验证需要固定模型、精度、Batch、序列长度、软件版本、延迟目标和功耗条件，并获取 Kernel / Memory / Interconnect 的实测计数。

### Evidence Boundary（证据边界）

TPU 案例来自 2015 年部署、2017 年发表的第一代 8-bit 推理芯片和当时 Google 工作负载，不应直接外推到今天的训练集群或 HBM GPU。论文的“operations per weight byte”选择了权重内存边界，也不等同于所有激活、缓存和互连流量。厂商论文能提供真实生产测量，但工作负载选择、比较系统和未公开成本仍限制普遍结论。

## 9. Transfer（迁移）：以后看到“新芯片快两倍”，按什么顺序问？

先固定任务：模型、输入形状、精度、Batch、软件、正确性、延迟目标和测量边界是否相同？

再计算或实测强度：完成同一输出需要多少有用运算，跨 HBM 或目标内存层实际搬了多少字节？工作点位于哪个 Ridge Point 左右？

然后看距离屋顶：如果远低于对应屋顶，是形状、并行度、分支、依赖、同步、Host 还是通信造成？

最后才做经济判断：每小时价格乘以端到端时间是多少，移植、验证、闲置、电力和容量风险是否改变结果？

## Teach-back（20-30 分钟讨论）

1. 有一台 200 TFLOP/s、4 TB/s 的加速器。Kernel X 的强度是 10 FLOP/byte，Kernel Y 是 80 FLOP/byte。请分别算出 Ridge Point 和两个 Kernel 的 Roofline 上限；然后说明若只能把计算或带宽中的一个翻倍，你会为每个 Kernel 选哪一个，为什么。
2. 某模型位于 Roofline 的计算侧，却只达到峰值的 20%。请不要回答“软件没优化”。请提出至少四个可区分的机制，并为每个机制说出需要观察的证据。

## 11. 现在我们可以重新回答开头的问题

新卡峰值计算翻倍，只会抬高水平的计算屋顶。第一个矩阵模型若已接近该屋顶，就可能接近翻倍；第二个模型若位于带宽斜坡，或虽在计算侧却因形状、利用率和 SLA 距屋顶很远，增加算术单元便不会自动转成速度。

今天在地图上点亮的是 `SYSTEM.COMPUTE.ROOFLINE_ARITHMETIC_INTENSITY`：它把前天的 HBM Bandwidth 与昨天的 GPU Compute Throughput 合并成一个可判别的性能模型。下一步通向 Server Node & Interconnect：当单颗芯片的屋顶被看清后，我们将跟随数据跨越 CPU Host、PCIe / NVLink、NIC 和多颗 Accelerator，判断通信何时成为新的屋顶。

- **Precision & Quantization（精度与量化）**：较少字节可能提高强度和峰值，但必须保留数值正确性。
- **AI Infrastructure Economics（AI 基础设施经济学）**：利用率、SLA 与端到端时间决定每单位有效产出成本。
- **Energy & Cooling（能源与冷却）**：功率限制会把理论计算屋顶压成更低的持续屋顶。
