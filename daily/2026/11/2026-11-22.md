> **今天如果只记住一件事，就是：Cloud 的经济价值不是“租一定比买便宜”，而是用产品价格换取资源池、弹性、交付速度和一部分运营责任；只有把同一业务服务在同一时间、性能、可靠性与风险边界下的完整 Total Cost 放在一起，才能判断成本真的下降了，还是只是换了账单形状。**

# Mastery Core（掌握核心）

## 1. Opening Puzzle（开场谜题）：Dropbox 为什么先依赖 Amazon，后来又把 500 PB 搬回自己手里？

Dropbox 起步时，把用户文件内容放在 Amazon S3。这样做很自然：一家年轻公司可以先把工程力量投入同步、分享和产品体验，不必先买磁盘、租机房、建存储系统、安排 24 小时值班并证明数据不会丢失。

几年后，同一家公司却投入两年多建设 Magic Pocket，把绝大多数用户文件搬入自建基础设施。2016 年 Dropbox 宣布，超过 90% 的用户数据已经由自己的系统存储和服务。表面上看，这像在推翻早期选择：如果自建更便宜，为什么不从第一天就自建？如果 Public Cloud 更高效，为什么规模变大以后要离开？

真正需要解释的不是“Cloud 好还是坏”，而是：**工作负载、规模、不确定性和团队能力变化后，同一责任边界的经济价值为什么会翻转？**

今天跟随一个用户文件 Block。它会告诉我们，客户从来不只是选择“租磁盘”或“买磁盘”，而是在选择谁提前建设容量、谁承担空置、谁运营复制和修复、谁对增长预测负责，以及哪一方有能力把这些责任做得更便宜。

## 2. 先定义母概念：Cloud Service 是一份被产品化的计算能力

NIST 把 Cloud Computing 定义为：通过网络按需访问一组共享、可配置、能够快速供应和释放的计算资源。它的五项关键特征包括 On-demand Self-service、Broad Network Access、Resource Pooling、Rapid Elasticity 与 Measured Service。

这一定义的经济含义很重要。Provider 先建设服务器、存储、网络、机房、软件与运营系统，把异质的物理资产汇成资源池，再把资源池切成可通过 API 购买、快速释放并按量计量的产品。Customer 购买的不是一块具体磁盘的产权，而是一项具有接口、性能、位置、可靠性、计费和责任边界的服务能力。

因此，Cloud 并没有消灭资本、闲置、故障和人员劳动。它把这些内容重新组合：

- Provider 在全体客户之间 Pool 需求，承担一部分建设、预测、折旧、碎片、设备故障和底层运维风险；
- Customer 用按量价格、承诺折扣、容量预留、请求费、存储费与数据传输费支付服务；
- 服务抽象越高，Provider 通常接管的底层工作越多，但 Customer 仍要对自己的数据、身份、配置、应用行为、端到端可靠性和业务损失负责；
- 责任没有消失，只是沿产品边界重新分配。

这就是今天的母概念：**Cloud Economics 研究的不是一个小时价格，而是产品边界怎样重新分配资产所有权、容量利用率、交付速度、运营工作和剩余风险。**

## 3. Follow One Unit（跟随一个最小单位）：一个 4 MB 文件 Block 的完整成本在哪里？

Dropbox 的 Magic Pocket 把文件切成最多 4 MB 的 Block，再把许多 Block 聚合成更大的 Bucket 和 Volume。先不进入它的全部架构，只跟随其中一个 Block。

### 在 Public Cloud 中

Customer 调用 Object Storage API 写入 Block。Provider 负责建设底层存储节点、机房、电力、网络、故障替换、容量池和服务软件，并按存储量、请求、检索、复制、位置与传输边界收费。Customer 不必知道 Block 落在哪块盘，却仍要决定：

- 对象如何命名、加密、授权和保留；
- 应用怎样重试，怎样处理重复或失败请求；
- 是否购买跨 Region 复制、版本与恢复能力；
- 哪些请求和 Egress 会发生，是否形成持续成本；
- Provider 中断时，业务是否有替代路径；
- 数据和应用怎样在未来迁出。

### 在自建系统中

企业要采购或租赁磁盘、服务器、网络与机架，决定复制或 Erasure Coding，写 Placement、Repair、Scrubbing、Monitoring 和 Deployment 软件，支付机房、电力、带宽、备件、折旧和人员成本。单个 API 请求不再产生相同的 Provider Request Fee，但企业已经提前购买了整套能力；不用满的空间和网络也由自己承担。

两个方案都在存储同一个 Block，却把成本放在不同位置。Cloud 更像把固定能力拆成可计量的 Service Units；自建更像先拥有一条生产线，再把年度固定成本摊给实际使用量。

## 4. Total Cost of Ownership（总拥有成本）：先让比较对象相同

TCO 不是把所有能想到的费用堆在一起，而是对**同一业务能力**在**同一时间窗口**内统计为了建设、运行、保护、改变和退出它所需的全部资源。

一个可比较的边界至少要固定六件事：

1. Useful Output：要完成多少成功请求、保存多少可恢复数据或交付多少训练结果？
2. Demand Shape：需求是稳定、季节性、突发、快速增长，还是可能归零？
3. Service Quality：延迟、吞吐、Durability、Availability、RTO 与 RPO 是什么？
4. Time Horizon：比较一年、三年还是完整设备寿命？
5. Operating Capability：团队已经具备哪些硬件、软件、供应链和 24×7 运营能力？
6. Exit Boundary：迁移、重写、数据传输、合同、折旧剩余和停机怎样处理？

若这些边界不同，较低的账面数字可能只是买了较少的服务。例如，一台裸服务器采购价没有包含多 AZ 冗余、流量入口、备份、修复、值班和快速扩容；一个 Cloud Instance 小时价也没有包含应用工程、错误配置、闲置资源、数据 Egress 与长期迁移。

## 5. Demand Shape（需求形状）：Cloud 首先出售的是“不必提前确定”

假设一家公司未来一年可能需要 100 到 1,000 个 Compute Unit，但现在不知道峰值何时出现。自建需要提前选择数量、等待采购和部署，并承担买多后的空置或买少后的业务损失。On-demand Cloud 允许公司在需要时扩张、不用时释放；它把一部分预测错误变成按量价格。

这份选择权在三个场景中特别有价值：

- 新产品：需求分布很宽，失败后可能迅速缩小；
- 短时峰值：年度峰值远高于平均值，购买全年资产会产生大量空闲；
- 速度关键：晚三个月上线的机会损失大于单位资源价差。

反过来，若负载长期稳定、规模巨大、硬件利用率高、应用具有专用需求，而且团队已经拥有供应链和运营能力，按量溢价可能持续超过自建的固定成本。此时“弹性”不是免费的好处；如果业务根本不释放资源，就一直在为没有使用的选择权付费。

## 6. 一个透明的 Break-even 模型：利用率怎样改变答案？

设一套自建资源每年完整固定成本为 120 万美元，包含折旧、机房、电力、网络、支持和运维；它可提供 1,000 个等价 Compute Unit。先忽略增长、故障、资金成本和迁移。

若平均只有 25% 被用于有价值工作：

```text
Useful unit-hours = 1,000 × 8,760 × 25% = 2,190,000
Owned cost per useful unit-hour = $1,200,000 ÷ 2,190,000 ≈ $0.548
```

若平均利用率为 50%，成本约为 `$0.274 / useful unit-hour`；若为 80%，约为 `$0.171`。

现在假设一份可比 Cloud 能力的透明教学价格为 `$0.25 / unit-hour`。自建成本与它相等所需的平均利用率为：

```text
Break-even utilization
= $1,200,000 ÷ (1,000 × 8,760 × $0.25)
≈ 54.8%
```

这个 54.8% 不是市场结论。120 万美元、1,000 Unit 和 0.25 美元都是教学假设。数字的作用是暴露机制：**固定成本除以实际有用利用量后才成为单位成本。** 如果把闲置、故障备用、采购提前期或人员漏出自建分子，结果会偏向自建；如果把 Cloud 折扣、请求、传输、托管服务、长期闲置或迁移漏出另一边，结果会偏向 Cloud。

而且，高利用率不是无条件的胜利。若把容量推到 95% 后不能吸收故障、增长和维护，业务会用 Tail Latency、排队与中断支付另一种成本。可比较的利用率必须保留同样的 Reliability Headroom。

## 7. Shared Responsibility（共同责任）：服务抽象提高，责任怎样移动？

AWS 的 Shared Responsibility Model 原本主要说明 Security 与 Compliance：AWS 负责 Cloud 基础设施本身，Customer 责任随所选服务变化。EC2 Customer 要管理 Guest OS、补丁、应用和 Security Group；S3、DynamoDB 等更高抽象服务由 AWS 运行更多底层层级，但 Customer 仍管理数据分类、权限和使用方式。

把这个思路扩展到可靠性与经济性时，必须谨慎：具体责任来自服务文档、架构和合同，不能用一张安全图代替全部 SLA。但它提供了一个有效原则：**产品接管的是明确层级的操作，不是客户业务结果。**

| 层级 | IaaS 中通常谁主要运营 | 更高抽象服务中的变化 | Customer 仍不能外包掉什么 |
|---|---|---|---|
| Facility、Server、Physical Network | Provider | 仍由 Provider | 选择 Region、服务与合同边界 |
| Hypervisor / Service Runtime | Provider | Provider 接管更多 OS、Database Engine 或 Storage Software | 正确选择容量、版本和产品配置 |
| Guest OS、Middleware、Patch | Customer | Managed Service 可接管一部分 | 应用兼容、升级决策、验证与回滚 |
| Application、Data、Identity | Customer | Provider 提供工具和默认值 | 数据含义、权限、Secret、业务逻辑与删除风险 |
| End-to-end Reliability / DR | Customer 设计并与 Provider 能力组合 | Managed Feature 可减少步骤 | 业务 RTO / RPO、依赖图、演练和剩余中断损失 |

“Shared” 也不表示每项工作由双方各做一半。更准确地说，双方分别控制不同层级，并在接口处共同决定结果。Provider 可以让磁盘和服务内部副本可靠，Customer 仍可能用错误权限删除数据；Provider 可以提供三个 Availability Zone，Customer 仍可能只部署一个 Zone；Customer 可以做 Multi-region，Provider 的 SLA Remedy 仍可能只是 Service Credit，而不是全部业务损失。

## 8. Main Case — Dropbox Magic Pocket：什么时候规模让责任边界翻转？

### Before：S3 让一家年轻公司先交付产品

Dropbox 早期一直采用 Hybrid Architecture：Metadata 和 Web Server 运行在自己管理的数据中心，用户文件内容存放在 Amazon。这个安排让公司不必从第一天就建设大规模 Object Storage，同时仍可控制核心应用与 Metadata。

这不是“浪费钱”。在产品、增长和工作负载还不确定时，Public Cloud 把容量、底层耐久性与硬件运维产品化，Dropbox 可以更快获得一项本来需要多年积累的能力。Cloud 的单位价格里包含了 Provider 的资本、资源池、工程、值班、故障替换与需求风险。

### Pressure Builds：40 PB 变成 500 PB，单位成本开始支配系统

Dropbox 工程团队回顾，2012 年用户数据约 40 PB，2016 年已超过 500 PB，四年增长超过 12 倍。500 PB 等于 500,000 TB；当每个 Byte 长期保存、复制、校验并被用户访问时，极小的单位成本差也会被放大。

与此同时，Dropbox 已经经营自己的 Metadata、Web Server、数据库与机房，积累了供应链、网络、自动化和大规模数据库运营能力。也就是说，自建的固定组织成本不再从零开始；一部分必要能力已经存在，专用存储可以与真实工作负载共同设计。

2013 年夏天，Magic Pocket 成为主要工程项目。团队不是因为一张公开价格表就立即迁移，而是先做 Prototype，观察自己的 File Distribution 和 Workload，再设计适合它们的存储系统。

### Turning Point：把通用服务换成专用生产系统

2014 年 8 月，Dropbox 开始 Dark Launch，在两个区域镜像数据，并额外保留六个月备份。2015 年 2 月 27 日，系统首次只在内部基础设施中存储和提供新用户文件；之后才扩大迁移。

这个顺序非常关键。经济决策没有跳过可靠性：若新系统节省单价却丢失数据，TCO 会被业务损失彻底翻转。Dropbox 需要自己接管 Placement、Replication、Erasure Coding、Integrity Verification、Capacity Expansion、Hardware Supply 和 24×7 Operations，也接管此前由服务商内部承担的相应风险。

### Cascade：500 PB 迁移把网络、机架、供应链和验证都变成责任

Dropbox 的目标是在六个月内把系统扩大到 500 PB 以上，并为此在三个区域安装服务器、建设高性能网络。公司报告迁移峰值超过 0.5 Tbit/s；另一篇工程文章把 500 PB 描述为超过 4 Exabit 的网络数据，在不到六个月内完成移动。

只做理论下限：

```text
500 PB × 8 = 4,000 Pbit = 4 Exabit
4 Exabit ÷ 0.5 Tbit/s = 8,000,000 seconds ≈ 92.6 days
```

92.6 天是假设始终以峰值传送、没有协议、重试、校验、并行双写和业务流量的序列化下限；实际项目不到六个月。这个数字改变理解的地方是：迁移不是一个会计按钮。网络吞吐、机架交付、双份存储、完整性校验和回滚时间本身都是 Transition Cost。

Magic Pocket 还把 Block 放入最多 4 MB 的单位，聚合为 1 GB Bucket，再跨机器和至少两个独立 Zone 保存。Dropbox 后续披露，超过 50% 的磁盘和数据库工作负载来自内部验证流量。自建看似消除了外部 Request Fee，却没有消除验证；它把验证从外部账单变成了内部硬件、能耗和工程成本。

### Decision：保留 Hybrid，而不是宣布 Cloud 失效

到 2015 年 10 月 7 日，Dropbox 提前达到由自建系统服务 90% 数据的目标；2016 年对外宣布时，仍明确表示会在适合用户的地方继续与 Amazon 合作，尤其包括全球区域需求。2022 年 Dropbox 工程文章也说明，公司在把用户文件迁入 Magic Pocket 后，仍把 S3 与 HDFS 用于其他内部产品和工具。

这不是一次宗教式的 “Cloud Exit”。Dropbox 对一个规模巨大、形状稳定、战略重要、可被专门优化的存储工作负载改变了边界，同时保留通用云在其他工作负载和地理需求上的价值。

### Outcome：账单形状确实改变了，但公开财务不能只归因于一个工程项目

Dropbox 的 SEC 文件给出了罕见的成本拆分。2015 到 2016 年，Cost of Revenue 从 4.074 亿美元降到 3.906 亿美元；公司称 Infrastructure Optimization 使基础设施成本净减少 3,950 万美元，其中 Third-party Datacenter Service Provider Expense 减少 9,250 万美元，但自有基础设施的 Depreciation、Facilities 与 Support Expense 增加 5,300 万美元。

这组数正是“账单形状改变”的证据：

```text
$92.5m lower third-party expense
− $53.0m higher depreciation, facilities and support
= $39.5m net infrastructure-cost reduction
```

云服务费没有凭空消失；其中一部分变成了折旧、机房、支持、硬件与内部运营。净额下降说明 Dropbox 在当时规模和条件下获得了经济收益，但也说明只拿 9,250 万美元宣布“省了这么多”会漏掉接回来的 5,300 万美元成本。

同期 Gross Margin 从 2015 年 33% 升到 2016 年 54%，2017 年又升到 67%。Dropbox 明确把改善归于 Infrastructure Optimization **以及同时发生的收入增长**；2016 到 2017 年 Revenue 增长 31%，基础设施成本又下降 3,510 万美元。公开文件不能把 34 个百分点的两年毛利率变化全部因果归给 Magic Pocket，因为用户增长、收入、Inactive Account 管理、其他使用优化和会计折旧都同时变化。

### Aftermath：自建的优势来自已经具备的能力，也创造新的暴露

Dropbox 后来继续优化 Cold Storage、Erasure Coding、供应链和 Edge Network。它获得了更强的 Workload-specific Optimization 与成本控制，却也必须直接承担硬件采购、磁盘和网络技术选择、供应中断、容量规划、机房依赖和系统软件长期维护。

案例留下的不是“规模超过 500 PB 就该自建”。真正的判断是：**当负载足够大、稳定和专用，内部团队能以可接受可靠性持续运营，而且节省的完整单位成本超过资本、迁移、组织和退出代价时，自建可能胜出；条件不成立时，Cloud 的风险池和速度仍可能更有价值。**

## 9. Meaningful Comparison（有意义的对照）：同一个工作负载在不同阶段可以有不同答案

| 条件 | Public Cloud 更可能创造价值 | 自建更可能创造价值 | 需要验证的证据 |
|---|---|---|---|
| 需求不确定性 | 失败可快速释放，峰值可临时扩张 | 预测稳定且容量长期使用 | 逐时 / 逐月需求分布与增长误差 |
| 规模与利用率 | 小规模免去最低经济规模 | 大规模高利用率可摊薄固定成本 | 同可靠性边界下的 useful utilization |
| 工作负载专用性 | 通用 API 与托管能力足够 | 专用硬件 / 软件明显减少单位资源 | 请求、数据温度、网络与故障实测 |
| 交付速度 | API 立即获得能力，减少采购提前期 | 已有机房、供应链和标准化平台 | Time-to-service 与机会损失 |
| 运营能力 | Provider 的经验和自动化可被共享 | 内部团队已有强运营与硬件能力 | On-call、修复、供应链与故障演练记录 |
| 退出与变化 | 未来可切换服务或区域 | 数据巨大、服务成熟且变化慢 | Egress、重写、合同、停机与剩余折旧 |

这张表不是评分卡。某一列项目更多并不自动决定答案；应把它们换成同一业务结果的现金流、风险和时间分布。最容易被忽略的往往是 Optionality：Cloud 允许晚一点承诺，自建允许在规模稳定后控制更多单位成本。两者购买的是不同的未来选择。

## 10. 反例与边界：为什么“稳定大负载”仍不一定适合自建？

一个负载即使稳定而且巨大，也可能因为以下条件继续适合 Cloud：它需要全球 Region 和合规认证；硬件代际变化太快；业务无法吸引或保留基础设施团队；需求虽稳定但可靠性目标要求大量异地容量；企业资本昂贵；迁移风险远大于单位差价；或者 Managed Database、Identity、Security 与 Observability 的组合价值高于裸资源节省。

反过来，小公司也不应把 “Cloud-native” 等同于无需管理成本。若团队长期保留过大的 Instance、让测试环境永不关闭、把同一 Byte 反复跨 AZ / NAT / Region 移动，或使用高抽象服务却没有删除自己的旧运维层，Cloud 可能同时保留旧组织成本并增加新账单。

## 11. Fact、Interpretation、Inference 与 Hypothesis

> **Fact（事实）**：Dropbox 表示用户数据从 2012 年约 40 PB 增至 2016 年超过 500 PB；到 2015 年 10 月已由自建基础设施服务超过 90% 的数据。SEC 文件记录 2016 年 Third-party Provider Expense 减少 9,250 万美元，同时自有基础设施折旧、机房和支持增加 5,300 万美元，Infrastructure Optimization 的净基础设施成本下降为 3,950 万美元。

> **Interpretation（解释）**：这些事实说明 Dropbox 没有消灭存储成本，而是把外部服务支出转成内部资产与运营成本，并在当时规模、利用率和组织能力下得到净收益。

> **Inference（推断）**：Dropbox 的超大、持续增长、可专门优化的文件存储负载，加上已经存在的基础设施团队，使自建边界比创业初期更有吸引力。这个推断与公开材料一致，但公开资料不能把每一美元收益分配给规模、硬件设计、数据清理、合同变化或软件优化。

> **Hypothesis（仍需验证的假设）**：某个今天的企业只要达到某一 PB、服务器数或年度 Cloud Bill，就应该复制 Dropbox 的选择。验证必须取得该企业自己的需求分布、折扣、人员、资本、可靠性、迁移、供应链和退出数据；Dropbox 的阈值不能外推。

### Evidence Boundary（证据边界）

- Dropbox 工程文章是一手技术叙述，直接支持项目顺序、公开架构和公司报告的规模，但不是独立审计。
- SEC 文件支持会计成本、收入和公司对 Infrastructure Optimization 的归因；它没有识别 Magic Pocket 单独的因果效果，也没有披露 AWS 私有价格、完整硬件 BOM、人员成本或每 PB TCO。
- 500 PB、0.5 Tbit/s 和 92.6 天的换算是理论流量模型；实际迁移包含并发业务、双写、校验、重试和随时间变化的吞吐。
- 120 万美元、1,000 Unit、0.25 美元与 54.8% Break-even 是透明教学假设，不是 Dropbox、AWS 或任何客户的价格与利用率。
- AWS Shared Responsibility 页面主要针对 Security 与 Compliance；可靠性、财务和业务责任必须进一步读取具体服务文档、SLA、架构和合同。

# Industry Apprenticeship（行业学徒制）

## 12. 今天只回答一个行业问题：谁把基础设施产品化，谁为风险池付款？

Cloud Provider 向上游购买土地、电力、服务器、Accelerator、Memory、Storage、NIC、Switch、Optic、软件与劳动，再通过规模、标准化、Pooling 和 Automation 把它们包装成 Instance、Object、Database、Queue、Identity 与其他服务。Customer 的支付沿 Usage、Commitment、Reservation、Request、Storage、Transfer 和 Managed Feature 流向 Provider；Provider 再把收入分配给上游资产、折旧、运营与利润。

客户支付的不是简单的硬件成本加成。价格还要覆盖：

- Provider 在需求到来前建设的 Idle / Headroom；
- 不能完美配对的 Fragmentation；
- 随时供应和快速释放的 Option Value；
- 底层故障、维修、升级、Security 和 Compliance 运营；
- 全球 Region、API、Billing、Support 与 Ecosystem；
- Provider 的资本成本、研发和商业回报。

Provider 也不是接走全部风险。Customer 仍承担产品是否成功、资源是否 Rightsized、架构是否跨故障域、Identity 和 Data 是否正确、迁移是否可行，以及服务中断超出合同补救后的 Business Loss。

**Total Cost of Ownership（总拥有成本）**第一次出现时要这样理解：它不是采购价加电费，而是某项能力在选择的时间窗口内，从获得、运行、保护、改变到退出的完整成本。历史上这个词用于防止买方只看设备标价；在 Cloud 里，它同样防止只看 Instance Rate。付款方是使用计算能力的业务；受益方是需要把技术选择与业务结果放在同一分母的管理者和工程团队；它解决的是“便宜的部件是否产生便宜的完整服务”；常见误解是把一张 TCO Spreadsheet 当成不确定性的精确答案。

**Build vs Buy（自建还是购买）**也不是所有权偏好。Build 表示组织接管更多设计、资本、容量、供应链、运营和故障责任；Buy 表示通过合同购买一个有边界的产品，并支付供应商的风险池与利润。真实架构常是 Hybrid：只对高规模、稳定、差异化明显的层自建，其余继续购买。

因此行业价值不能只看 Revenue 或 Cloud Bill，还要看：

- Cost per successful useful request / recoverable object / completed job；
- Idle、Reserved 与 Stranded Capacity；
- Gross Margin 与 Cash Capital 的时间分布；
- Time-to-market、Scaling Delay 与退出周期；
- Incident、RTO / RPO、SLA Remedy 与剩余业务损失；
- Customer Concentration、Commitment、Data Gravity 与 Switching Cost；
- 软件和运营能否把上游芯片与机房真正转成合格服务。

公开资料可以看到产品边界、List Price、财务汇总和部分案例，却通常看不到客户折扣、内部资源池利用率、产品级成本、Supplier Margin 与责任赔偿条款。没有这些数据时，应保留范围和翻转条件，不编造一个精确 ROI。

## 13. Transfer（迁移）：以后看到“Cloud 比自建贵三倍”，先问什么？

先问分母是不是同一项业务。比较的是一台 VM 与一台服务器，还是相同成功请求、延迟、Region、Durability、RTO、RPO 和支持？

再把账单还原为资源和责任：Compute 为什么一直运行，Storage 有多少 Version，Byte 穿过哪些边界，Managed Service 替代了哪些人员和软件，哪些旧成本其实没有被移除？

然后画需求形状。平均值、峰值、增长误差和可中断部分分别多大？Cloud 的弹性是否真的被使用，自建的设备是否能保持高而安全的利用率？

最后加入时间与退出：上线提前带来多少价值，迁移需要多久，数据移动和应用重写花多少，合同和折旧何时结束？只有结论在这些范围变化后仍稳定，才值得做长期承诺。

## Teach-back（20–30 分钟讨论）

1. 为一项陌生业务服务画出 Cloud 与自建两种完整边界。至少包含 Compute、Storage、Network、Identity、Reliability、Operations、Capacity、Migration 与 Business Interruption；说明每项谁控制、谁付款、谁吸收失败。最后指出哪三个事实最可能让选择翻转。
2. 使用 120 万美元 / 年、1,000 Unit 的透明模型，自选一个 Cloud 单价和三种利用率。先算 Break-even，再加入一项可靠性 Headroom、一项迁移成本和一项 Time-to-market 价值；解释为什么你的最终建议不是单看单位小时价格。

## 15. 现在我们可以重新回答开头的问题

Dropbox 先使用 Amazon、后来建设 Magic Pocket，并不是前后矛盾。创业初期，Public Cloud 用资源池、弹性和运营能力替 Dropbox 承担了大量必须先于需求建设的责任，让公司更快交付产品；当文件存储增长到数百 PB、工作负载变得稳定而专用、内部基础设施能力已经形成时，同一外包边界的持续单位成本超过了 Dropbox 接回资本和运营责任后的完整成本。

2016 年公开数据最清楚地说明了这一点：9,250 万美元外部服务支出减少，同时出现 5,300 万美元折旧、机房和支持增加，净基础设施成本减少 3,950 万美元。Cloud 成本没有神秘消失；它被重新分配，而 Dropbox 在当时条件下让新组合更便宜。

今天在地图上点亮了 `SYSTEM.COMPUTE.CLOUD_ECONOMICS_SHARED_RESPONSIBILITY_INTEGRATION`：我们学会从一项完整业务服务出发，沿资产、利用率、弹性、运营、可靠性、责任和退出边界判断 Total Cost，而不把 Rent-vs-Buy 口号当结论。下一步通向 Semiconductor-to-Cloud Integration（半导体到云服务整合）：把 11 月从 Wafer、Fab、Package、HBM、GPU、Server、Network、Data Center 到 Cloud 的完整物理流、钱流和控制权重新闭合，判断一美元云收入怎样沿价值链分配。
