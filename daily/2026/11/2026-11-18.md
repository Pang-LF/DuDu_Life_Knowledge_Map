# Mastery Core（掌握核心）

## 1. Opening Puzzle（开场谜题）：系统说“上传成功”，下一秒为什么还可能读不到？

你把一张照片上传到云存储。界面显示 Success。现在有四个不同问题：

- 明年照片的字节还在不在？
- 此刻服务能不能响应 GET？
- GET 会不会返回刚写入的新版本，而不是旧版本或“找不到”？
- 如果整个 Region 消失，另一个 Region 最多落后多久？

日常语言很容易把四问压成一句“数据安全吗”。可它们分别对应 Durability、Availability、Consistency 和 Disaster-recovery RPO。一个系统可以做到照片字节没有丢，但暂时无法读取；可以高度可用，却返回旧版本；可以在当前 Region 强一致，却让异步的跨区域副本落后几分钟。

所以“成功”不是自然事实，而是一份协议：服务在什么条件下才向客户端确认、确认之后承诺什么、没有承诺什么。

## 2. 先定义母概念：Storage System（存储系统）是什么？

Storage System（存储系统）把数据从短暂计算状态保存为可寻址、可读取、可更新并可恢复的持久状态。它至少管理五件事：

1. **Identity（身份）**：这份数据叫什么，Bucket、Key、Version 或 Block Address 是什么？
2. **Bytes（字节）**：实际内容是什么，是否完整？
3. **Metadata（元数据）**：位置、大小、版本、权限、时间与校验信息是什么？
4. **Placement & Replication（放置与复制）**：副本在哪些设备和故障域？
5. **Read / Write Semantics（读写语义）**：一次成功写入后，哪些读取在什么顺序下必须看见什么？

今天以 Object Storage（对象存储）为主：客户端用一个 Key 读写完整 Object，不直接管理底层磁盘。Object Storage 历史上解决的是海量、耐久、按名称访问的非结构化数据；它常用于图片、日志、备份与 Data Lake。常见误解是把它当成本地磁盘的远程版本：实际上它的更新粒度、延迟、请求计费、版本和一致性接口都不同。

先定义 Storage System，才能理解 Durability 等性质。否则“十一位九”“强一致”“跨区域复制”只是互不相连的标签。

## 3. Follow One Object（跟随一个对象）：从 PUT 到可恢复状态

客户端对 `photo.jpg` 发出 PUT。一个简化但有用的路径是：

1. **Receive**：入口验证身份、权限、对象名和请求完整性。
2. **Encode & Check**：系统计算或验证 Checksum；某些系统还会做 Erasure Coding（纠删码），把数据变成多个可重建片段。
3. **Place**：Placement 选择不同设备或 Failure Domain，避免所有副本共享一块盘、一个机架或一个位置。
4. **Persist**：数据与 Metadata 写入满足当前确认规则的存储位置。
5. **Acknowledge**：只有达到服务规定的成功条件，客户端才收到 Success。
6. **Read**：后续 GET 通过 Metadata 找到合格副本，并按 Consistency 规则选择版本。
7. **Scrub & Repair**：后台通过 Checksum、巡检和副本比较发现静默损坏或缺失，再从健康副本重建。
8. **Replicate for Recovery**：若客户启用跨区域复制，另一条异步路径把对象和部分 Metadata 复制到目标 Region。

这八步里，复制只是中间机制。没有确认规则，就不知道“Success”覆盖了几份持久写入；没有 Failure Domain，就不知道副本是否独立；没有读规则，就不知道哪个版本可见；没有校验和修复，坏副本可能长期潜伏；没有监控复制延迟，就不知道跨区域恢复点。

## 4. 四个承诺必须分开

| 承诺 | 精确问题 | 常用证据 | 它不自动保证什么 |
|---|---|---|---|
| Durability（持久性） | 一段时间后，正确字节仍存在的概率多大？ | 副本 / 纠删码、故障域、Checksum、Scrub、Repair、Versioning | 此刻可读、低延迟、最新版本 |
| Availability（可用性） | 一次有效请求此刻能否在时间边界内成功？ | Request Success、Latency、完整服务路径、Failover | 字节永不丢、一定读到最新版本 |
| Consistency（一致性） | 多次读写的可见顺序允许是什么？ | API 语义、并发历史、版本与顺序测试 | 服务永远在线、灾难后零数据损失 |
| RPO（恢复点目标） | 灾难恢复后最多允许回退多旧？ | 复制延迟、最后复制版本、恢复演练 | RTO、正常读取一致性、单对象持久性 |

一个极端对照能把边界看清：把磁盘锁进不会损坏的保险柜，数据 Durability 可能很高，但 Availability 是零；把旧缓存放在全球许多位置，Availability 很高，但 Consistency 可能很弱；同 Region 每次写入强一致，不代表异步灾备 Region 的 RPO 为零。

## 5. “十一位九”究竟是什么意思？

AWS 当前文档说，S3 Standard 被设计为一年内 `99.999999999%`，即十一位九的 Object Durability，并在至少三个 Availability Zone 冗余存储数据；它同时给出 `99.99%` 的 Availability 设计值。

把两个数字翻译成同一数量级。十一位九意味着教学上可把年对象损失概率看成约 `10^-11`。如果一个账户整年保存 10 亿个对象，透明期望值模型是：

```text
Expected lost objects
= 1,000,000,000 × 10^-11
= 0.01 object / year
```

也就是长期统计期望约每 100 年一个对象，而不是“这一百年一定只丢一个”。相关故障、错误权限、恶意删除、客户覆盖和模型边界都不能从这个小数中消失。

同一个产品的 99.99% Availability 若按 365 天换算，对应约 52.56 分钟年度不可用预算：

```text
365 × 24 × 60 × 0.01% ≈ 52.56 minutes
```

一个是对象年损失概率的设计目标，一个是请求服务时间比例；分母不同，不能互换。**Durability 的“九”比 Availability 多，不代表每次 GET 都会成功。**

## 6. Replication（复制）怎样提高持久性，又为什么仍然不够？

Replication 是把同一逻辑数据保存为多个可用副本。付款方可能是 Provider，也可能是 Customer：同 Region 基础冗余可包含在产品价内，跨 Region、额外版本和复制请求则可能单独计费。受益方是需要设备、机架、位置或区域故障后仍能找回数据的人。

三份副本只有在以下问题都有答案时才有意义：

- 副本是否跨过相关的 Failure Domain？
- 写入在一份、两份还是更多份持久化后确认？
- 某份损坏由什么信号发现，多久发现？
- Repair 从哪份健康副本重建，修复期间风险怎样变化？
- 错误删除和错误覆盖会不会也迅速复制？

最后一问很重要。Replication 忠实复制状态变化，可能把“坏操作”也复制出去。Versioning（版本控制）解决另一类问题：同一个 Key 的旧版本仍可保留。AWS 文档明确说明，S3 Versioning 保存的是每个完整 Object 版本，不是增量差异；简单 Delete 通常添加 Delete Marker，而显式删除指定 Version ID 才永久移除该版本。

因此一个 100 GB 对象每天完整覆盖一次、保留 30 个版本而不设 Lifecycle，近似需要：

```text
100 GB × 30 full versions = 3,000 GB ≈ 3 TB
```

版本提高了误删和覆盖后的可恢复性，却把存储、治理和永久删除成本带回来。它不是免费复制，也不等于离线不可变备份。

## 7. Consistency（一次成功写入后，后续读取允许看见什么？）

Consistency 不是“数据有没有复制完整”，而是并发读写看见的顺序规则。

- **Strong Read-after-write Consistency（强读后写一致性）**：一次写入成功返回后，后续读取必须看见新版本。
- **Eventual Consistency（最终一致性）**：如果不再发生新更新，副本最终收敛；收敛前某些读取可能看见旧版本或缺少对象。
- **Atomic Object Update（原子对象更新）**：读取看见旧对象或新对象，不会看见一半旧、一半新。

用一个三副本教学模型建立直觉。若写入需要两个副本确认，读取也查询两个副本，`W + R = 2 + 2 > 3`，读集合与写集合必然至少重叠一份。这个 Quorum（法定人数）直觉解释了为什么读写集合重叠有助于看到新值。

但它不是 S3 内部算法的公开描述，也不能单独解决并发写入顺序、网络分区、失败重试、Metadata 与版本选择。真正的 Strong Consistency 还需要定义谁决定最新版本、怎样排序，以及故障时是否拒绝请求而不是返回旧值。

## 8. Deep Case — Amazon S3，2006–2020：字节已安全写入，Data Lake 为什么还要维护另一套目录？

### Before：海量对象存储优先解决规模与持久性

S3 在 2006 年推出后，让客户不必预先购买磁盘阵列和文件服务器，就能用 API 保存大量对象。对象可以在写入被接受后持久保存，但早期 S3 的部分读取与 LIST 采用 Eventual Consistency。

这不是“对象随机丢失”。它意味着 PUT 已经成功后的一小段时间里，不同读取路径可能还没有全部看见新对象。对个人上传图片，这个窗口也许只是刷新一下；对自动化 Data Pipeline，它会改变下一步输入集合。

### Pressure Builds：一份刚写入的文件，可能从下一项计算的清单里消失

跟随一个 Data Lake Partition。上游 Job 写入 `part-0001`，PUT 返回 Success；下游 Job 立刻 LIST 这个目录，准备把所有 Partition 纳入计算。如果 LIST 暂时漏掉刚写对象，下游并不知道自己看到的是一个不完整集合。

这比明确报错更危险：Job 可能成功结束，却计算了不完整数据。客户因此需要等待、重试、维护额外 Metadata，或使用 EMRFS Consistent View、S3Guard 等一致性辅助层。主存储与辅助目录必须一起运行、扩容和修复。

### Turning Point：Data Lake 规模把“短暂不可见”变成长期架构成本

Dropbox 把分析平台迁到 S3 时，AWS 公开案例给出的规模是 34 PB。34 PB 不是 34 PB 都同时重写，也不是一次强一致性实验；它说明辅助一致性机制要面对的对象目录、作业和运维规模已经非常大。

当越来越多 Analytics、Machine Learning 和 Lakehouse 工作负载把 S3 当共享事实层，“写入成功后还需旁路目录判断是否可见”不再只是应用细节，而成为平台复杂度、故障面和成本。

### Cascade：Durability 没有失败，理解却仍可能失败

对象字节可以已经安全存在，GET / LIST 的可见性仍可能落后。应用于是引入第二套 Metadata Store；第二套 Store 又需要权限、容量、备份、故障恢复和与 S3 的对账。若两套状态分歧，团队要判断哪个才是事实。

这条级联揭示当天核心：Durability 回答“字节是否活着”，Consistency 回答“操作何时必须看见它”。把两者混成“数据安全”，就会错过 Data Pipeline 的真正故障机制。

### Decision：改变存储协议，而不是要求每个客户继续补丁

2020 年 12 月 1 日，AWS 宣布 S3 的 GET、PUT、LIST，以及 Tags、ACL 和 Metadata 变更在所有现有和新对象、所有 Region 上提供 Strong Read-after-write Consistency。AWS 表示没有额外费用、没有性能影响，也不需要跨 Region 的 Global Dependency。

从协议角度，这一改变把“成功写入后的最新版本可见性”纳入基础产品承诺。客户不再需要仅为了弥补 S3 可见性窗口而维护旁路一致性层。

### Outcome：一个 Object 的 Success 变成更完整的下游事实

写入成功后，后续 GET 返回新对象，LIST 也反映变化；覆盖和删除同样具有强一致的可见性。AWS 文档还说明单个 Key 的更新是 Atomic：并发 GET 看见旧版本或新版本，不会看见部分更新的损坏对象。

这没有把 Availability 变成 100%，也没有给跨 Region 异步复制零延迟。它只是把一项关键语义从“最终会看见”提高为“成功后立即应看见”。Dropbox 的公司陈述认为这可以移除软件开销并降低运行成本；这是客户 / 厂商陈述，不是所有工作负载的独立成本审计。

### Aftermath：更强一致性减少了架构层，却没有消灭恢复问题

Data Lake 可以少维护一层一致性旁路，但 Versioning、Backup、Cross-region Replication、Access Control 与 Disaster Recovery 仍然存在。Strong Consistency 甚至会更快地让所有读取看见一次正确授权但错误的覆盖；它不会替客户决定是否保留旧版本。

因此 2020 年改变不是“存储问题全部解决”，而是把四个承诺中的 Consistency 单独提高，同时保留 Durability、Availability 与 RPO 的独立工程边界。

## 9. Meaningful Comparison（有意义的对照）：同 Region 强一致，跨 Region 为什么仍可能落后？

Amazon S3 Replication Time Control（RTC）是额外的复制能力。AWS 当前说明把它设计为在 15 分钟内复制 99.99% 的新对象；合同 SLA 则以每个 Region Pair、每月 99.9% 的对象在 15 分钟内完成作为门槛，未达到时按条款提供 Service Credit。

这里有三个不同数字：

- `15 minutes`：观察一个对象复制完成的时间界限；
- `99.99%`：产品设计目标；
- `99.9%`：SLA 中触发补救的月度门槛。

设计目标不等于合同门槛，Service Credit 也不等于恢复丢失业务。若应用持续写入 2 GB/min，源 Region 在一个透明的 15 分钟复制窗口末端完全不可恢复，简单上界是：

```text
2 GB/min × 15 min = 30 GB not-yet-confirmed-at-destination
```

这不是 RTC 保证会丢 30 GB，也不是 S3 实测；真实暴露取决于每个对象复制状态、恢复时点和失败模式。它只说明：异步复制的延迟可以直接变成 Disaster-recovery RPO 风险，必须用 Metrics 和恢复演练验证。

## 10. Boundary & Counterexample（边界与反例）

更多同步副本不总是更好。跨远距离 Region 等待每份副本确认，会增加光速传播、协调和网络分区带来的写入延迟或不可用性；异步复制保持本地写入速度，却允许目标 Region 落后。系统必须在 Consistency、Latency、Availability、RPO 和成本之间做明确选择。

同样，One Zone 存储并非天然错误。AWS S3 One Zone-IA 把数据放在单个 AZ，价格更低但不承受整个 AZ 的物理丢失；对于可重新生成的 Thumbnail 或已经在别处保存的副本，这可能是合理选择。把唯一的合规档案放进去，却与需求不匹配。

正确问题不是“有没有最多副本”，而是：**对这份数据的价值、重建成本、访问模式与恢复目标，哪一组确认、隔离、可见性、版本和修复承诺最合适？**

# Industry Apprenticeship（行业学徒制）

## 11. 今天的行业问题：客户保存一个 Object，谁为主副本、冗余副本、请求、取回、跨区流量、版本和恢复付款？

先把玩家与价值流分开：

- **Cloud Provider** 建设设备、AZ、Region、Metadata、校验、修复和计量系统，并把部分基础冗余打包进 Storage Class。
- **Customer / Data Owner** 选择 Class、Region、Versioning、Lifecycle、Replication、Retention 与访问权限，并支付使用费用。
- **Application / Platform Team** 决定写入确认后的业务动作、是否能容忍旧读、怎样重试和怎样恢复。
- **End User / Regulator** 关心照片、交易、模型或档案最终是否正确、及时、可追溯。

### Storage Class（存储类别）为什么出现？

并非所有字节都同样常读、同样难重建或需要同样快恢复。Storage Class 把访问频率、位置冗余、取回速度、最短保存期和价格组合成不同产品。

AWS 当前 S3 文档中，Standard 跨至少三个 AZ、设计可用性 99.99%；Standard-IA 也跨至少三个 AZ，但设计可用性 99.9%，有 30 天最短保存期、最低计费对象大小与取回费用；One Zone-IA 在单 AZ，适合可重建数据或另一份副本；Archive 类别用更慢取回交换更低存储成本。

历史原因是冷数据若一直占用最昂贵、最快的在线资源，会让所有客户为不需要的访问能力付费。付款方是 Data Owner，受益方也是 Data Owner；Provider 通过分层调度不同介质和服务能力。常见误解是“便宜 Class 只是同样产品打折”，实际上故障域、访问时延、最短期限和取回收费可能都不同。

### 一笔账怎样展开？

客户账单不只是 `$ / GB-month`：

- Source 与 Destination 都保存副本，因此跨区域复制通常支付两边 Storage；
- 复制会产生 Replication PUT，请求本身也计量；
- Cross-region Replication 可能产生源 Region 的跨区 Data Transfer；
- RTC 还可能增加专门的 Data Transfer 与 Metrics 费用；
- Versioning 的每个完整版本都占用存储；
- Infrequent Access 与 Archive 可能产生 Retrieval、最短期限或提前删除费用；
- Lifecycle 可以自动转换和过期版本，但错误规则也可能过早删除恢复点。

因此最低 `$ / GB-month` 不等于最低 Cost per Recoverable Object。真正要比较的是：在目标 Failure Domain、RPO、RTO、访问频率与保留要求下，保存、验证、复制、取回、传输和演练的全生命周期成本。

## 12. Industry Vocabulary（行业词汇，第一次完整拆解）

- **Object Storage**：按 Key 管理完整对象的服务。解决海量非结构化数据寻址和耐久保存；客户按存储、请求、传输和附加能力付费。常见误解是把它当成本地可随机覆盖的 Disk。
- **Checksum**：从字节计算出的完整性摘要，用来发现传输或存储中的意外变化。它帮助发现错误，不自动提供健康副本，也不证明内容在业务上正确。
- **Erasure Coding**：把数据编码成多个片段，只需其中足够多片段就能重建。它用计算和网络换取比完整复制更高的空间效率；编码片段数量本身不等于独立故障域数量。
- **Versioning**：同一 Key 保留多个完整版本，主要解决误覆盖和误删恢复。它由客户启用与治理，会增加存储，不等于离线 Backup。
- **Cross-region Replication**：把对象异步复制到另一 Region，解决区域隔离、合规或就近访问。客户支付目标存储、请求与相关传输；它不自动提供零 RPO 或完整应用恢复。
- **Egress / Data Transfer Out**：数据离开一个服务或 Region 的传输计量。历史上它覆盖网络容量与跨边界流量成本，也影响客户迁移和多云经济性；“对象已经付过存储费”不代表所有移动免费。

## 13. Fact、Interpretation、Inference 与 Hypothesis

> **Fact（事实）**：AWS 当前文档把 S3 Standard 设计目标写为十一位九 Durability、99.99% Availability 与至少三个 AZ；2020 年 AWS 宣布所有 S3 GET、PUT、LIST 等操作提供强读后写一致性；Versioning 保存完整版本；RTC 的设计目标和合同 SLA 分别使用 99.99% 与 99.9% 的 15 分钟复制口径。

> **Interpretation（解释）**：这些数字和功能保护不同对象：字节留存、请求成功、版本可见、误删恢复和跨区域恢复点，不能用一个“安全”标签互相替代。

> **Inference（推断）**：对重要数据，价值更高的审计顺序通常是确认语义 → 故障域 → 一致性 → 校验修复 → 版本 / 删除治理 → 复制延迟与恢复演练，而不是先数副本。

> **Hypothesis（仍需验证的假设）**：某个具体应用能在 Region 丧失后满足其 RPO / RTO。验证需要对象级复制状态、依赖服务、权限、密钥、DNS、恢复容量、恢复顺序和 Game Day 数据；启用 Replication 本身不够。

### Evidence Boundary（证据边界）

今天主要使用 AWS 官方产品文档与 AWS 自述案例。它们可以支持公开语义、设计目标、价格组成和公司所述改进，但不是 S3 内部协议、独立故障率或所有客户成本的审计。三副本 Quorum、十亿对象期望损失、30 GB RPO 和 3 TB Versioning 均为透明教学模型，不代表 S3 的未公开实现或客户实测。RTC 的 99.99% 是设计目标，99.9% 是 SLA 门槛，不能混写。

## 14. Transfer（迁移）：以后看到“数据已安全复制”，按什么顺序追问？

先指定一个 Object、一次 PUT 和一个 Failure。问 Success 在几份什么性质的持久写入后返回，副本隔离的是 Device、Rack、AZ 还是 Region。

再问读取语义。成功后 GET / LIST 必须看见最新版本吗？并发写入怎样排序？失败时系统会返回旧值、错误，还是阻塞？

然后追问静默损坏和人为错误。Checksum 怎样产生与验证，Scrub 和 Repair 多久运行，Versioning、Retention、Immutable Copy 与 Delete 权限怎样分开？

最后做恢复测试。目标 Region 最后复制到哪个 Version，DNS、Identity、Key、Application 与 Capacity 是否可用，真实 RPO / RTO 是否符合业务，而不是只看控制台中“Replication enabled”。

- **Cloud Network, DNS & Data Movement（云网络、DNS 与数据移动）**：副本同步、读取和恢复都受路径、带宽、时延、路由与缓存约束。
