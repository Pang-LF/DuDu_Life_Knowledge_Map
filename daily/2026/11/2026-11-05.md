# Mastery Core（掌握核心）

## 1. 开场：一段已经通过所有软件测试的逻辑，为什么 Fab 仍然无法制造？

想象你写了一段数字逻辑：两个输入都为 1 时，输出才为 1。仿真显示它在所有输入组合下都正确。你把代码发给 Fab，并说：“请把这个 AND Gate（与门）造到硅片上。”

Fab 仍然无法行动。代码没有告诉它使用哪一种晶体管、供电电压是多少、器件在温度和制造波动下多快、金属线放在哪一层、线宽和间距至少多大、哪些形状代表接触孔，也没有告诉它相邻结构怎样避免短路或可靠性失效。

昨天我们知道制造需要一层层选择位置。今天的问题正好反过来：设计团队怎样把“我要这个逻辑功能”变成几十层可制造的几何图形，同时又不需要知道 Foundry 每一台设备的秘密配方？

## 2. 先定义母概念：Chip Design（芯片设计）制造的不是硅，而是受约束的意图

Chip Design（芯片设计）是把产品要完成的功能，逐步转换成电路、器件、连接、时钟、电源和物理几何，并证明这些内容在规定的性能、功耗、面积、可靠性和制造约束下能够工作。

设计的直接产物是 Information（信息）：Specification（规格）、RTL（寄存器传输级描述）、Schematic（电路图）、Netlist（网表）、Layout（版图）、约束、验证结果和最终制造数据库。Fab 的产物是 Processed Wafer（已加工晶圆）。两者之间必须有一个双方都能执行、又不必暴露全部工艺秘密的接口。

这个接口就是 Process Design Kit / PDK（工艺设计套件）。它由 Foundry 针对一条具体 Process Technology（工艺技术）发布并维护，常见内容包括：

- Device Models（器件模型），告诉仿真工具晶体管、电阻和电容在不同条件下怎样表现；
- Layer Definitions / Technology Files（层定义 / 工艺文件），告诉版图工具哪些数字层对应扩散区、多晶硅、接触孔和不同金属层；
- Design Rules（设计规则）及可执行 DRC Rule Deck（设计规则检查规则集），规定宽度、间距、包围、密度等几何边界；
- Extraction Rules（寄生参数提取规则），把版图中的线和邻近结构转换为电阻、电容等实际影响；
- LVS Rules（版图与电路图比对规则），从版图抽取器件和连接，再与原始网表或电路图比较；
- PCells、symbols 与其他经过验证的器件表示，帮助工具生成和识别可制造结构。

具体 PDK 的内容、许可与支持范围会变化。Standard Cell Library（标准单元库）、Memory Compiler（存储器生成器）、接口 IP 和完整参考流程可能来自 Foundry、EDA 公司或第三方 IP 伙伴，不应把它们全部误认为 PDK 本体。

## 3. 跟随一个最小单位：一个 AND Gate 怎样从行为变成几何？

第一步是 Specification（规格）。团队先说明这个逻辑要做什么、工作频率、供电、延迟、功耗、测试与外部接口要求。若规格本身含糊，后面的工具只能更精确地实现错误目标。

第二步是 RTL（寄存器传输级描述）与 Functional Verification（功能验证）。RTL 用硬件描述语言表达数据怎样在时钟边沿之间流动以及逻辑怎样变换；仿真、形式验证和测试环境检查它是否符合规格。这里主要回答“逻辑对不对”，还没有决定每个晶体管在晶圆上的坐标。

第三步是 Logic Synthesis（逻辑综合）。工具读取 RTL、时序与面积等约束，以及针对目标工艺表征过的 Standard Cells（标准单元），把行为转换成由 AND、NAND、Flip-flop（触发器）等单元及其连接构成的 Gate-level Netlist（门级网表）。同一段 RTL 在不同 PDK、单元库、频率和功耗目标下，可能得到不同实现。

第四步是 Physical Implementation（物理实现）。Floorplanning（平面规划）决定芯片边界、主要模块、存储器、I/O 与电源结构；Placement（布局）给标准单元分配位置；Clock-tree Synthesis（时钟树综合）分发时钟；Routing（布线）在允许的金属层和通孔中连接网表。此时抽象连接第一次变成具有长度、宽度、邻近关系和拥塞的几何。

第五步是 Extraction & Signoff（提取与签核）。布线不再是理想连线：它有电阻和电容，电源网络会压降，快速信号会耦合，金属承载电流也有可靠性限制。工具用 PDK 和认证流程重新计算 Timing（时序）、Power（功耗）、Signal Integrity（信号完整性）、IR Drop（电压降）、Electromigration（电迁移）等，并检查几何与连接。

最后才是 Stream-out / Tape-out（制造数据导出 / 设计定稿交付）：团队冻结一个受版本控制的版图数据库，通常以 GDSII 或 OASIS 等格式交给 Foundry。Foundry 与 Mask Data Preparation（光罩数据准备）环节还可能进行层映射、数据检查、可制造性处理、光学邻近修正和图形分割，最终生成写入每张 Photomask / Reticle（光罩）的数据。

## 4. PDK 为什么更像“可执行合同”，而不是知识百科？

Foundry 不会把完整制造配方交给每个客户。客户通常不需要知道某台刻蚀机的精确气体流量，也不应随意修改退火温度。它需要知道的是：如果我画出这种器件和几何，Foundry 承诺按哪一组模型、规则、层定义和验收流程解释它。

“可执行”很重要。PDF 中写着最小间距，只能让工程师阅读；DRC Rule Deck 能让工具在数十亿图形中自动找出违规。器件模型不仅说晶体管“可能更慢”，还允许仿真和时序工具在不同 Process、Voltage、Temperature / PVT（工艺、电压、温度）条件下计算边界。Extraction Deck（提取规则集）则把几何变成设计必须承受的寄生电阻与电容。

“合同”也不是法律意义上的全部商业条款，而是一种技术接口：Foundry 定义一条可接受的设计空间，客户在其中作出产品选择。PDK 版本、EDA 工具版本、IP 版本和签核选项必须彼此一致；换了其中一个版本，原来的“clean”结果不一定自动成立。

## 5. 四种检查分别能证明什么，不能证明什么？

Design Rule Check / DRC（设计规则检查）询问：版图几何是否满足 Foundry 的制造规则？它能发现线太窄、间距不足、接触孔没有被金属充分包围等问题。DRC clean 表示没有发现已编码规则的违规，不表示逻辑功能正确，也不表示所有良率风险为零。

Layout Versus Schematic / LVS（版图与电路图比对）询问：从版图抽取出的器件和连接，是否与预期的网表或电路图一致？它能发现 open（断路）、short（短路）、器件或端口不匹配。LVS clean 仍不能证明规格正确；如果“黄金网表”本身引用了错误 ROM 版本，版图和错误网表完全一致也可能通过。

Timing / Power / Integrity Signoff（时序、功耗与完整性签核）询问：在指定的工作负载、模型、PVT corners（边界条件）和假设下，信号是否按时到达、电源是否稳、金属与器件是否在可靠范围内。它依赖模型和场景覆盖，不是对所有未来使用状态的数学证明。

Functional Verification（功能验证）询问：实现是否符合规格。它可以发生在 RTL、门级网表和形式模型等多个阶段，但验证覆盖仍有边界。四类检查互补，因为“几何可造”“连接一致”“电气满足边界”和“产品功能正确”不是同一个命题。

## 6. Tape-out 到底冻结了什么？

Tape-out 这个名字来自过去把最终设计数据写到磁带交付制造的历史。今天通常不再递交实体磁带，但这个词仍表示一个组织与技术承诺点：某一版设计、IP、PDK、规则、工具设置和签核证据被指定为制造输入。

冻结并不意味着所有文件从此永远不动。Foundry 可能在数据准备阶段要求修正，团队也可能批准 waiver（豁免）或执行 Engineering Change Order / ECO（工程变更）。但任何变更都必须受控地重新检查受影响内容，否则“通过签核”的对象和“实际制造”的对象会分离。

Tape-out 也不是量产开始。之后还有 Foundry 数据验收、光罩制作、Wafer Start（晶圆投片）、数周或更久的制造、Wafer Probe（晶圆级测试）、封装、成品测试、Bring-up（首次上电调试）和资格化。第一次回来能工作的 silicon 常被称为 first-pass silicon success（一次投片成功），但“能上电”“通过功能测试”“满足全部性能”“达到经济良率”和“可以量产”仍是不同状态。

## 7. Before：为什么 Open-source Hardware（开源硬件）过去常停在“可以看代码”？

到 2020 年前，RISC-V 等开放指令集和许多 RTL 项目已经让人们能够共享数字逻辑。但从共享 RTL 到真实硅片，中间仍缺少制造接口。商用 Foundry PDK 通常受 NDA（保密协议）与许可限制；经过认证的 EDA 工具、IP、设计服务、光罩和工程批次也要付费。

这不是单纯的“行业不愿开放”。PDK 包含从实际制造数据提炼出的模型、规则与流程，Foundry 必须维护准确性、版本和客户支持；错误接口可能浪费昂贵光罩和晶圆。先进工艺还涉及更复杂的商业、知识产权与安全边界。

但结果是：一位学生或研究者即使能公开 RTL，也难以公开一套其他人可以复制的 RTL-to-GDS（从逻辑到版图）流程，更难让陌生人验证同一个设计是否真的可制造。开源停在设计意图，制造仍是封闭接口。

## 8. Pressure Builds：为什么“开放一份规则文件”仍然不够？

Google 与开放硬件社区想降低实验门槛，SkyWater 拥有一条成熟的 130 nm Mixed-signal CMOS（混合信号 CMOS）工艺。但 PDK 即使可以下载，也不会自动把 RTL 变成通过检查的 GDS。

设计者还需要标准单元、工具流程、统一的芯片外框与 I/O 接口、提交门户、版本管理、许可检查、数据完整性检查、DRC，以及真正愿意接收这些数据的 Foundry 和制造排程。更现实的问题是固定成本：一位研究者独占一套光罩和一片完整晶圆，绝大部分面积与成本都可能被浪费。

因此压力不是“有没有设计文件”，而是能否把 PDK、EDA flow（电子设计自动化流程）、提交规则、共享制造与实物交付连成一个闭环。

## 9. Turning Point：SKY130 为什么不只是一份 GitHub 仓库？

2020 年，Google 与 SkyWater 发布针对 SkyWater 130 nm 工艺的 SKY130 Open Source PDK（开源工艺设计套件）；Google、SkyWater 与 Efabless 随后启动 Open Source Multi-Project Wafer / MPW（开源多项目晶圆）计划。Google 提供赞助，SkyWater 提供工艺与制造，Efabless 提供提交平台、标准化 harness（载体框架）和 OpenLane RTL-to-GDS 开源流程。

SkyWater 在 2020 年 11 月宣布，首轮 PDK 发布后两周下载量已超过 1,700 次；每次 shuttle（流片班车）计划提供 40 个设计名额，Efabless 在把设计拼到同一晶圆前执行许可、数据完整性和 DRC 检查。符合开放许可要求的入选设计可以由赞助方承担制造费用。

关键变化不是“文件免费”这一个动作，而是工艺定义、自动化工具、提交接口、共享光罩与真实制造第一次形成可重复路径。PDK 把 Foundry 的物理边界交给工具，OpenLane 把 RTL 逐步转换成 GDS，MPW 再把多个小设计组合到共同的制造批次中。

## 10. Cascade：跟随一个开放设计走完最后一公里

一位设计者先让 RTL 通过功能验证，再使用针对 SKY130 的标准单元和 PDK 完成综合、布局、时钟树、布线、提取和签核。最终数据必须装进规定的 harness 区域，并满足层映射、I/O、尺寸和验证要求。

Efabless 不只是收一个压缩包。平台检查设计是否满足开放许可、文件是否完整、数据有没有损坏、DRC 是否符合要求，再把多个通过的设计聚合成同一次 MPW。Foundry 接收的是一个经过统一接口整理的制造数据库，而不是来自 40 个作者、40 种命名和40套假设的任意文件。

晶圆制造后，区域被切割成 Die（裸片），再进入封装和 bring-up。若某个设计不工作，工程师需要区分 RTL bug、IP 版本、时序、供电、版图、签核覆盖、封装、测试板和制造偏差。开放流程让其他人能够看到设计与验证结果，因而更容易复制问题、提交 bug 或改进工具。

## 11. Decision：开放、成熟节点与共享制造分别放弃了什么？

参与 Google 赞助的 shuttle，设计者获得低成本甚至无直接制造费的真实 silicon 路径，但必须公开设计并遵守项目规则；需要保密商业 IP 的团队则要选择商业服务，例如后来扩展出的付费 shuttle。开放是许可与协作选择，不等于所有商业设计都适合公开。

选择 130 nm 成熟工艺降低了实验复杂度并适合研究、简单微控制器和混合信号设计，却不能代表先进 CPU、GPU 或 HBM 的密度和性能。成熟节点“可以学习完整接口”与“可以替代先进节点”是两个命题。

更重要的是，SKY130 仓库当时明确把开放 PDK 标为 Experimental Preview / Alpha（实验预览 / 早期版本），并警告它不适合直接用于生产设计。SkyWater 的商业工艺已经生产过大量芯片，不代表新整理的开放 PDK 在每一种工具和用法中都已达到生产保证。

## 12. Outcome：数字说明的不是“人人都能造先进芯片”，而是接口变得可进入

Google 在 2023 年总结：计划已经运行 8 次 SKY130 shuttle 和 1 次 GF180MCU 初始测试；按每次 40 个名额，共制造 360 个设计，来自 19 个国家的提交超过 600 个。`360 / 600 = 60%` 只是累计制造设计数与累计提交数的简单比值，不是单轮录取率，也不能解释延期、重复提交或资格检查原因。

参与者提交的数百个 bug 与 pull request 又改善了 PDK、工具和文档。这里出现一个软件世界熟悉、芯片世界更昂贵的反馈回路：更多设计暴露更多边界问题；修复后的接口使下一批设计更容易重现；真实 silicon 再检验模型和流程。

结果并不是 Foundry 变成一台无人管理的打印机。恰恰相反，计划证明了一套明确 PDK、认证流程、标准载体、提交门和共享制造安排，才把开放逻辑变成可制造版图。

## 13. Aftermath：为什么计划后来把 PDK 交给 CHIPS Alliance？

2023 年，Google 宣布 SKY130 与 GF180MCU Open PDK 将进入 Linux Foundation 的 CHIPS Alliance 工作组，以扩大维护和治理参与。多所大学已把开放 PDK 纳入课程，NIST 也采用 SKY130 迁移其纳米技术研究用设计。

这一步说明 PDK 不是一次性附件。工艺、模型、工具、文档和已知问题需要长期版本治理；设计者必须知道哪个版本被哪条流程验证过。开放治理能改善透明度和复现性，但不会取消 Foundry 对真实工艺、制造验收和生产支持的责任。

## 14. 一个数字为什么会改变理解：MPW 分摊的是哪一类成本？

做一个明确标注为 Toy Cost Allocation（简化成本分摊）的模型。把一套共同 Mask Set（光罩组）和一次 shuttle 准备的固定成本记为 `1 unit`。若一个小设计独占它，设计承担 `1 unit`；若 40 个同面积、同规则设计共享且简单平均，单个设计对应的固定成本份额为 `1 / 40 = 2.5%`。

现实不会如此整齐：设计面积不同，赞助方可能承担费用，数据准备、封装、测试、失败处理和 Foundry 利润仍存在，某些层也可能不共享。这个模型只说明 MPW 的经济机制：它通过把多个设计拼到同一套制造固定成本上，降低每个实验必须独自承担的门槛；它没有让工艺验证、工具、光罩和晶圆变成零成本。

## 15. 有意义的对照：几个经常被混为“设计完成”的状态

| 状态 | 它证明了什么 | 它还没有证明什么 |
| --- | --- | --- |
| RTL simulation clean（RTL 仿真通过） | 已覆盖场景中的逻辑行为符合检查条件 | 几何可制造、时序、电源、全部未知状态正确 |
| Synthesis complete（综合完成） | RTL 已映射到目标库的门级网表 | 放置布线后仍满足时序和功耗 |
| DRC clean（设计规则通过） | 没发现已编码几何规则违规 | 连接、功能、良率或可靠性必然正确 |
| LVS clean（版图电路一致） | 抽取版图与参考网表 / 电路图匹配 | 参考设计本身正确或性能达标 |
| Timing / power signoff（时序 / 功耗签核） | 指定模型、corner 和场景下达到边界 | 所有现实工作负载和制造偏差均被覆盖 |
| Tape-out（设计定稿交付） | 某一受控版本被接受为制造输入 | 已经投片、获得工作芯片或达到量产良率 |
| First silicon（首批硅片） | 真实器件已经返回并可测试 | 完整功能、可靠性、经济良率和量产资格已完成 |

## 16. 反例：通过 Foundry 规则，不等于产品一定正确

PDK 能判断版图是否落在 Foundry 建模和制造规则内，却不知道用户真正想造的是温度传感器、汽车控制器还是加密芯片。一个设计可以 DRC clean、LVS clean，却把规格理解错；也可以引用错误 ROM、遗漏罕见状态、在未覆盖的软件负载下过热。

反过来，一个规则违规也不一定意味着物理上绝对无法制造。某些特殊结构可由 Foundry 审核并给予 waiver，但这会改变责任和风险。规则是对可重复生产经验的工程化边界，不是自然定律；豁免也不是“工具太死板所以忽略它”，而是需要证据、审批和可追踪版本的风险决定。

## 17. Fact、Interpretation、Inference 与 Hypothesis

**Fact（事实）**：Cadence 对 PDK 的公开说明列出器件模型、原理图符号、网表流程、参数化单元、物理验证规则与寄生提取文件。Synopsys 说明 DRC 根据 Foundry runset 检查制造规则，LVS 将版图抽取的器件与连接和参考网表比较。Google、SkyWater 与 Efabless 在 2020 年启动 SKY130 开放 PDK 与 MPW 计划；Google 2023 年记录 360 个制造设计、600 多个提交和 19 个国家。

**Interpretation（解释）**：PDK 的核心价值是把 Foundry 的工艺能力与边界变成 EDA 工具和设计团队可以重复执行的接口，从而减少每次 tape-out 都重新解释制造知识的成本。

**Inference（推断）**：Foundry 的竞争力不只在设备和工艺配方，也在 PDK 准确度、IP 生态、EDA 认证、文档、版本治理和客户支持，因为这些因素影响设计周期与一次投片成功概率。

**Hypothesis（仍需验证的假设）**：开放 PDK 会普遍降低商业先进芯片成本，或任何 PDK 的规则通过率都能预测最终良率。SKY130 计划证明了特定成熟工艺和赞助 shuttle 的可进入性；它不能识别先进节点 IP、光罩、验证与制造成本的反事实，也不能把设计 clean 直接转换为产品良率。

## 19. Industry Apprenticeship：Tape-out 出错时，Fabless 与 Foundry 谁负责？

今天行业里只回答一个问题：**Fabless 公司把版图交给 Foundry 之后，双方各自拥有什么、为哪些工作付钱，又怎样划分设计错误与制造偏差风险？**

先分资产与责任。Fabless 客户通常拥有或依法许可产品规格、RTL、电路、集成方案、验证环境和最终版图；第三方 IP 公司仍拥有其 CPU core、接口、Memory Compiler 或标准单元的知识产权，客户只获得合同许可。EDA 公司拥有设计工具；Foundry 和 EDA 伙伴共同认证某些工具与流程，但工具认证不替客户完成产品验证。

Foundry 拥有 Process Recipe（工艺配方）、制造设施、过程控制数据、工艺演进和 PDK 发布权。客户获得在合同与 NDA 边界内使用 PDK 的权利，不因此拥有刻蚀、沉积、掺杂和良率调优的全部秘密。Mask（光罩）的付款、保管、复用、修改和所有权也受具体合同约束，不能用一条行业口号概括。

钱流通常从 Fabless 客户流向工程师、EDA 软件、第三方 IP、设计服务、光罩 / NRE（一次性工程费用）、工程批次和量产晶圆；Foundry 再支付设备、材料、公用工程、维护、工艺研发与折旧。MPW 把多个客户拼到共同光罩和晶圆上，降低原型固定成本；专属量产 tape-out 则换取更大面积、保密性、排程和产品控制。

风险不能简单写成“设计错客户赔，制造错工厂赔”。若错误 RTL 或错误 IP 版本被准确制造，责任明显偏向客户；若 Foundry 没有按承诺的工艺规格执行，责任偏向 Foundry。但 Yield Loss（良率损失）可能来自设计敏感性、规则边缘使用、光罩数据、随机缺陷、工艺漂移、封装或测试，归因需要失效分析和合同定义。公开资料通常不披露具体赔偿上限、良率保证和重投条件。

从业者因此看 First-pass Silicon Success（一次投片成功）、Tape-out Schedule（定稿进度）、Signoff Closure（签核收敛）、Mask Revision（光罩修改）、Turnaround Time（周转时间）、Wafer Yield（晶圆良率）、Test Yield（测试良率）和 Respin（重新流片）。Respin 不是按一下重新打印：它可能意味着修设计、重新签核、修改部分或全部光罩、等待新的制造批次并推迟收入。

Foundry 的议价权来自稀缺工艺、准确 PDK、经过验证的 IP / EDA 生态、制造表现、产能和客户切换时间；大型客户的权力来自订单规模、共同开发、可预测需求、工程能力和多源选择。TSMC 把 OIP（开放创新平台）描述为涵盖硅验证 IP、EDA 认证、云设计和设计服务的完整基础设施，目标是缩短 design time、time-to-volume、time-to-market 与 time-to-revenue。这说明 Foundry 出售的不只是晶圆加工，还出售一个降低接口失败和迭代时间的生态。

外行最容易误解的是“Fabless 把图纸发给代工厂”。真正交付的是一个受 PDK、IP、工具版本、签核证据和合同边界共同约束的数据包；双方的关系更像共同维护一条高成本、低容错的接口，而不是普通印刷店接收 PDF。
