# Mastery Core（掌握核心）

## 1. Opening Puzzle（开场谜题）：16,384 张 H100，为什么不能直接写成“16,384 份训练能力”？

想象凌晨两点，Meta 的 Llama 3.1 405B Training Job 正在运行。控制台显示数千台机器通电，GPU 温度正常，网络端口亮着，数据也在 Storage 中。几分钟后，一张 GPU 报错，整个同步训练组停下来；系统从 Checkpoint 恢复，重新安排资源，再继续。午后机房温度变高，吞吐又小幅下降。进入 128K Context 阶段，同样的 GPU 数量每秒完成的模型计算也低于 8K 阶段。

如果“AI Capacity = GPU Count”，这些变化不该发生。硬件数量没有突然消失，为什么训练能力却变了？

答案藏在真正的最小单位里。训练的目的不是让芯片忙，也不是累计 GPU-hours，而是完成一个经过正确性检查、同步成功、并能被后续步骤继承的模型更新。只要这个更新没有完成或没有保留下来，局部设备做过多少工作，都不能完整计入目标产出。

## 2. 先定义母概念：什么是 Useful Model Progress？

把一次训练拆到最小可理解单位。模型读取一批 Token，执行 Forward Pass 产生预测和 Loss，执行 Backward Pass 计算 Gradient，各个 Worker 交换必要状态，Optimizer 更新参数，系统验证数值没有异常，并在适当边界把状态写入 Checkpoint。完成后，下一步能从这个新状态继续。

**Useful Model Progress（有用模型进展）**就是在规定的模型、数据、精度、正确性和恢复边界内，已经完成、验证并能被后续工作继承的模型状态变化。今天用“一个被保留下来的合格训练步”作为最小单位。

这一定义把几种常被混在一起的容量分开：

- **Provisioned Capacity（已配置容量）**：合同或资产清单上存在多少 GPU、服务器和机架；
- **Runnable Capacity（可运行容量）**：满足健康、软件、拓扑、内存和调度条件，能够加入当前 Job 的部分；
- **Active Capacity（活跃容量）**：此刻实际执行工作的部分；
- **Useful Compute（有用计算）**：真正服务模型步骤的计算，而不是等待、重试、无效通信或错误结果；
- **Preserved Progress（保留进展）**：通过验证并越过恢复边界，故障后不需要重做的进展。

只有最后一层直接对应训练目的。GPU-hours 是资源使用记录，不自动等于学习进展；MFU 衡量模型计算相对理论峰值的利用，也不自动说明这些计算经历了多少恢复或最终保留了多少。

## 3. Follow One Unit（跟随一个最小单位）：一个合格训练步怎样穿过整条链？

先留在最靠近目标的地方。Data Pipeline 要提供正确 Token；Model 和 Runtime 决定算子、精度和 Parallelism；Checkpoint 之前的所有 Worker 必须对“当前模型状态”有一致认识。若数据损坏、软件产生 NaN、版本不一致或状态同步失败，设备再忙也不是合格进展。

然后进入 Accelerator。一个 405B Parameter 模型仅把每个参数按 BF16 两个 Byte 存一份，Weights 就约为：

```text
405 billion parameters × 2 bytes ≈ 810 GB
```

一张 H100 的 HBM 是 80 GB。810 GB 已超过十张卡的总容量，而且训练还需要 Gradient、Optimizer State 和 Activation。这个计算不是 Meta 披露的完整内存账本，只是一个下界；它已经足以说明模型不能放进单卡，必须切分状态。

Meta 使用 Data、Tensor、Pipeline 与 Context 四种 Parallelism。每种切分都解决一个约束，也产生新的协调：Tensor Parallelism 让一次矩阵运算跨卡，Pipeline Parallelism 把不同层分给不同阶段，Data Parallelism 复制部分计算并同步 Gradient，Context Parallelism 分摊长序列。Runtime 必须选择一种让模型“装得下、算得动、交换成本可接受”的组合。

再向外走到 Server。Meta 的 Grand Teton 一台包含八张 GPU 和两颗 CPU；在最大披露配置 16,384 张 GPU 下，名义上对应 2,048 台八卡服务器。服务器内的高速互连、CPU Feeding、NIC、Firmware、电源和散热共同决定八张卡能否作为一个合格节点工作。八张健康卡装在错误拓扑、错误固件或供电不足的服务器里，仍不是 Runnable Capacity。

跨服务器以后，Collective Communication 把局部结果拼回共同状态。Meta 的集群端点使用 400 Gbps RoCE；较小 Pod 内具有 Full Bisection Bandwidth，顶部 Aggregation 则披露为 1:7 Oversubscription。Parallelism 必须理解这张拓扑：把通信最频繁的 Worker 放得更近，避免让某个交换层成为所有步骤反复等待的门。

再向物理设施走。16,384 张 H100 按 700 W TDP 简单相乘，GPU-only Nameplate 为：

```text
16,384 × 700 W ≈ 11.47 MW
```

这不是实际平均功率，也没有包含 CPU、NIC、Storage、Power Conversion 与 Cooling。它只是说明为什么 Power 和 Thermal Behavior 不再是背景。Meta 报告当 GPU 同时等待、启动或停止时，功率变化可以达到数十 MW；午后较高温度与 1–2% 的训练吞吐变化相关。机房温度没有减少 GPU 数量，却改变了它们可持续交付的有效能力。

最后再向上游倒推。H100、HBM、Advanced Package、Substrate、Fabricated Die 与 Wafer 都必须经过资格化，才能形成这些服务器。若今天已经部署的 Job 因 Network Straggler 停顿，增加 Wafer Starts 不会立刻提高下一步；若明年计划扩建却拿不到合格 HBM 或 Package Slot，上游反而可能决定新增训练能力。**同一条链，当前运营约束和扩产约束可以位于不同层。**

## 4. Binding Constraint（绑定约束）：不是“最慢的东西”，而是当前最有边际解释力的约束

**Binding Constraint（绑定约束）**是：在给定工作负载、时间尺度和系统状态下，增加一单位该层的有效能力，会提高最终有用输出；而增加非绑定层的能力，暂时不会提高最终输出。

因此不能看使用率最高、价格最贵或故障次数最多就宣布瓶颈。要做一个 Marginal Relief Test（边际缓解测试）：

```text
固定模型、数据、正确性边界与时间窗口
→ 只缓解一个候选约束
→ 观察被保留的合格训练进展是否增加
→ 检查新约束是否随之出现
```

例如：模型状态装不进 HBM 时，增加 Network Bandwidth 不会使 Job Runnable；已经装得下但 All-reduce 等待严重时，改善拓扑或 Collective Library 可能提高每步速度；硬件故障频繁时，Spare、Checkpoint 与自动恢复可能比再增加名义 GPU 数更能提高 Preserved Progress；数据管道无法稳定供给时，GPU 和网络都会等待。

约束还会移动。8K Context 的稳态训练、128K Context 的长序列阶段、一次大规模故障后的恢复窗口、温度较高的午后，以及建设下一座集群，都不是同一个系统状态。今天的答案必须写明“对哪个 Workload、哪个阶段、哪个时间尺度”。

## 5. Main Case — Llama 3.1 405B：一张 GPU 的故障怎样变成整栈问题？

### Before：小规模计算可以把机器故障当局部事件

在普通 Web Service 中，一台机器失败，Load Balancer 可以把无状态请求送往另一台；在小型 Batch Job 中，一个 Task 也可能单独重试。故障仍有成本，但局部失败不必总是暂停整个系统。

大规模同步训练不同。数千个 Worker 共同计算同一个模型更新。一个 Worker 迟到，其他 Worker 可能必须等待；一个 Worker 返回错误状态，整个更新可能无效；故障若发生在 Checkpoint 之间，已做工作还可能重算。最小单位从“一张卡完成一段计算”变成“整个参与组完成并保存一个一致更新”。

### Pressure Builds：405B 参数、15.6T Token 和 `3.8 × 10^25` FLOPs 把所有接口推到可见位置

Meta 报告 Llama 3.1 405B 使用 405 Billion Parameters、15.6 Trillion Training Tokens 与约 `3.8 × 10^25` FLOPs。15.6T Token 不是 15.6T 条独立事实，而是训练数据被切成模型处理单位后的总量；`3.8 × 10^25` 是计算量估计，不是完成质量或训练成本。

规模改变的不只是“要更多 GPU”。模型状态必须切分；每个步骤要交换状态；Storage 要供应数据并写入 Checkpoint；Scheduler 要找到拓扑匹配的健康资源；Power 与 Cooling 要吸收大规模同步变化；错误检测必须区分可恢复故障、软件错误与 Silent Data Corruption。

### Turning Point：最多 16,384 张 H100 被组织成一个训练系统

Meta 披露训练使用最多 16,384 张 H100。每台 Grand Teton Server 有八张 GPU 与两颗 CPU。集群提供 400 Gbps RoCE 连接，并用拓扑感知的 Collective Communication 与四维 Parallelism 将模型映射到硬件。

这一步把 11 月的各层接在一起：HBM 使模型局部状态可访问；GPU 执行并行算子；Server 提供本地互连与支持边界；Network 让跨节点状态同步；Storage 提供数据和恢复点；Power / Cooling 维持可持续频率；Packaging、Fabrication 和 Wafer 则是所有已部署设备成为合格部件的上游前提。

### Cascade：54 天中 419 次意外中断，让可靠性成为吞吐的一部分

Meta 对一个 54-day Snapshot 报告 466 次 Job Interruption，其中 47 次 Planned、419 次 Unexpected。419 除以 54 约为每天 7.76 次，或整个 Job 大约每 3.1 小时遇到一次意外中断。

这不是“每张 GPU 三小时坏一次”。分母是整个大型 Job 的观察时间，事件来自 GPU、HBM、Host、Network、Software、Sensor 与其他类别，系统又包含成千上万个部件，不能把 Job-level Incident Rate 写成单部件 MTBF。

论文表中列出 148 次 Faulty GPU、72 次 HBM3、54 次 Software Bug、35 次 Network Switch / Cable、32 次 Host Maintenance 等。表格把 148 次 Faulty GPU 同时印为 30.1%，但 `148 / 419 ≈ 35.3%`；这是一处源内不一致。因此本课保留 Count，不把 30.1% 当作经重新确认的比例。

故障会沿同步边界级联：一个 Worker 停止，Collective 等待；Job 保存诊断信息；Scheduler 找替代资源；Checkpoint 被读取；模型状态重新分发；所有 Worker 重新建立一致状态。于是 Spare Capacity、Storage Bandwidth、Checkpoint Frequency、Diagnosis Time 和 Repair Automation 都成了 Training Throughput 的组成部分。

### Decision：Meta 没有只买更多 GPU，而是共同设计并行、网络、存储、恢复与物理运行

Meta 使用 240 PB Storage，披露可持续 2 TB/s、峰值 7 TB/s；每张 GPU 的 Checkpoint 分片可在 1 MB 到 4 GB 之间。公司优化 Collective Library、Topology-aware Placement、Failure Diagnosis、Checkpointing、Scheduler 与 Spare，并让绝大多数中断自动处理；54 天窗口中只有三次需要显著人工介入。

公司还对 Air-cooled Grand Teton 进行 Mechanical 与 Thermal 改造，使 H100 可以运行到 700 W，而不是等待整个设施先改成液冷。这是一个真实边界选择：为了更快部署，系统在现有机房限制内重新平衡 Board、Airflow、Power 和 Operations。

### Outcome：38–43% MFU 与超过 90% Effective Training Time 描述不同损失边界

Meta 报告 BF16 Model FLOPs Utilization：8,192 GPU、8K Context 时约 43%；16,384 GPU、8K 时约 41%；16,384 GPU、128K 时约 38%。GPU 数增加一倍没有保持同样 MFU，长 Context 又进一步降低，说明通信、内存和调度开销随配置变化。

MFU 不是“59% 的钱浪费了”。它把 Model FLOPs 与设备理论峰值比较；数据移动、通信、框架开销和某些必要操作可能不进入分子。超过 90% Effective Training Time 则描述经过中断、恢复和维护后，大部分经过时间仍用于训练。两个指标的定义边界不同，不能直接相乘得到一个精确 Goodput。

Model Card 另披露 405B 模型使用 30.84 Million H100 GPU-hours。这个数记录资源使用，不是训练总天数，更不是账单。它不能与 54-day Reliability Snapshot 拼接推导 Wall-clock Time，因为两者覆盖的作业、阶段和统计边界没有被声明为相同。

### Aftermath：完成模型不等于发现一个永久瓶颈

Llama 3.1 405B 的成功说明整栈可以被协调到产生模型，但没有证明 GPU 永远是唯一稀缺层。Model Fit 阶段可能首先受 HBM 与 Sharding 约束；稳态步骤可能受 Compute / Communication Mapping 约束；Long Context 会改变 Memory 与 Collective 压力；Failure State 把 Recovery 和 Spare 变成约束；午后 Thermal State 影响频率；下一代集群建设又可能受电力、合格 Package、HBM、Fabrication 或交付周期约束。

真正可迁移的知识不是“Meta 的瓶颈是 X”，而是每次都从 Preserved Useful Progress 向后追踪，并用边际缓解证据定位当前的 X。

## 6. Meaningful Comparison（有意义的对照）：为什么 Installed GPU、MFU、Effective Time 与 Preserved Progress 不能互换？

| 指标 | 分子大致是什么 | 能回答什么 | 不能单独回答什么 |
|---|---|---|---|
| Installed GPU Count | 已安装设备数量 | 名义资产规模 | 当前 Job 能否运行、是否匹配拓扑、是否产生正确结果 |
| GPU-hours | 设备数量 × 使用时间 | 资源消耗规模 | 单价、总账单、模型质量、重做比例 |
| MFU | 模型 FLOPs / 理论峰值 FLOPs | 算术利用程度 | 中断恢复、结果是否保留、每美元成本 |
| Effective Training Time | 训练状态时间 / 观察时间 | 恢复和等待占用多少时间 | 训练状态内的算术效率、模型质量 |
| Preserved Useful Progress | 验证并可继承的模型状态变化 | 是否真正接近训练目标 | 若无统一质量边界，也不能跨模型简单比较 |

最有意义的运营判断是把这些指标放在同一因果图中，而不是选一个漂亮数字。GPU Count 是潜在资源；Runnable Capacity 需要合格系统；MFU 描述训练状态内部的一个效率边界；Effective Time 描述状态切换；Preserved Progress 才回到最终目的。

## 7. 反例：网络总是 AI 集群瓶颈吗？

不是。如果模型放不进 HBM，Network 再快也启动不了；如果 Data Pipeline 跟不上，GPU 与 Network 会一起等待；如果 Job 已在单机内完成，跨节点网络可能不是主要约束；如果 Software Kernel 映射很差，提升 Fabric Bandwidth 也不会自动提高算术效率。

反过来，Network Utilization 没有达到 100% 也不证明网络不受限。Collective 可能被尾部延迟、拓扑热点、同步顺序或小消息效率限制，而不是被平均带宽占满。瓶颈判断需要对最终步骤做 Marginal Test，而不是把局部使用率当结论。

## 8. Fact、Interpretation、Inference 与 Hypothesis

> **Fact（事实）**：Meta 报告 Llama 3.1 405B 有 405B 参数、使用 15.6T Training Tokens 和约 `3.8 × 10^25` FLOPs；训练规模最多 16,384 张 80 GB HBM3 H100。54-day Snapshot 有 466 次中断，其中 419 次意外；BF16 MFU 在披露配置中为 38–43%，Effective Training Time 超过 90%。

> **Interpretation（解释）**：训练能力是 Model、Runtime、Compute、Memory、Network、Server、Storage、Power / Cooling 与 Recovery 共同生产的系统服务；同步边界把局部故障转成全局进展损失。

> **Inference（推断）**：在某些 Llama 3.1 训练状态下，改善 Topology-aware Communication、Failure Recovery 或 Thermal Operation，可能比增加同等数量的名义 GPU 更能提高 Preserved Progress。论文提供一致证据，但没有公开所有边际实验。

> **Hypothesis（仍需验证的假设）**：下一代 Frontier Training 的主要约束会永久位于 HBM、Advanced Packaging 或 Power。这个判断需要订单、交期、Qualification、利用率、工作负载、网络和设施边际数据；今天的公开案例不能确认永久位置。

### Evidence Boundary（证据边界）

- 主要来源是 Meta 论文、Model Card 与工程文章，支持其自身系统陈述，但不是独立成本审计。
- 54 天是故障观察窗口，不是完整训练时长；30.84M H100 GPU-hours 也不能提供未披露的 Wall-clock 或采购价。
- `405B × 2 bytes`、2,048 台服务器、1.31 PB Aggregate HBM、11.47 MW GPU-only TDP 与每 3.1 小时一次 Job Interruption 是透明计算，不是 Meta 直接披露的完整系统指标。
- 11.47 MW 使用 Nameplate TDP；它既不是设施总负荷，也不是平均能耗。
- 论文的 Faulty GPU Count 与打印百分比存在不一致；本课不自行改写原表，只说明算术差异。
- 公开资料没有指出 Wafer、Foundry、Package、HBM 或哪家供应商在采购上构成 Meta 的第一个绑定约束。

# Industry Apprenticeship（行业学徒制）

## 9. 今天只回答一个行业问题：一笔 Frontier Training 预算究竟购买什么，谁为 Idle、Spare、Restart 与 Qualification Risk 付钱？

历史上，企业先购买 Server、Chip、Network 和 Data-center Asset，再由自己的工程团队把它们组合成计算服务。Cloud 与 AI Infrastructure Platform 把部分组合工作产品化，但 Frontier Lab 即使购买 Cloud Capacity，仍要定义 Model、Data、Runtime、Correctness 与训练目标。付款边界可以移动，完整系统责任不会消失。

今天的白话定义是：**Training Buyer 购买的不是一堆永远满速的 GPU，而是在指定时间内把数据可靠地转换为经过验证、能够继续使用的模型进展。** 硬件供应商、Cloud Provider、Data-center Operator、Network Vendor、Memory / Packaging / Foundry Partner 与 Model Lab 分别持有不同资产和风险。

| 参与者 | 主要交付 | 谁付款 | 谁直接受益 | 容易被忽略的风险 |
|---|---|---|---|---|
| Model Lab / Meta | 数据、模型、Runtime、目标与验收 | 企业资本与运营预算 | 产品、研究和下游应用 | 数据质量、模型失败、软件错误、需求价值 |
| Accelerator / System Platform | 合格 GPU、Interconnect、Server 与 Software Support | Lab、Cloud 或 OEM | 能运行特定 Workload 的客户 | 供应承诺、保修、产品转换、资格化 |
| Network / Storage / Data Center | 可到达、可恢复、供电冷却的 Cluster | Lab 或 Cloud | 训练团队与最终业务 | 闲置、Spare、故障域、扩建延迟 |
| Cloud Provider | 计量容量、调度、运维与合同边界 | Training Customer | 更快获取容量与服务 | 利用率、折旧、库存、SLA、资产过时 |
| HBM / Packaging / Foundry / Wafer | 通过资格化的上游部件和制造能力 | Chip / System Supplier | 整条下游链 | Yield、Cycle Time、Capacity Commitment、需求反转 |

**Idle Capacity（闲置容量）**不是自动浪费。为了让大规模 Job 同时获得完整拓扑、快速替换故障节点并承受需求波动，系统可能有意保留余量。谁支付它取决于资产和合同：自建时由 Lab 通过折旧和利用率承担；Cloud 模式下 Provider 先承担 Pooling Risk，再通过价格、承诺和超额销售管理；Dedicated Capacity 合同又可能把风险退回客户。

**Spare Capacity（备用容量）**解决故障后的快速替换。受益者是需要训练连续性的 Job，付款者可能是自建客户、Cloud Provider 或设备供应商的 Warranty / Support 体系。常见误解是把 Spare 当成重复采购；实际上它是降低恢复时间的 Reliability Input，但保留多少应与失败概率和中断价值比较。

**Restart / Checkpoint Risk（重启与检查点风险）**来自两次持久化之间的进展可能丢失。Checkpoint 太少，故障后重做多；太频繁，Storage 和同步开销增加。付款不仅是 Storage Cost，还包括全组等待、重新调度和工程时间。

**Qualification Risk（资格化风险）**指新 GPU、HBM、Package、Server、Firmware 或 Network Configuration 即使名义规格正确，也可能尚未通过客户 Workload、Thermal、Reliability 和 Software 验证。付款方常通过预付款、长期采购、工程投入或延迟承担；受益方是获得稳定交付的下游。常见误解是把出厂合格等同于整个训练系统合格。

Meta Model Card 的 30.84M H100 GPU-hours 不能乘一个公开 On-demand Price 就宣称“Llama 3.1 405B 成本”。Meta 可能拥有硬件、签订不同合同、使用内部转移价格，并同时支付网络、服务器、设施、电力、折旧、人员、失败重做和上游承诺。公开资料没有同口径总账单，也没有供应商逐美元分配。

## 10. Transfer（迁移）：遇到陌生 AI Workload，怎样在五分钟内找第一个候选约束？

第一，写下可验收的 Useful Output。Training 是被保留的合格模型进展；Inference 可能是满足正确性、延迟和成本边界的有效响应。没有这个分子，所有“利用率”都可能优化错对象。

第二，固定 Workload State：Model Size、Context、Batch、Precision、Parallelism、Reliability Boundary 与时间尺度。否则 8K 与 128K、训练与推理、正常与故障恢复会被错误混在一起。

第三，从输出向后追：Model / Runtime → Compute → HBM → Local Interconnect → Server → Cluster Network → Storage / Checkpoint → Power / Cooling → Package / HBM Supply → Fabrication → Wafer。每层写“必须交付什么合格对象”，而不是只写公司名。

第四，做边际测试。若给候选层增加一单位有效能力，Preserved Progress 是否提高？若不提高，继续寻找；若提高，记录提高范围和新瓶颈。不要把最贵、最热、最忙或故障最多自动当答案。

## 12. 现在我们可以重新回答开头的问题

16,384 张 H100 不能直接写成 16,384 份训练能力，因为训练的最小可验收单位不是一张卡的局部工作，而是整个参与组完成、验证并保存的模型更新。Model State 必须放得下，Runtime 必须正确切分，GPU 必须执行，Collective 必须同步，Network 与 Server 必须避免长尾等待，Power / Cooling 必须维持运行，Checkpoint 与 Spare 必须把故障后的重做压到可接受范围。任一绑定层都能让其他层的名义容量无法变成 Preserved Progress。

Meta 案例没有给出一个永久瓶颈；它给出了一种诊断方法。8K、128K、故障恢复、午后热状态和下一代扩建会暴露不同约束。正确做法是先固定 Workload 与有用输出，再从结果反推全栈，并寻找“缓解这一层会不会让合格进展增加”的证据。
