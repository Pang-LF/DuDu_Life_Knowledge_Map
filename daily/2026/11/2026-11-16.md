昨天，我们证明一柜服务器只有在电力、排热、机架密度和冗余状态同时对齐后，才成为可持续的物理容量。今天继续跟随同一批机器：物理能力已经存在，云平台怎样把它变成客户可以点击购买的 Instance，又为什么“总资源还有很多”仍不保证下一台 Instance 能启动？

这是从 Data Center Physical Infrastructure 进入 Cloud Resource Management 的第一课。**Cloud（云）**不是远方的一台神秘电脑，而是把共享的服务器、存储和网络资源，通过抽象、自动配置、计量和调度，变成按需服务的系统。今天先建立 Instance、Quota、Reservation、Placement、Overcommit 与 Utilization 的母关系；下一课才能讨论 Region、Availability Zone、Replica 与 Failure Domain 怎样把已放置资源变成可靠服务。

> **今天如果只记住一件事，就是：云容量不是所有服务器剩余 CPU、内存和 GPU 的加总，而是一组可行放置；只有当一份完整请求的全部资源与位置、拓扑、故障域、策略和承诺能在同一时刻落进同一个合格位置，它才成为可出售、可运行的容量。**

## 1. Opening Puzzle（开场谜题）

一座云区域的运营报表显示：CPU 还有 40%，内存还有 35%，GPU 也有一块空闲；昨天学过的供电与冷却路径都正常。客户现在请求一台 `16 vCPU + 128 GiB RAM + 1 GPU` 的 Instance，控制台却返回 Insufficient Capacity。

如果把云容量理解为总数，这个结果不合理。但把视角缩到三台 Host（物理宿主机），情况可能是：

| Host | 空闲 vCPU | 空闲内存 | 空闲 GPU | 当前状态 |
|---|---:|---:|---:|---|
| A | 16 | 64 GiB | 1 | GPU 在这里，但内存不够 |
| B | 8 | 256 GiB | 0 | 内存很多，但 CPU 与 GPU 不够 |
| C | 24 | 128 GiB | 0 | CPU、内存够，但没有 GPU |

池中合计有 48 vCPU、448 GiB RAM 和 1 GPU，全部大于请求；但没有一台 Host 同时满足三项。客户买的不是三个总数，而是一份必须共同落地的资源组合。今天跟随这一份请求，从 API 进入 Quota 检查、Scheduler、Hypervisor，最后到达一台真实 Host。

## 2. 先定义母概念：Cloud 把什么变成了什么？

NIST SP 800-145 把 Cloud Computing 定义为：通过网络按需访问一组共享、可配置的计算资源，并能以很少的管理工作快速配置和释放。它列出五个关键特征：On-demand Self-service、Broad Network Access、Resource Pooling、Rapid Elasticity 与 Measured Service。

这一定义包含两层：

- **Physical Layer（物理层）**：真实服务器、存储、网络、电力和冷却；
- **Abstraction Layer（抽象层）**：把物理能力表示为 VM、Container、Volume、Virtual Network、Instance Type、Policy 与 API 的软件层。

抽象不是把物理约束删除，而是把“客户必须知道哪一台服务器”改成“客户声明需要什么能力，由平台寻找满足条件的位置”。因此云资源管理的核心问题可以写成：

```text
Sellable capacity for request r
= the number of feasible placements of r
under current resources, topology, policy, reservation and failure constraints
```

同一资源池对不同请求会有不同容量。它可能还能放 100 台小型 CPU Instance，却放不下一台大型 GPU Instance；也可能在 Region 总体有资源，但客户指定的 Availability Zone、Instance Type 或 Placement Group 没有可行位置。

## 3. Follow One Request（跟随一份请求）：从点击 Launch 到真正运行

客户提交的不只是“给我算力”。一份简化请求至少可能包含：

```text
Image / OS
+ Instance Type: vCPU, memory, accelerator
+ Network and storage requirements
+ Region / Availability Zone
+ tenancy, security and placement policy
+ reservation target and account identity
```

### 第一道门：Admission 与 Quota

**Quota（配额）**是控制面允许某账户在某区域、某资源类别中申请或运行的上限。它解决多租户系统中的治理问题：防止误操作或单一租户无限占用资源，并为容量计划提供边界。

AWS 的 EC2 文档举例，账户在每个 Region 有可运行 On-Demand vCPU 上限；如果新请求会超过上限，请求失败，可以释放资源或申请提高 Quota。这里最容易犯的错误是：

```text
Quota headroom ≠ physically available host capacity
```

Quota 允许你提出请求，不代表平台已经为你保留硬件。反过来，物理池有空闲资源，也不能绕过账户 Quota、权限、镜像、网络或存储限制。

### 第二道门：Filter（筛选合格位置）

Scheduler 先从所有 Host 中排除不合格者。例如：

- CPU 架构、虚拟化能力或 GPU 型号不匹配；
- 内存、Local Storage、Network Interface 或端口不够；
- Host 位于错误 Zone、Rack 或 Failure Domain；
- License、Tenancy、Security、Affinity / Anti-affinity 不允许；
- 已有 Reservation、维护状态或可靠性 Headroom 不能被占用。

筛选以后得到的是 Feasible Set（可行集合）。若集合为空，区域总利用率再低也不能放置。

### 第三道门：Score 与 Place（评分与落点）

若多个 Host 都可行，平台还要决定放在哪里。紧密 Packing 可以填满部分机器，让其他机器保持完整，方便未来大请求和节能；Spread 可以留下每台机器的突发 Headroom，降低局部故障集中，却可能把空闲资源切成难以组合的小碎片。

放置不是一次性计算。Host 故障、维护、负载突发、工作结束和新机器加入都会改变可行集合。平台要持续监控、重启、迁移或重新放置能被移动的工作；不能安全迁移的本地状态、加速器或低延迟工作则缩小选择。

## 4. Virtualization（虚拟化）：它创造的是接口与隔离，不是物理资源

**Virtual Machine（虚拟机）**给 Guest OS 呈现一组虚拟 CPU、内存布局与设备，使多个 Guest 可以在同一物理 Host 上隔离运行。Linux KVM 的正式 API 很具体：创建一个 VM 后，它最初没有 vCPU 和内存；管理程序再创建 vCPU、设定 Memory Layout，并创建或连接 Virtual Device。

因此一台 Instance 的简化映射是：

```text
Guest vCPU → Host scheduling time on physical CPU threads
Guest memory → mapped / backed host physical memory
Virtual NIC → virtual switch / physical NIC path
Virtual block device → local or networked storage path
Virtual or passed-through accelerator → a compatible physical device
```

Virtualization 解决三个历史问题：

1. **Isolation**：不同客户拥有分离的 Guest、权限与地址空间；
2. **Multiplexing**：一台大 Host 可以承载多个较小工作负载；
3. **Standard Interface**：客户选择 Instance / Image，而不必配置每块裸硬件。

但它不能创造真实 CPU Cycle、DRAM Byte、NIC Bandwidth 或 GPU。若物理 CPU 同时被多个 vCPU 要求满载，必须排队；若所有 Guest 的活跃内存同时增长，Host 不能靠地址翻译制造更多 DRAM；需要独占或直通的 GPU 还会形成离散边界。

## 5. Placement（放置）：为什么总和足够仍会失败？

回到开场的三台 Host。请求 `16 vCPU + 128 GiB + 1 GPU`，可行条件是：

```text
CPU_i ≥ 16
AND RAM_i ≥ 128 GiB
AND GPU_i ≥ 1
AND every location / policy / topology constraint is true
for at least one host i
```

A 只有 GPU，B 只有大内存，C 只有 CPU 与足够内存。资源不能跨 Host 随意拼成一台普通 VM，所以可行 Host 数是零。

**Fragmentation（碎片化）**就是空闲资源存在，却因分散在不同 Host、不同资源维度或不同约束区域而不能满足当前请求。四台机器各剩 8 vCPU，合计 32 vCPU，也放不下一台要求单机 16 vCPU 的 VM。碎片不是资源消失了，而是对当前请求不可组合。

可采取的动作各自改变不同条件：

- 把 A 上的一个内存工作负载迁走，使 A 释放到 128 GiB；
- 客户改用较小内存或无 GPU 的 Instance Type；
- 允许另一 Zone，扩大候选 Host 集合；
- 新增 GPU Host，但必须同时带够内存、网络、电力和冷却；
- 更好地预留完整 Host，减少未来大请求被碎片阻断。

“增加总 CPU”可能完全无效，因为当前绑定条件是 GPU 与内存在同一 Host 上对齐。

## 6. Request、Reservation、Allocation 与 Utilization 不是同一个数

| 概念 | 它回答的问题 | 谁控制 / 观察 | 常见误解 |
|---|---|---|---|
| Request / Limit | 工作负载声明最多需要多少？ | 用户、编排器、Scheduler | 请求量就是实际用量 |
| Quota | 账户最多获准申请多少？ | 控制面 / 组织治理 | Quota 等于已留硬件 |
| Reservation | 哪份能力被提前承诺给谁、何时何地？ | Provider 与客户 / 内部团队 | 所有“Reserved”都是折扣 |
| Allocation / Placement | 哪些资源已经落到哪台 Host？ | Scheduler / Hypervisor | 已分配就正在充分使用 |
| Utilization | 实际用了多少 CPU 时间、内存、带宽或设备？ | Telemetry / Billing | 平均利用率能描述尾部拥塞 |

设一台 Host 有 64 个物理 CPU Thread。平台向 8 台 VM 各分配 16 vCPU，总分配为 128 vCPU，即表面上 2:1 Overcommit。若每台平均实际使用 4 vCPU，Host 平均需求是 32，相对 64 只有 50% 使用率；共享提高了平均利用率。

但若 8 台 VM 同时需要 16 vCPU，总需求是 128，超过 64 一倍。Scheduler 只能分时，客户会看到等待和延迟。这个透明模型不是任何云产品的承诺；它只说明 Overcommit 的收益来自负载峰值不完全重合，风险则出现在相关突发和错误估计。

内存更难随意超卖。假设 512 GiB Host 为系统和故障处理保留 64 GiB，只剩 448 GiB Allocatable。四台各承诺 112 GiB 后，即使此刻实际只用 300 GiB，一份 128 GiB 请求也可能被拒绝：平台若按承诺边界放置，不能假设所有工作永远少用。Ballooning、Swap、Compression 或可回收 Cache 可以改变策略，却会引入延迟、抖动或 OOM 风险。

## 7. Failure Domain（故障域）：为什么“分散”会减少可放置容量？

**Failure Domain（故障域）**是可能被同一故障同时影响的一组资源，例如一台 Host、一个 Rack、一条电源路径或一个 Availability Zone。把三个 Replica 分到不同 Rack，可以降低单柜故障同时杀死全部副本的概率；但 Anti-affinity 也要求 Scheduler 找到三个不同位置，每个位置都满足资源条件。

因此 Placement 有一个真实交换：

- 紧密放置提高局部资源利用率、减少通信距离，却集中相关故障；
- 分散放置提高故障隔离，却消耗更多完整位置、网络路径和 Headroom；
- 大型 Gang-scheduled Job 可能要求许多节点同时可用，任何一个位置缺失都会让全组等待。

今天只把 Failure Domain 当作 Placement Constraint，不正式教授 Cloud Reliability。下一课会再从 Replica 和服务结果出发，区分 Region、Zone、Host 与 Shared Responsibility。

## 8. Deep Case — Google Borg：为什么统一共享比“每个团队一组机器”更省？

### Before：一台服务器属于一个应用，最容易理解

早期集群管理的自然做法，是让服务团队拥有固定机器：Gmail 的服务放一组，Batch Job 放另一组。这样责任清楚，性能看起来也更可控。但面向用户的服务必须为流量尖峰和部分故障留出 Headroom；批处理又会随任务开始和结束大幅波动。各自保留的余量很少同时被用到。

Google 在 2015 年 Borg 论文中描述的规模已经是：数十万个 Job、数千种应用、多个 Cluster，每个 Cluster 最多达到数万台 Machine。固定分割会让每个团队都为自己的峰值买机器，同时在其他时段闲置。

### Pressure Builds：服务要低延迟，批处理要吞吐，两者不能同样承诺

Borg 的 Workload 同时包含应当持续在线、处理微秒到数百毫秒请求的长期 Service，以及运行数秒到数天的 Batch Job。前者通常是较高 Production Priority，后者多为较低 Priority。

如果只按 Request 相加，面向用户的服务会占满机器，因为它们必须声明应对流量尖峰的资源；如果只按实际 Usage 填满，尖峰到来时又会争抢 CPU 和内存，伤害延迟与可靠性。问题不是“怎样达到 100% 使用率”，而是“怎样让可中断工作吸收安全余量，同时保护不可中断服务”。

### Turning Point：Job 声明需求，Borg 在 Cell 中统一放置

Borg 把一组由同一控制面管理的机器称为 Cell。用户提交 Job，每个 Job 含一个或多个运行同一程序的 Task；每个 Task 声明 Resource Limit 和 Constraint。Quota 先决定 Job 能否进入调度，Priority 决定资源冲突时谁更重要，Scheduler 再筛选与评分具体 Machine。

这一步改变了所有权：团队不再拥有某台机器，而是拥有一份可被控制面解释的资源权利和优先级。机器仍然有异质 CPU、Memory、Disk 和属性，抽象只让它们进入统一决策。

### Cascade：共享、细粒度请求与回收共同减少机器数

Google 对真实生产负载做高保真模拟。论文报告，在 Shared Borg Cell 中，98% 的 Machine 同时运行 Production 与 Non-production Task；在 Borg 管理的全部机器中，这一比例是 83%。若把 Production 与 Non-production 分开，中位 Cell 需要多 20–30% 的机器，原因是低优先级工作可以使用高优先级服务暂时不用的 Headroom。

这不是说共享没有代价。论文比较同类机器上 CPU Cycles per Instruction，观察到共享环境可能有干扰；作者明确说结果并不单一。但即使采用对共享最不利的结果，减少的机器仍超过 CPU Slowdown 的代价，而且共享同时改善 Memory 与 Disk 使用。

Borg 还允许 CPU 以 milli-core、Memory / Disk 以 Byte 提出细粒度请求。研究者把 Production Job 的 CPU 与内存需求向上取整到 0.5 Core、1 GiB 起步的 2 的幂固定桶，模拟结果显示中位情况下需多 30–50% 资源。为什么这个数字重要？因为 Instance Type 让产品、价格与操作更标准，却可能把客户需要的 3 Core / 5 GiB 向上装入更大盒子；盒子内部剩余资源如果不能重新组合，就变成规格碎片。

### Decision：Priority、Quota、Reservation 与 Usage 分层，而不是混成一个数字

Borg 用 Priority 表达相对重要性；高优先级 Task 可以抢占较低优先级 Task，但 Production Task 之间不互相抢占，以限制 Preemption Cascade。Quota 是按 CPU、RAM、Disk 等资源组成的向量，在 Admission Control 阶段检查，不是 Scheduler 的落点。

Production Quota 被限制在 Cell 的实际资源范围，使符合 Quota 的 Production Job 通常可运行，但论文保留 Fragmentation 与 Constraint 例外；低优先级 Quota 可以超卖，因此 Job 即使获准进入，也可能 Pending。Borg 还估计真实资源需求并回收未用余量给较低优先级工作。这是“承诺给关键服务、机会性借给可中断工作”，不是假装同一资源同时无条件属于两者。

### Outcome：高利用率来自风险分层，不来自删除余量

Borg 的结果不是把每台机器永久塞满，而是把不同时间形状、优先级和可中断性的工作放在同一资源池，用隔离和控制保护关键服务。大 Cell 还降低 Fragmentation，因为更多 Host 提供更多组合机会；固定小池会让每个池都留下不能互借的尾料。

但是论文中的机器节省是对 Google 当时 15 个大型代表性 Cell、真实约束和模拟方法的结果。它不是任意 Cloud Provider、GPU Cluster 或客户 VM 的通用节省比例；共享干扰、网络、存储、软件许可和故障域都可能改变收益。

### Aftermath：Kubernetes 继承了声明式思想，但 Cloud VM 仍有不同边界

Borg 的 Job Spec、Task、Label、Constraint、Resource Request、Priority 与控制循环影响了后来容器编排系统。可是 Borg 主要管理 Google 内部 Container Workload；公共 IaaS 还要处理客户 Guest OS、硬件隔离、产品化 Instance Type、计费、合规、Tenancy 与公开 Capacity Promise。

案例真正留下的不是“所有系统都应照抄 Borg”，而是：Pool 的经济价值取决于能否让异质需求共享而不破坏重要承诺；Scheduler 的产品不是最高平均利用率，而是在约束下把请求转成可靠运行结果。

## 9. Comparison（比较）：四种“有容量”其实是四道不同的门

| 状态 | 判断问题 | 失败时看到什么 | 典型修复 |
|---|---|---|---|
| Authorized | 账户权限与 Quota 是否允许？ | Limit / Permission Error | 调整权限、释放或提高 Quota |
| Physically Available | 合格 Host 是否拥有对应资源？ | Insufficient Capacity | 等待、换类型、扩池、换 Zone |
| Placeable | CPU、RAM、GPU、网络、存储、拓扑和策略能否同址？ | Pending / No Feasible Host | 迁移、整理碎片、放宽 Constraint |
| Reserved / Assured | 指定能力是否提前为该客户保留？ | 高峰时无法保证启动 | Capacity Reservation / Commitment |
| Actually Used | 已放置资源做了多少有用工作？ | Idle / Low Utilization / Tail Contention | Rightsizing、回收、弹性、调度优化 |

VM 与 Container 也不能简单说谁“更轻”。VM 通常给 Guest OS 更完整的机器抽象和隔离边界；Container 共享 Host Kernel，以进程与 Namespace / Cgroup 等机制隔离，启动和密度常更灵活。实际安全、性能和运维结果取决于实现、工作负载和威胁模型。今天正式掌握的是资源抽象与可行放置，不把 Container Architecture 点成第二主课。

## 10. Industry Apprenticeship：云厂商卖的是服务器、Instance，还是 Capacity Promise？

今天只回答一个行业问题：**客户购买一台 Instance 时，谁承担服务器空置、资源碎片和高峰时无法放置的风险；Capacity Reservation 又怎样改变风险归属？**

先把经典术语说白：

- **Instance**：一台可通过 API 创建和删除的虚拟服务器。AWS 说明 Instance Type 给出 CPU、Memory、Storage 与 Network 的组合；部分 Host 资源专用于某 Instance，Network 和 Disk Subsystem 等资源可能共享。
- **On-Demand**：客户按实际运行时间付费，不做长期承诺；Provider 负责建设 Pool，但普通 On-Demand 请求并不保证指定类型在指定 Zone 的每一刻都有容量。
- **Capacity Reservation**：Provider 在指定 Availability Zone 按匹配属性为客户保留计算位置。AWS 的正式账单示例是预留 20 台、实际运行 15 台，客户仍为另外 5 台 Unused Reservation 按等同 On-Demand 费率付款。
- **Savings Plan / Reserved Instance**：主要是定价或消费承诺工具，不能一概当成物理 Capacity Reservation；具体产品和区域条款不同，必须看合同对象。

历史上 Public Cloud 用大池、多租户和按需计费，把单个客户“先买服务器再等交付”的资本风险转给 Provider。Provider 购买土地、机房、服务器、网络、软件和运维，承担需求预测、代际更新、闲置、碎片和故障风险；客户用更高的单位灵活性价格换取快速启动和按量缩放。

Capacity Reservation 把部分风险转回来。客户为了“在这个 Zone、这个 Instance Type、这个时间一定有位置”，即使不用也付费；Provider 获得更确定的收入与需求信号，并必须保护对应能力不被普通请求占用。Reservation 因而可能让全池报表看见空闲硬件，却不能把它卖给别人——那不是意外碎片，而是已收费的承诺。

AWS 的 Launch Troubleshooting 还明确区分两种失败：`InstanceLimitExceeded` 是账户达到 Region Quota；`InsufficientInstanceCapacity` 是 AWS 当前没有足够 On-Demand Capacity。后者的建议包括稍后重试、减少一次请求数量、不指定 Zone 或换 Instance Type。这个区别是行业分析的最低要求：治理上限、物理短缺、规格碎片和客户保留不能混成一个“Capacity 不足”。

钱流可以沿三层追踪：

1. Provider 向土地、电力、数据中心、服务器、芯片、网络和软件供应商支付资本与运营成本；
2. Customer 按 Instance 时间、存储、网络、Managed Service、Commitment 或 Reservation 付款；
3. Scheduler 决定同一物理资产能否承载更多可计费服务，同时不破坏性能、隔离、可靠性和承诺。

因此真正的行业指标不只是 Fleet CPU Utilization。还要看 Placement Success、Pending Time、Fragmentation by resource / Zone、Reserved-versus-used capacity、Tail Latency、Preemption / Eviction、Failure-domain balance、Revenue per commissioned capacity，以及 Cost per Useful Output。把利用率推到 100% 可能提高短期收入，也可能消灭突发和故障 Headroom。

议价权来自哪里？Provider 控制资源池、Scheduler、API、Billing、Region / Zone 和客户关系；Chip / System Vendor 控制稀缺硬件与软件生态；大型客户可以用承诺规模交换价格和容量确定性。公开文档不能告诉我们具体内部 Overcommit Ratio、Instance 毛利、客户折扣、Capacity Allocation 或 SLA Remedy，不能从一个公开价格反推全部经济性。

## 11. Fact、Interpretation、Inference 与 Hypothesis

> **Fact（事实）**：NIST 把 Resource Pooling、Rapid Elasticity 与 Measured Service 列为 Cloud 的关键特征。Google Borg 论文报告 Production 与 Non-production 分池会让中位 Cell 多需 20–30% 机器，把细粒度请求向固定的 2 的幂资源桶取整会让中位资源需求增加 30–50%。AWS 文档区分 Region Quota Error 与当下 On-Demand Capacity 不足，并规定未使用的 Capacity Reservation 仍按等同 On-Demand 费率计费。

> **Interpretation（解释）**：这些事实共同说明 Pooling 与 Scheduler 的价值来自把不同形状、时间和优先级的需求组合起来；抽象降低客户操作复杂度，却没有消除 Host、资源维度、位置和承诺边界。

> **Inference（推断）**：当 Fleet 总利用率不高却出现启动失败，候选原因包括资源碎片、严格 Instance Type、Zone / Topology Constraint、Reservation、维护与可靠性 Headroom，而不应先断言 Provider 缺少总服务器。区分它们需要位置与资源维度的 Placement 数据。

> **Hypothesis（仍需验证的假设）**：某个指定云区域当前主要受 GPU 数量、GPU–Memory 共址、网络拓扑、Quota、Capacity Reservation、Anti-affinity、Power / Cooling 或软件调度限制。验证需要 Scheduler Filter Reason、Host Inventory、Request Shape、Reservation Map、Failure-domain Map、Queue / Pending Time 与实际 Usage Trace。

### Evidence Boundary（证据边界）

Borg 证据来自 Google 内部 2014 年检查点和 2015 年论文中的 15 个大型代表性 Cell 模拟，不是公共 IaaS 的直接测量。Borg 主要管理 Container Task，而今天同时用 KVM 和 EC2 解释 VM；两者共享资源放置逻辑，但隔离、产品、计费和迁移边界不同。三 Host、64 Core、512 GiB 与 2:1 Overcommit 都是透明教学模型。AWS 文档说明公开产品语义，不披露 Host Inventory、内部 Scheduler、Overcommit、折扣、成本或利润。

## 12. Transfer（迁移）：以后看到“云资源还有 40% 空闲”，先问什么？

先固定请求形状：多少 vCPU、Memory、GPU、Local Storage、Network、Image、Tenancy、Zone、Topology 和持续时间？“一个 Instance”不是同质单位。

再分四道门：账户是否 Authorized；物理资源是否 Available；完整请求是否 Placeable；对应能力是否 Reserved。错误代码、Pending 原因与 Scheduler Filter 比平均利用率更接近机制。

然后比较 Request、Allocation 与 Usage。Request 是承诺边界，Allocation 是已经落点，Usage 是实际消耗；低 Usage 可以是需要突发 Headroom，也可以是 Rightsizing 机会。只有低优先级、可抢占工作能够安全吸收的余量，才适合积极回收。

最后才讨论经济：Provider 承担多少 Idle / Fragmentation Risk，Customer 是否通过 Reservation 或 Commitment 付费接手，增加 Packing 会不会恶化 Tail Latency、Failure Isolation 与未来大请求的可行性。

## 14. 现在我们可以重新回答开头的问题

CPU 还有 40%、内存还有 35%、GPU 还有一块，描述的是不同资源在 Pool 中的总量或平均状态。客户请求的却是一份不可随意拆开的组合：16 vCPU、128 GiB、1 GPU，以及 Zone、网络、存储、Tenancy、Reservation 与 Failure-domain 条件。若 GPU 在只有 64 GiB 空闲内存的 Host A，足够内存在没有 GPU 的 B，CPU 与内存在没有 GPU 的 C，那么可行集合为空；Scheduler 拒绝请求是正确行为。
