# Mastery Core（掌握核心）

## 1. Opening Puzzle（开场谜题）：计算单元已经准备好了，为什么还在等？

想象 GPU 需要读取一个 64-byte Cache Line（64 字节缓存行）。64 字节等于 512 bit。

若一次只能并行传 32 bit，单看宽度就需要 16 份传输才能搬完 512 bit；若接口宽度是 1024 bit，它的物理宽度已经足以同时覆盖这份 512-bit 载荷。真实存储还受到 Burst、命令、地址、Bank、协议和调度约束，这个小故事不是实际延迟模型，只是在隔离一个直觉：**一条路可以靠车辆跑得更快增加流量，也可以靠增加大量并行车道增加流量。**

那么，为什么不直接在显卡主板上铺 1024 条甚至 4096 条高速线？因为每一条长距离高速信号都需要封装引脚、主板走线、间距、电气驱动和功耗；线越多，布线越困难，线越快，Signal Integrity（信号完整性）越难控制。HBM 的设计选择是把内存移近，让“极宽”在封装内部成为可能。

## 2. 先定义母概念 Memory System（存储系统）

Memory System（存储系统）负责在计算需要之前保存数据，并在需要时把数据送到指定位置。今天必须分开三个经常混淆的量：

- **Capacity（容量）**：能保存多少 Byte，例如 80 GB。
- **Bandwidth（带宽）**：单位时间最多能搬多少数据，例如 3.35 TB/s。
- **Latency（延迟）**：从提出一次访问请求到数据可用要等待多久。

一条高速公路可以每小时通过很多车，却不保证某一辆车到目的地的时间最短。类似地，高带宽不等于低延迟；大容量也不等于数据能被快速搬出。

HBM 是 DRAM（Dynamic Random-access Memory，动态随机存取存储器）的一种封装与接口体系。DRAM Cell 保存 bit，Bank 与 Channel 让不同区域可以被组织和并行访问。HBM 没有改变“用 DRAM 保存数据”这个母概念，而是改变许多 DRAM Die 怎样堆叠、连接并靠近处理器。

## 3. Follow One 64-byte Block（跟随一个 64 字节数据块）

一段模型权重或图像数据先存在某颗 HBM DRAM Die 的 Cell Array 中。Memory Controller 发出命令，目标 Bank 激活相应 Row，再选出 Column。Sense Amplifier（感应放大器）读取微弱电荷状态，I/O 电路把 bit 送向 Die 边缘。

如果目标数据位于上层 DRAM Die，信号需要沿 TSV（Through-Silicon Via，硅通孔）垂直穿过硅片。TSV 是贯穿硅片的微小导电通道；它不是 Memory Cell，也不会自己增加容量。Die 之间还需要 Micro-bump（微凸点）或其他键合结构完成垂直电气和机械连接。

多个经过减薄的 DRAM Die 由此形成一个 Stack（堆栈），底层 Logic / Base Die 或接口电路负责组织外部连接。HBM Stack 与 GPU 或 Accelerator 并排放在 Silicon Interposer（硅中介层）或其他高密度封装布线平台上。中介层上的数千条短走线把 HBM 的宽接口接到 Memory Controller；数据最后进入 GPU Cache、Register 或计算单元。

“堆叠”主要解决垂直容量与连接密度，“靠近”使超宽、短距离接口可制造，“并行通道”使很多 bit 同时移动。三者共同构成 HBM；只说“内存叠起来所以更快”仍然缺少机制。

## 4. 带宽是怎样算出来的？

第一阶峰值带宽可以写成：

`Peak Bandwidth = Data I/O 数 × 每个 I/O 每秒传输次数 ÷ 8`

除以 8，是把 bit/s 转成 Byte/s。做一个透明的等带宽比较：

- 较窄高速接口：`256 bit × 8 Gbit/s ÷ 8 = 256 GB/s`
- 超宽低速接口：`1024 bit × 2 Gbit/s ÷ 8 = 256 GB/s`

两者峰值带宽相同，但实现路径不同。前者让每根线更快；后者使用四倍宽度、四分之一的单线速率。HBM 通过封装内的短连接，让第二种路径更可行，并可能减少为高速远距离信号付出的 I/O 功耗。

SK hynix 对 HBM2E 的公开例子给出了同一算法：1024 个 Data I/O、每个 3.6 Gbit/s，得到 `1024 × 3.6 ÷ 8 = 460.8 GB/s`。这是每个 Stack 的理论接口带宽，不是任何程序都能持续获得的有效带宽。

## 5. Peak Bandwidth 为什么不等于程序得到的带宽？

GPU 只有在请求足够并行、地址访问适合合并、Bank 冲突受控、Cache 重用合理、控制器调度有效时，才能靠近峰值。若程序重复读取同一小块数据，Cache 可能比 HBM 更重要；若访问随机且串行，再宽的接口也可能利用不足；若模型容量超过 HBM，数据还要跨更慢的互连或主机内存移动。

因此，真实分析至少要分开：

- **Peak Bandwidth（峰值带宽）**：接口规格允许的上限。
- **Sustained / Effective Bandwidth（持续 / 有效带宽）**：特定程序实际搬运的数据率。
- **Arithmetic Intensity（算术强度）**：每搬一个 Byte，程序能完成多少计算。
- **Capacity Fit（容量适配）**：工作集是否能放进本地 HBM。

HBM 缓解的是外部存储带宽压力，不会自动修复所有缓存、软件、互连或计算利用率问题。

## 6. Deep Case：AMD + SK hynix Fiji / Radeon R9 Fury X，2009–2015

### Before：GDDR5 为什么曾经足够好？

GPU 长期把多颗 GDDR Memory Package 放在 GPU 周围的主板上。GDDR 依靠较高的每引脚传输速率和数百 bit 的总线提供带宽，制造、测试和显卡板级生态已经成熟。内存容量也可以通过改变芯片数量和密度配置。

这种结构的问题不是它“很慢”，而是继续增加带宽需要更高信号速率、更多引脚和更多主板走线。每一次提升都增加 I/O 功耗、板面积、信号完整性和布线约束。

### Pressure Builds：计算增长开始追上供数能力

GPU 增加并行计算单元后，更多单元会同时请求纹理、图像和中间结果。若外部内存不能持续供数，新增计算单元的边际价值下降。

但把 GDDR 总线继续加宽并不免费：GPU Package 需要更多 I/O，PCB 需要容纳更多高速线，显存芯片占据更多面积。提高单线速率又会提高信号和功耗难度。问题已经从“DRAM Cell 是否够多”变成“如何在有限功耗与面积内把数据搬过边界”。

### Turning Point：把内存从主板移进封装系统

SK hynix 公开历史记录显示，公司 2009 年开始 HBM 开发，并与 AMD 合作推进产品。2015 年，AMD 发布 Radeon R9 Fury 系列，称其为首个采用 HBM 的 GPU 产品家族。

Fiji GPU 与四组 HBM Stack 并排放在 Silicon Interposer 上。每组 HBM 通过垂直 TSV 连接多层 DRAM，并通过中介层上的大量短连接接入 GPU。AMD Fury X 的公开规格是 4 GB HBM、4096-bit 接口和最高 512 GB/s 带宽。

### Cascade：一条更宽的路要求整个制造系统改变

为了获得 4096-bit 总接口，供应链不只需要多做几颗普通 DRAM：DRAM Die 要减薄、形成 TSV、精确键合并完成 Stack Test；大型 Interposer 要连接 GPU 和四组 HBM；Package 必须控制翘曲、热和供电；最终还要验证 GPU、全部 Stack 与数千条连接共同工作。

容量也出现交换。Fury X 的 4 GB HBM 相比一些可配置更多 GDDR 容量的方案并不宽裕。HBM1 的创新首先解决带宽、面积和功耗边界，并没有同时最大化所有 Memory System 指标。

### Decision：接受新封装风险，换取带宽与面积效率

AMD 和 SK hynix 接受尚不成熟的 HBM 与 2.5D 封装路径，换取超宽接口。AMD 的发布资料把上一代 Radeon R9 290X 的 512-bit GDDR5、320 GB/s 与 Fury HBM 的 512 GB/s 对比：带宽增加 60%。AMD 同时声称 HBM 相比 GDDR5 减少 94% PCB 内存占用面积，并提供超过三倍的每瓦带宽表现。

这些百分比来自 AMD 自己的产品比较和测试口径，应视为 Company Claim（公司主张），不是独立实验；它们能说明公司当时的设计理由，不能单独证明整张显卡性能或总能效的因果提升全部来自 HBM。

### Outcome：HBM 是否越过了实验室？

Radeon R9 Fury X 于 2015 年 6 月上市，说明 TSV、Stack、Interposer 与 GPU 已经形成可销售产品。4096-bit 与 512 GB/s 不是概念图，而是进入公开产品规格的系统接口。

但 4 GB 容量、复杂封装和早期生态也说明：技术上可售不等于已经成为所有 GPU 的经济最优解。SK hynix 后来的回顾明确写到，早期 HBM 市场尚未准备好，高性能计算生态仍不成熟。

### Aftermath：为什么 AI 时代让旧选择重新变得关键？

随着加速器用于更大规模并行计算和 AI，数据搬运压力继续上升。NVIDIA 官方规格显示，H100 SXM 配置为 80 GB HBM、3.35 TB/s；H200 为 141 GB、4.8 TB/s。

从 Fury X 的 512 GB/s 到 H200 的 4.8 TB/s，公开峰值带宽约为 9.4 倍；容量从 4 GB 到 141 GB，约为 35 倍。这个跨近十年的比较只显示 HBM 系统演进的数量级，不能当成同代产品性能或价格的公平比较。

HBM 从早期高端图形设计，变成 AI Accelerator 的核心配套；与此同时，堆叠高度、散热、测试、先进封装和合格产能也更直接地限制最终 Accelerator 数量。

## 7. 对照：DDR、GDDR 与 HBM 把工程成本放在哪里？

| 维度 | DDR DIMM | GDDR | HBM |
|---|---|---|---|
| 典型位置 | 主板插槽，离 CPU 较远 | GPU 周围的主板封装 | 与 Accelerator 同一先进封装内 |
| 增加带宽的主要路径 | 多 Channel、提高速率 | 较高单线速率与较宽板级总线 | 数千条短连接、多个独立 Channel 与 Stack |
| 容量与可替换性 | 通常较灵活、成本较低 | 板级配置较灵活 | 受 Stack 数、密度和封装边界约束 |
| 板级面积 | DIMM 占用系统空间 | 多颗显存围绕 GPU | 内存占用面积更紧凑 |
| 工程代价 | 主板走线、Channel 和访问距离 | 高频信号、引脚、PCB 面积与 I/O 功耗 | TSV、减薄、键合、Interposer、热、测试与组合良率 |
| 常见误解 | “容量大就一定快” | “每根线更快就永远更优” | “HBM 自动降低延迟并让所有程序更快” |

没有一种内存普遍最好。服务器需要大容量和可维护性，消费显卡需要成本与容量灵活性，AI 加速器可能愿意为极高带宽和能效支付复杂封装成本。正确选择由工作负载和完整系统约束决定。

## 8. Stack Yield 与 Thermal（堆栈良率与热）：为什么多一层不是只多一点容量？

一组 HBM Stack 必须让多颗 DRAM Die、TSV、Micro-bump、Base Die 和外部接口共同成功。简单第一阶模型可以写成：

`Good Stack ≈ Good DRAM Die × Die 数量 × Bond / TSV Yield × Stack Test Acceptance`

这不是把一个 Die 良率机械地乘很多次；实际生产会使用 KGD、冗余、修复、分档和相关缺陷模型。但方向很重要：堆叠越高，更多薄 Die 和垂直连接必须在有限高度与翘曲下共同满足规格。

散热也不是“HBM 比 GPU 凉，所以不用管”。上层 Die 的热必须穿过其他材料和连接路径离开，温度会改变 Leakage、Refresh、时序与可靠性；逻辑 Die、HBM、Interposer 和 Cooling Solution 必须共同设计。Samsung 在 12-high HBM3E 的公开材料中强调更小 Die 间距、热阻、翘曲与高层堆叠良率，说明容量增长本身会重新打开制造和热问题。

## 9. Industry Apprenticeship：为什么增加 DRAM Wafer Start，仍可能交不出更多 AI Accelerator？

今天只回答一个行业问题：**HBM 供应链究竟出售什么合格对象，哪一项匹配不足会卡住最终 Accelerator？**

Memory IDM（存储 IDM，例如 SK hynix、Samsung、Micron）不只交付普通 DRAM 晶圆。它要设计 HBM、制造 DRAM 与 Base Die、形成 TSV、减薄与堆叠、测试并完成客户资格化，最终交付特定容量、速度、功耗和 Stack 高度的合格 HBM。

Accelerator Designer（加速器设计公司）定义 Memory Controller、Stack 数、接口、容量、热设计与合格供应商，并为 HBM 和封装投入付款。Foundry / Advanced Packaging Provider（晶圆代工与先进封装服务商）制造 Logic Die，并把它与 HBM、Interposer、Substrate 组装。设备与材料商提供 TSV、键合、减薄、Underfill、量测与测试所需工具。Cloud / System Customer 最终为完整 Accelerator、Server 或计算服务付款，而不是购买一堆彼此不能组合的零件。

用一个透明的假设模型看匹配约束：

```text
可进入终测的 Package
≤ min(
    1,000 颗 Good Logic Die,
    5,500 组 Good HBM ÷ 每包 6 组 = 916 包,
    900 个 Interposer / Package / Test Slot
  )
= 900 包

若 Final Package Yield = 95%，最终约 855 包。
```

这些数字不是任何公司产品数据。它只说明：再增加 1,000 组 HBM，若封装槽位仍是 900，最终产出不变；先增加封装槽位，产出又会在 916 包附近遇到 HBM；继续补 HBM 后，Logic Die 可能成为下一瓶颈。瓶颈会随匹配库存移动。

因此议价权不只来自“谁有最多 DRAM Wafer”，而来自谁能在正确时间交付已经通过特定客户资格化、与逻辑和封装匹配的 Stack。更换 HBM 供应商需要 Memory Controller、Signal / Power Integrity、Thermal、Package、Firmware、Reliability 和系统验证，切换不是把一个通用零件换掉那么简单。

客户特定的 Stack Yield、Package Yield、价格、长期协议、分配优先级和报废责任通常保密。公开的“产能扩张”或“售罄”声明，需要继续追问产品代际、Stack 高度、合格客户、交付时间和封装配套，不能直接等同于全行业 Good Accelerator 数量。

## 10. Practitioner Metrics（从业者真正看的数字）

- **I/O Width 与 Per-pin Data Rate**：带宽来自多少并行 I/O、每根多快。
- **Bandwidth per Stack / Package**：单 Stack 与整颗 Accelerator 的理论上限。
- **Effective Bandwidth**：真实 Kernel 获得多少，而不是只看规格峰值。
- **Capacity per Stack / Package**：工作集能否留在本地，是否需要跨互连换入换出。
- **Bandwidth per Watt**：为搬动每 GB/s 数据消耗多少 I/O 与系统功率。
- **Good Stack Yield**：投入 Die 和键合后有多少 Stack 达到目标速度、容量与可靠性。
- **Qualified Output**：通过指定客户和产品资格化的可交付数量，而不是所有 HBM 总产量。
- **Package Yield 与 Cycle Time**：Logic、HBM、Interposer、Substrate、Assembly、Test 齐套后多少通过，多久完成。
- **Thermal Margin**：在目标功耗、环境和冷却条件下，离温度或可靠性限制还有多少余量。

## 11. Fact、Interpretation、Inference 与 Hypothesis

> **Fact（事实）**：AMD 2015 年公开 Fury X 使用 4 GB HBM、4096-bit 接口和最高 512 GB/s；AMD 与 SK hynix 的公开历史把它描述为首个商业 HBM GPU 路径。NVIDIA 官方规格给出 H100 SXM 80 GB / 3.35 TB/s 与 H200 141 GB / 4.8 TB/s。SK hynix 的 HBM2E 资料给出 1024 I/O × 3.6 Gbit/s = 460.8 GB/s。

> **Interpretation（解释）**：HBM 的带宽优势主要来自把内存移近计算，使用超宽、短距离和高度并行的接口，而不是单纯追求最高 per-pin speed；它用更复杂的 3D Memory 与 2.5D Package 换取带宽、功耗和面积效率。

> **Inference（推断）**：当 Accelerator 需要多组指定 HBM 时，合格 Stack 与先进封装必须按比例匹配，任何一个短板都会限制 Good Package；资格化数据和集成平台因切换慢而产生议价权。

> **Hypothesis（仍需验证的假设）**：某一家 Accelerator 的 HBM 采购价格、Stack Yield、Package Yield、分配优先级或性能提升主要由 HBM 单一因素决定。公开资料不足以识别这些客户级数字或严格因果贡献。

## 12. Transfer（迁移）：以后看到“HBM 供应增加”，先问什么？

先把名词拆成对象：增加的是 DRAM Wafer、TSV Capacity、Good Stack、某一代已资格化 HBM、CoWoS 类封装槽位，还是通过 Final Test 的 Accelerator？

再问匹配比例：每颗 Package 需要几组 HBM，容量和速度是什么，Logic、Interposer、Substrate、Bonding、Test 与 Cooling 是否同时可得？

最后问真实使用：峰值带宽是多少，应用有效带宽是多少，容量是否适配，性能受 Memory、Compute、Network 还是 Software 限制？只有这三层都回答，供应和性能主张才落到同一个系统边界。

2. 某 AI Accelerator 需要 8 组 HBM。公司宣布 HBM 产量增加 50%，但 Accelerator 出货只增加 10%。请构造至少四种机制，并说明你需要哪些 Good Stack、资格化、Package Slot、Logic Die、Final Yield、Thermal 或需求数据来区分它们。

# Knowledge Expansion（知识拓展，不自动点亮）

今天通过 Fiji / Fury X 接触了 GPU Memory Controller、DRAM Bank、Cache、Arithmetic Intensity 与 AI Accelerator，但没有把 GPU 微架构、Roofline Model 或训练系统单独设为 Mastery Core。它们只用于解释峰值带宽怎样变成或没有变成有效计算吞吐。

# Connection Preview（连接预览，不正式教授）

- **GPU Parallelism（GPU 并行计算）**：大量计算单元怎样把已到达的数据转成吞吐，又为何分支、占用率和同步会降低利用率。
- **Roofline Model（屋顶线模型）**：算术强度怎样决定程序受 Memory Bandwidth 还是 Compute Peak 限制。
- **Thermal & Power Delivery（散热与供电）**：Logic 与 HBM 如何争夺封装功耗和冷却余量。
- **AI Infrastructure（人工智能基础设施）**：单卡 HBM 容量和带宽怎样扩展成多卡网络、服务器和数据中心瓶颈。

# Closing the Loop（闭环）

**现在我们可以重新回答开头的问题**：计算单元准备好了却仍在等待，是因为计算吞吐需要数据持续穿过存储边界。HBM 把多层 DRAM 移到 Accelerator 旁边，通过 TSV 垂直连接 Stack，再用 Interposer 上的数千条短连接形成超宽接口；它没有删除 Memory Bottleneck，而是用更高带宽与更好的面积、功耗效率，交换了 Stack Yield、热、测试、封装、资格化和供应匹配的新约束。

今天在地图上正式点亮的是 `SYSTEM.SEMICONDUCTOR.HBM_TSV_MEMORY_BANDWIDTH`，行业应用候选是 `BUS.SEMICONDUCTOR.HBM_SUPPLY_ECONOMICS`。下一步通向 GPU Parallelism：今天解释了数据怎样抵达 Accelerator，下一课研究大量并行计算单元怎样消费这些数据，以及为什么理论算力不会自动成为实际吞吐。
