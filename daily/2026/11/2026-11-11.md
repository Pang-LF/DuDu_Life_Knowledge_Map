# Mastery Core（掌握核心）

## 1. Opening Puzzle（开场谜题）：32 个人为什么可能只做出 16 个人的工作？

想象一支 32 人的工队，每个人负责处理一张图片中的一个 Pixel（像素）。工头说：“如果亮度大于阈值，就增强对比度；否则就降低噪声。”

第一组 32 个像素全部高于阈值。工头只需发出“增强对比度”这一个共同指令，32 个人一起做，32 个位置都产生有用结果。

第二组恰好 16 个高、16 个低。若这支工队只能在同一时刻执行一个共同指令，它要先让 16 个人做“增强”，另外 16 个人等待；再让另一半做“降噪”，前一半等待。两条路径工作量相同的简化情形下，每一段只有 16 / 32 的位置在产生结果，平均 Lane Utilization（通道利用率）只有 50%。

这不是某一块 GPU 的精确周期模型，而是 Control Divergence（控制分歧）的最小直觉：**人没有消失，计算单元也没有坏；问题是工作没有以适合硬件共同执行的形状到达。**

## 2. 先定义母概念 Processor 与 Throughput（处理器与吞吐）

Processor（处理器）读取 Instruction（指令）和 Data（数据），执行运算并产生结果。评价处理器时要先分开两个问题：

- **Latency（延迟）**：一个任务从开始到完成要多久？
- **Throughput（吞吐）**：一段时间内能完成多少任务或运算？

CPU 通常用较复杂的控制、预测和缓存，让少量线程尽快完成复杂而多变的任务。GPU 则把更多晶体管和功耗预算放到大量并行算术通道，并依赖很多线程共同提供吞吐。它不是“更快的 CPU”，而是为另一种工作形状优化的处理器。

因此，GPU 适合的是 Data Parallelism（数据并行）：同一套操作可以应用到许多不同数据元素，例如许多像素、矩阵元素或神经网络激活。若任务高度串行、分支各异或每一步都依赖前一步结果，大量并行通道可能无事可做。

## 3. 从 Kernel 到 Warp：软件怎样被交给硬件？

在 CUDA 中，Kernel（核函数）是一段由 CPU 发起、让 GPU 对许多数据元素并行执行的函数。程序员把大量 Thread（线程）组织为 Block（线程块），再把许多 Block 组成 Grid（网格）。

GPU 硬件不会独立调度每一个线程。它把线程按 32 个一组组织为 Warp。一个 Streaming Multiprocessor（SM，流式多处理器）保存许多 Warp 的寄存器、程序位置和状态，并从已经准备好的 Warp 中选择下一条指令执行。

可以把层级理解为：

```text
一个问题
→ Grid：这次 Kernel 的全部工作
→ Block：可以共同使用局部资源并同步的一组线程
→ Warp：硬件共同发射指令的 32 个线程
→ Thread：处理一个或若干数据元素的逻辑执行实例
```

Thread 是程序员表达并行工作的单位；Warp 是硬件实际共同推进指令的基本小队。理解这个区别，才知道为什么同样有 1,024 个线程，两种程序的吞吐可能差很多。

## 4. 跟随一个像素：它怎样穿过 GPU？

一张图片的一个像素先从昨天学习的外部 Memory System 进入 GPU Cache 或 Register（寄存器）。Kernel 中的一条线程负责这个像素；同一 Warp 的另外 31 条线程负责相邻像素。

SM 的 Warp Scheduler（Warp 调度器）看到这组线程已经获得输入，便发射一条共同指令，例如乘法或加法。算术通道对 32 个不同像素执行同一操作。若下一条指令依赖尚未返回的内存数据，这个 Warp 暂时不能继续；调度器会寻找另一个已经准备好的 Warp。

这就是 Latency Hiding（隐藏等待）：GPU 通常不是让一次内存访问突然没有延迟，而是在一个 Warp 等待时切换到另一个 Warp 做有用工作。前提是 SM 中必须有足够多独立且已准备好的 Warp，同时寄存器、Shared Memory（共享内存）和 Block 数量不能先耗尽硬件资源。

## 5. Occupancy（占用率）：为什么“坐满”有帮助，却不等于跑得快？

Occupancy 通常指一个 SM 上实际驻留的 Active Warp 数量，相对于该硬件允许的最大值。更高 Occupancy 往往给调度器更多候选 Warp，在某些 Warp 等待 Memory、Dependency 或 Pipeline 时，仍可能找到可执行工作。

但 Occupancy 不是最终成绩：

- 一个 Kernel 使用太多 Register，每个 SM 能同时容纳的 Warp 会减少。
- 一个 Block 使用太多 Shared Memory，可驻留的 Block 会减少。
- 即使 Occupancy 很高，所有 Warp 也可能同时等待同一类 Memory Request。
- 降低 Register 使用来追求满 Occupancy，可能引发 Register Spill，把数据反而写回更慢的 Memory。
- 某些计算密集型 Kernel 在中等 Occupancy 已经填满计算流水线，继续增加不会更快。

所以 Occupancy 回答的是“调度器有多少在场的候选工作”，不是“这些工作是否有用、是否准备好、是否命中了真正瓶颈”。

## 6. Control Divergence（控制分歧）：为什么条件判断会让同一小队轮流等待？

NVIDIA 的 CUDA Programming Guide 说明，Warp 的 32 个线程在同一时刻执行共同指令。当条件分支让不同线程选择不同路径时，Warp 要执行每条被选择的路径，并暂时关闭不属于当前路径的线程。

回到开场的 16 / 16 例子。若 A、B 两条路径工作量相同：

```text
路径 A：32 个 Lane 中 16 个有效
路径 B：32 个 Lane 中另 16 个有效
两段都必须执行 → 平均有效 Lane = 16 / 32 = 50%
```

这只是解释机制的假设模型。真实代价取决于分支长度、编译器、Predication（谓词执行）、线程重新汇合和其他指令。但方向稳定：若同一 Warp 的线程经常做不同的事，硬件的共同执行宽度就难以转化为有用吞吐。

有意义的对照是：如果 Warp 0 的 32 个线程全部走 A，而 Warp 1 的 32 个线程全部走 B，两组仍然执行不同代码，却没有发生 Warp 内分歧。问题不是系统里存在分支，而是分支边界是否切进同一 Warp。

## 7. Memory Coalescing（存储合并）：同样读 128 字节，为什么可能搬运 1,024 字节？

昨天我们学习了 HBM 的 Peak Bandwidth。今天要看到，软件地址形状决定一条 Warp 能使用多少带宽。

CUDA Guide 的简化例子使用 32-byte Memory Transaction（存储事务）：32 个线程各读取一个相邻的 4-byte 值，一共需要 128 个有效字节。如果地址连续，这 128 字节可由四个 32-byte 事务覆盖：

`32 threads × 4 B = 128 useful B`

`4 transactions × 32 B = 128 transferred B`

有效利用率是 `128 / 128 = 100%`。

如果线程之间的地址跨度至少 32 字节，可能需要 32 个独立的 32-byte 事务：

`32 transactions × 32 B = 1,024 transferred B`

程序仍只使用 128 字节，有效利用率变成 `128 / 1,024 = 12.5%`。也就是说，接口可能忙着搬运八倍于程序实际使用的数据。

这些是当前 CUDA Guide 用来解释访问形状的事务例子，不应直接当作 GTX 580 或所有 GPU 的精确性能预测。它们揭示的机制是：**带宽规格属于硬件接口，有效带宽属于硬件与地址模式的共同结果。**

## 8. Synchronization 与 Communication（同步与通信）：并行为什么还要相互等待？

并行工作只有在彼此足够独立时才能同时推进。若 Block 内线程必须等到其他线程完成才能进入下一阶段，Barrier（屏障）会让先到者等待；若两个 GPU 需要交换中间结果，Communication（通信）会占用链路和时间；若 CPU 必须在每个小步骤后重新发起工作，Launch 与 Host–Device Coordination 也会成为开销。

这不是说同步“有害”。矩阵分块、归约和神经网络层之间常常必须同步。真正的问题是：一次同步换来了多少后续有用计算？如果每搬一个小结果就等待一次，通信会淹没并行收益；如果一次通信后能完成大量独立运算，成本就能被摊薄。

## 9. Deep Case：AlexNet 如何把两张 GTX 580 变成可训练系统？

### Before：卷积神经网络已经存在，为什么没有立刻统治图像识别？

2012 年以前，Computer Vision（计算机视觉）大量依赖人工设计的特征，再把特征交给分类器。卷积神经网络并非新发明，但高分辨率图片、巨大训练集和高容量模型需要的计算与内存，使训练时间成为实际边界。

ImageNet 把问题规模推高：AlexNet 论文使用约 120 万张训练图片、1,000 个类别。模型包含约 6,000 万参数、65 万个神经元、五个卷积层和三个全连接层。问题不再是“算法能否写出来”，而是“数百万次图像处理与参数更新能否在可接受时间和内存内完成”。

### Pressure Builds：一张图片怎样膨胀为大量相似运算？

跟随一个 224 × 224 × 3 的图像 Crop。第一卷积层使用 96 个 11 × 11 × 3 的 Filter（滤波器），Stride（步幅）为 4。每个 Filter 要在许多空间位置重复执行乘加；不同位置、不同 Filter 和一个 Batch 中的不同图片提供了大量相似工作。

这正适合 GPU：不是让一个线程独自理解整张猫图，而是让大量线程分别处理不同位置和通道，再逐层组合结果。ReLU、卷积和矩阵运算有大量规则工作；而数据布局、边界、归约和层间依赖仍需要软件安排。

### Turning Point：为什么不是“买一张 GPU”就结束？

Krizhevsky、Sutskever 和 Hinton 编写了高度优化的 GPU 卷积实现。论文明确说，单张 GTX 580 只有 3 GB Memory，不足以容纳他们计划的网络，因此把网络分到两张 GPU。

他们不是让两张 GPU 在每一层都交换全部信息，而是把一半 Kernel 放在一张 GPU、另一半放在另一张，并只在特定层允许跨 GPU 通信。论文说明这个连接方案经过选择，使通信保持为计算量中可接受的部分。

### Cascade：一个 Batch 怎样成为流水系统？

训练使用 Batch Size 128。GPU 处理当前 Batch 时，CPU 同时为下一 Batch 生成随机 Crop、水平翻转和颜色扰动。论文称这种重叠让数据增强在训练流水中“实际上不增加额外计算等待”。

在 GPU 内，卷积把规则工作分配给许多线程；准备好的 Warp 在其他 Warp 等待数据时继续执行；两张 GPU 各自持有部分参数与激活；到需要跨越分区的层时才交换数据。HBM 当时尚未进入这个产品，3 GB GDDR Memory 与跨 GPU 连接直接塑造了模型分区。

于是，训练速度不是某一个数字决定的，而是 Parallel Work、Memory Capacity、Memory Access、CPU–GPU Overlap、GPU–GPU Communication 和优化代码共同形成的系统结果。

### Decision：研究团队接受了哪些工程约束？

他们选择两张 GTX 580、专门优化的 GPU 代码、Batch 128、特定跨 GPU 连接和约 90 次遍历训练集；同时使用 ReLU、Data Augmentation、Dropout 与 Weight Decay 控制训练和过拟合。

这项决策牺牲了软件通用性与实现简单度，换取了一个当时能训练的大模型。GPU 并不是论文中唯一创新，但它改变了“多大模型能在几天内被实验”这一研究边界。

### Outcome：15.3% 到底是谁的成绩？

训练在两张 GTX 580 上用了约 5–6 天。论文描述的单个 CNN 在 ILSVRC-2012 Test Data 上得到 18.2% Top-5 Error；把七个 CNN 的预测取平均后，提交结果是 15.3%，第二名是 26.2%。

26.2% 与 15.3% 相差 10.9 个百分点。若用第二名作分母，错误率相对下降约 `10.9 / 26.2 = 41.6%`。但 15.3% 不能写成“一张 AlexNet 单模型的误差”：它来自七个网络的 Ensemble（集成），其中还包含在更大数据集上预训练的模型。

论文还比较了双 GPU 网络与较小的单 GPU 网络，Top-1 / Top-5 Error 分别低 1.7 / 1.2 个百分点，训练时间略少。但作者明确提醒，这个比较偏向单 GPU 网络，因为两者容量并不相同。因此它不是纯粹识别“两张 GPU 让同一个模型快多少”的受控实验。

### Aftermath：AlexNet 证明了什么，又没有证明什么？

它证明大规模数据、深度卷积网络、优化 GPU 计算和正则化方法能够共同产生此前显著更好的图像分类结果，并把 GPU 加速推到 AI 研究中心。

它没有证明 GPU 单独造成 10.9 个百分点差距。数据集、网络架构、ReLU、Dropout、Data Augmentation、训练方法、代码实现和 Ensemble 都参与结果；论文也没有提供同一优化模型在 CPU 上的干净反事实。

## 10. Comparison（比较）：理论 FLOPS 与有效吞吐之间隔着什么？

| 层级 | 看起来拥有什么 | 转成有效吞吐还需要什么 | 常见误解 |
|---|---|---|---|
| Peak Compute | 核心数、时钟、每周期运算 | 指令类型、发射率、依赖与足够工作 | “FLOPS 高就一定快” |
| Resident Work | Active Warp / Occupancy | Warp 真的 Ready，资源不先耗尽 | “Occupancy 100% 才最好” |
| Control Flow | 大量线程 | 同一 Warp 尽量走共同路径 | “只要线程多就并行” |
| Memory | HBM / GDDR Peak Bandwidth | 合并访问、Cache 重用、足够并发 | “带宽规格就是程序带宽” |
| Communication | 多 GPU / 多节点 | 每次交换后有足够计算可摊薄成本 | “GPU 数翻倍，速度就翻倍” |
| Software | Kernel 能运行 | 优化 Library、Compiler、Profiler 与正确算法 | “硬件规格决定全部性能” |

Peak FLOPS 是天花板，不是承诺。它通常由计算单元、每周期可执行操作数和频率构成；程序还必须持续向这些单元提供正确指令和数据。真实吞吐是每一层利用率相乘后的结果，而不是某一个峰值数字。

## 11. Industry Apprenticeship：CUDA 为什么能把一次 GPU 销售变成平台关系？

今天只回答一个行业问题：**当客户购买的是算力结果而不是裸芯片时，CUDA 的哪些层让 NVIDIA 获得持续的平台权力？**

CUDA 最初于 2006 年推出。它不只是一个 Programming Language（编程语言），而是一套让开发者把通用并行工作映射到 NVIDIA GPU 的平台：包括编程模型、Compiler（编译器）、Runtime（运行时）、Driver（驱动）、Debugger / Profiler（调试与性能分析工具），以及 cuBLAS、cuFFT、cuDNN 等优化 Library（库）。

付款与受益要分开看：

- NVIDIA 投资 GPU 架构、驱动、编译器、Library、工具和文档，并通过 GPU、系统以及部分企业软件与服务获取收入。
- Cloud Provider、OEM 与 System Builder 购买 GPU / 系统或基础设施，再把机器、实例与服务卖给下游。
- Framework 与 Library 团队把高层 API 接入 CUDA；Application Team 投入工程时间、测试和运维，把工作负载建立在这些接口之上。
- 最终客户为服务器、云时、软件订阅或业务结果付款。CUDA Toolkit 本身是否单独收费，不足以衡量平台价值；它可以通过提高硬件可用性和需求来捕获价值。

平台权力来自累积的 Switching Cost（切换成本）：代码要移植，Library 覆盖要重建，数值结果和性能要重新验证，Profiler 与部署流程要替换，工程师要重新学习，框架和第三方工具还要支持目标平台。每一项都不保证客户永远不换，但它们让比较从“哪颗芯片峰值更高”变成“整个工作负载迁移要多久、风险多大、最终每美元和每瓦吞吐怎样”。

NVIDIA 2026 Form 10-K 把自己的战略明确描述为 Hardware、Systems、Software、Algorithms、Libraries、Models、Data 和 Services 的平台，并称开发者数量与 Installed Base 会强化生态、提高客户价值。这是公司对自身战略和优势的陈述，不是独立证明 CUDA 必然造成锁定或客户没有替代选项。

替代路径包括 CPU、AMD ROCm、其他 Accelerator、自定义 ASIC、开放编译器与跨平台 Framework。它们的竞争力不能只看芯片，而要看 Workload Coverage、Library Maturity、Porting Time、Correctness、Tooling、Availability、Price、Power 与长期 Roadmap。

真正的行业指标因此包括：

- **Time to Solution**：一次训练、模拟或推理完成要多久。
- **Throughput per Dollar / Watt**：完整系统而非芯片峰值的经济与能耗效率。
- **Effective Bandwidth 与 Compute Utilization**：数据和计算资源实际使用多少。
- **Library / Framework Coverage**：关键算子是否已优化并可维护。
- **Porting & Qualification Time**：迁移代码、验证结果和重新上线需要多少工程时间。
- **Installed Base 与 Developer Availability**：组织能否雇到、培训并保留会使用平台的人。

## 12. Fact、Interpretation、Inference 与 Hypothesis

> **Fact（事实）**：CUDA Guide 规定 Warp 由 32 个线程组成，并解释分支分歧、Occupancy 和存储事务；AlexNet 论文记录约 120 万张训练图片、6,000 万参数、两张 3 GB GTX 580、5–6 天训练、单模型 18.2% Top-5 Error 与七模型集成 15.3%；NVIDIA 2026 Form 10-K 把 CUDA 和数百个 Library / Framework / SDK / API 列为其技术栈。

> **Interpretation（解释）**：GPU 的优势来自把规则、独立且数据访问友好的工作映射到大量线程，并在 Warp 等待时调度其他 Warp；硬件并行度、存储系统和软件工作形状必须共同匹配。

> **Inference（推断）**：成熟 Library、Tooling、兼容性、开发者经验和部署流程会提高客户迁移成本，使 GPU 竞争从单颗芯片性能扩展为整个平台的可用性与时间成本。

> **Hypothesis（仍需验证的假设）**：某个具体客户选择 NVIDIA 主要因为 CUDA，或 CUDA 单独解释 NVIDIA 的价格、毛利、份额与议价权。验证需要客户级 Workload、替代平台性能、迁移成本、采购合同、可用性与组织能力数据。

## 13. Transfer（迁移）：以后看到“GPU 性能提高两倍”，先问什么？

先问工作负载：是同一模型、同一精度、同一 Batch、同一延迟目标和同一软件版本吗？吞吐提高是否牺牲了延迟、精度、容量或功耗？

再问利用路径：瓶颈在 Compute、Memory Bandwidth、Memory Capacity、Control Divergence、Synchronization、Communication 还是 CPU / I/O？Peak FLOPS、Occupancy 和带宽各自是上限、条件还是实测？

最后问平台边界：结果用了哪些 Library、Compiler、Kernel 优化和多 GPU 通信；切换到替代平台需要改多少代码、验证多少结果、等待多少硬件？只有把硬件、工作负载与软件同时固定，性能和议价主张才可比较。

## 14. 90-second Memory Test（90 秒记忆测试）

不回看正文，试着回答：

1. Latency 与 Throughput 分别问什么？GPU 为什么更偏向后者？
2. Thread、Block、Warp 与 SM 各是什么？为什么 Warp 而不是单个 Thread 决定分支效率？
3. Occupancy 为什么能隐藏等待，却不是越高越快？
4. 32 个线程各读 4 字节时，连续访问与大跨度访问为什么会分别搬 128 字节和最多 1,024 字节？
5. AlexNet 的 18.2%、15.3% 与 26.2% 各属于谁，为什么不能把差距全部归因于 GPU？

## Teach-back（20-30 分钟讨论）

1. 请跟随一个像素，从 HBM / GDDR 到 Cache、Warp、算术通道和输出，解释 Occupancy、Divergence、Coalescing 与 Synchronization 分别会在哪一步降低有效吞吐；不能只说“GPU 并行所以快”。
2. 两款 GPU 的理论 FLOPS 分别是 100 和 160，真实模型吞吐却是 90 和 104。请构造至少四种机制，并说明你需要哪些 Kernel、Memory、Warp、Library、精度、功耗与通信数据，才能判断是硬件、软件还是工作负载映射造成差距。

## Closing the Loop（闭环）

**现在我们可以重新回答开头的问题**：32 个计算单元只做出 16 个的工作，不一定因为芯片缺陷或数据不足，而可能因为同一 Warp 的线程走了两条路径，硬件必须依次执行并关闭不属于当前路径的 Lane。更广义地说，GPU 只有在程序提供大量相似、独立、地址友好且可持续调度的工作时，计算单元数量才会转化为有效吞吐。

今天在地图上正式点亮 `SYSTEM.COMPUTE.ACCELERATOR_GPU_PARALLELISM`，并以行业应用建立 `BUS.SEMICONDUCTOR.ACCELERATOR_PLATFORM_ECONOMICS`；HBM、Compute Foundation、Advanced Packaging、Interdependence 与 Bottleneck 只记录 review / transfer，不自动升级 mastery。

下一步通向 Roofline & Arithmetic Intensity：我们会把昨天的 Memory Bandwidth 与今天的 Compute Throughput 放在同一张性能地图上，判断一个 Kernel 究竟缺数据、缺计算，还是两者都没有被软件充分利用。
