# Mastery Core（掌握核心）

## 1. Opening Puzzle（开场谜题）：三台机器都活着，服务为什么仍然全挂？

一家在线商店运行三台完全相同的应用服务器。监控显示三台 VM 的 Operating System 都还在运行，CPU 和内存也没有异常；团队因此说：“我们有三份副本，已经高可用。”

可是用户仍然无法结账。可能的原因很多：三台 VM 都在同一机架，机架上联网络断了；它们分散在不同机架，却都依赖同一数据库；数据库也有副本，却使用同一错误配置；应用和数据库都正常，但 DNS、Load Balancer 或身份服务无法把请求送进去；备用区有机器，但切换必须调用此刻不可用的控制面；代码部署把同一个缺陷同时推给全部副本。

注意这个矛盾：**组件副本可以存活，服务路径仍然失败。** 用户请求必须穿过一条完整路径，只要任一硬依赖不可用而系统又没有替代路径，服务就不能完成约定功能。

## 2. 先定义母概念：Reliability（可靠性）研究什么？

Reliability（可靠性）是一个系统在规定条件和时间内，持续完成预期功能的能力。对在线服务来说，核心问题不是“机器有没有开机”，而是“用户要求的有效请求是否在约定时间内得到正确结果”。

今天需要分开几个相近但不相同的词：

- **Availability（可用性）**：在定义的时间或请求边界内，服务成功完成约定功能的比例。
- **Resilience（韧性）**：系统承受故障、限制影响并恢复服务的能力。
- **Durability（持久性）**：数据在一段时间后仍然存在且正确；明天会单独学习。数据可以没有丢失，但暂时读不到。
- **Fault Tolerance（容错）**：某些组件失效时，系统仍不间断地提供功能。
- **Disaster Recovery（灾难恢复）**：大范围中断后恢复系统与数据的策略，通常允许一段停机或数据损失窗口。

母概念先于地理名词：Region、Zone 和 Rack 不是天然的“可靠性等级”，而是设计者用来隔离某些共同故障的边界。边界是否有价值，取决于它是否真的切断了你担心的故障机制。

## 3. Follow One Request（跟随一个请求）：可靠服务需要哪四件事？

一位用户点击“确认支付”。这个请求先经过 DNS 找到入口，再进入 Load Balancer，被送到一台应用副本；应用读取 Session、Inventory 和 Payment State，写入结果，再把响应返回用户。

把这个请求看成一条必须完整闭合的服务路径：

1. **Reachability（可达性）**：用户能否找到并到达服务入口？
2. **Compute（计算）**：至少一个正确的应用副本能否处理请求？
3. **State（状态）**：副本能否读取足够新、足够完整的数据，并安全写入新状态？
4. **Coordination（协调）**：健康检查、路由、权限、配置和故障切换能否把请求送到正确路径？

三台应用 VM 只增加了第二层的候选路径。如果 DNS、Load Balancer、数据库、身份、配置、网络或控制面仍是单一硬依赖，组件冗余没有闭合用户路径。

### 串联依赖为什么会吞掉“九”？

做一个透明模型。假设 DNS、入口、应用和状态存储四个硬依赖各自有 99.9% 可用性，并且暂时假设它们相互独立：

```text
End-to-end availability
= 0.999 × 0.999 × 0.999 × 0.999
= 0.996006 ≈ 99.6006%
```

单看每项都是“三个九”，串起来却只剩约 99.6%。若按一年 8,760 小时换算，99.6006% 对应约 35 小时不可用，而单个 99.9% 组件约 8.76 小时。这个模型不是实际云服务承诺，因为真实依赖并不完全独立，部分失败也可能被缓存或降级吸收；它只揭示一个方向：**硬依赖越多，完整路径越难保持可用。**

## 4. Failure Domain（故障域）：边界切断的是哪一种共同原因？

Failure Domain（故障域）是可能被同一个故障同时影响的一组资源。它不是固定尺寸，可以是：

- 一台 Host：主板、电源、固件或 Hypervisor 故障；
- 一个 Rack：Top-of-Rack Switch、PDU、Busway 或局部冷却故障；
- 一个 Availability Zone（可用区）：一组物理分离的数据中心及其区级网络、电力或服务边界；
- 一个 Region（区域）：地理区域和区域级服务、控制面或依赖边界；
- 一个软件 / 控制边界：同一部署、配置、证书、Identity、DNS、Metadata Store 或运维工具；
- 一个组织边界：同一团队、同一操作权限和同一 Runbook 可能把错误同时传播给所有位置。

AWS 当前文档把 Region 描述为独立地理区域，把 Availability Zone 描述为 Region 内多个独立位置；一个 AZ 由一个或多个离散数据中心组成，具有冗余电力、网络和连接，并通过低延迟、高带宽、冗余网络与同 Region 其他 AZ 相连。这个定义说明厂商试图隔离哪些物理故障，但它不保证客户应用已经跨 AZ 部署，更不保证所有软件和区域依赖都被切开。

### 四种放置，对四种问题

| 放置方式 | 能较好覆盖 | 仍可能共同失败 | 新代价 |
|---|---|---|---|
| 同 Host 多进程 | 单进程崩溃 | Host、机架、配置、数据库 | 最低网络与运维成本 |
| 不同 Host / Rack | Host、部分机架故障 | AZ、区域服务、部署、状态层 | 更多容量与网络 |
| 不同 Availability Zone | 单 AZ 物理故障 | Region、区域控制面、共同软件和数据错误 | 跨区复制、流量、延迟与复杂度 |
| 不同 Region | 区域级物理或服务故障 | 全球依赖、同一代码 / 凭证 / 操作、数据语义错误 | 复制延迟、RPO、路由、合规与高成本 |

正确问题不是“我们是不是 Multi-AZ”，而是：**对这次具体故障，副本是否真的处于不同故障域？**

## 5. Correlated Failure（相关故障）：为什么三份副本的数学可能完全错？

假设每个副本在一个观察窗口内独立失败的概率都是 1%。三份副本只有全部失败时服务才中断，那么：

```text
P(all three fail) = 1% × 1% × 1% = 0.0001%
```

看起来从 1% 降到了万分之一百分比。但这个结论全部依赖“独立”二字。

现在加入一个概率为 0.5% 的共同故障：一次错误部署、区域 Metadata Store 故障或共享凭证过期会同时影响三份副本。第一阶模型变成：

```text
P(service fails)
≈ 0.5% + 99.5% × 0.0001%
≈ 0.5000995%
```

共同故障项比独立三副本项大约 5,000 倍。数字是假设，不是任何云厂商实测；它改变理解的地方在于：当共享原因占主导时，继续增加同类副本几乎不降低风险。此时更有价值的动作是切断共同依赖、缩小 Blast Radius（爆炸半径）、改变部署节奏、增加 Guardrail，或建立不依赖故障控制面的恢复路径。

## 6. Replica（副本）怎样才真正变成 Failover（故障切换）？

Replica（副本）是能承担相同功能或保存相同状态的另一份运行单元。历史上它解决的是单一机器会坏、维护必须发生、负载会波动的问题。付款方通常是服务所有者：他为额外计算、存储、复制流量和运维付费；受益方是依赖服务连续性的用户和业务。

但“有副本”常被误解为“会自动接管”。一次完整 Failover 至少需要四步：

1. **Detect（检测）**：健康信号必须区分真正故障与短暂抖动，过慢会拖长停机，过快会制造错误切换。
2. **Decide（决策）**：系统必须知道故障范围，是单 Host、单 Zone、Region 还是错误数据；错误范围会把流量送向同一故障。
3. **Route（路由）**：DNS、Load Balancer、Service Discovery 或客户端必须把新请求送到备用路径。
4. **Serve with State and Capacity（带状态和容量服务）**：备用方必须有足够新且一致的数据、权限、密钥、网络和预留容量，而不是只存在一台空 VM。

这解释了为什么恢复演练必须真的切流量。只测试“备用机能启动”，没有测试 Detection、Routing、State、Capacity 和依赖，就没有验证 Failover。

## 7. RTO、RPO 与 Error Budget（恢复目标与错误预算）

Reliability 必须从愿望变成可测目标：

- **RTO / Recovery Time Objective（恢复时间目标）**：一次中断后，服务最多可以多晚恢复。
- **RPO / Recovery Point Objective（恢复点目标）**：恢复后，最多可以丢失多旧的一段数据。
- **SLO / Service Level Objective（服务级目标）**：团队对服务可用性、延迟或正确率设定的工程目标。
- **Error Budget（错误预算）**：`1 − SLO`，表示一个窗口内允许失败的比例。
- **SLA / Service Level Agreement（服务级协议）**：提供方与客户之间带测量口径、排除项和补救方式的合同承诺。

按 730 小时的透明月度模型：

```text
99.9% availability → 0.1% × 730h = 43.8 minutes budget
99.99% availability → 0.01% × 730h = 4.38 minutes budget
```

同一场 45 分钟完整中断，会刚好耗尽 99.9% 月度预算，却约是 99.99% 预算的 10.3 倍。数字告诉我们“多一个九”不是漂亮小数，而是检测、切换、容量与恢复时间必须缩短一个数量级。

SLA 不等于业务连续性保险。它通常只在特定测量和排除条款下提供 Service Credit（服务抵扣），不会自动偿付客户的全部收入、声誉或数据损失。客户若需要比底层产品更高的端到端可用性，仍要设计自己的冗余、降级与恢复。

## 8. Deep Case — Amazon S3 US-EAST-1，2017：对象跨多个 AZ，为什么请求仍然失败？

### Before：冗余对象存储看起来已经切开了设备和机房故障

Amazon S3 是 Object Storage（对象存储）：客户用 Key 写入和读取对象，不管理底层磁盘与服务器。AWS 当前文档说明，S3 Standard 等存储类别会把对象冗余存储在一个 Region 的至少三个 Availability Zone，设计上可以承受整个 S3 AZ 的丢失。

这解决的是数据副本和物理设备 / AZ 损坏问题。可是一次 GET 不只需要对象字节仍然存在，还要知道对象位于哪里；一次 PUT 还要找到新的存储位置并更新 Metadata。S3 因此还有区域级 Index 与 Placement 等子系统。

### Pressure Builds：服务规模增长，但完整重启路径很少被触发

2017 年 2 月 28 日，S3 团队在 Northern Virginia（US-EAST-1）调试 Billing System 进度慢的问题。运维人员按既有 Playbook，准备从一个用于 Billing 的 S3 子系统移除少量服务器。

AWS 复盘说明，S3 的子系统设计可以在少量容量被移除或故障时继续工作；移除与替换容量本来就是正常操作。但 S3 多年来快速增长，最大的 Region 已经多年没有完整重启 Index 或 Placement 子系统。正常的局部韧性并没有等同于大规模恢复路径已经在当前规模下充分演练。

### Turning Point：一项合法操作的输入让移除范围越过安全边界

上午 9:37 PST，一名获授权团队成员输入命令参数时出错，移除的服务器远多于预期。被误移除的容量不只影响 Billing 路径，还支撑两个关键 S3 子系统。

Index Subsystem 管理 Region 内对象的 Metadata 与位置，GET、LIST、PUT 和 DELETE 都需要它；Placement Subsystem 为新对象分配存储，PUT 还额外依赖它。被移除的容量足以使两个子系统都必须完整重启。

这里的故障域不是“一块磁盘”或“一个 AZ 的对象副本”，而是共同的区域级 Metadata / Placement 与运维工具边界。对象仍有冗余副本，并不能绕过“请求要先找到对象或分配位置”这个硬依赖。

### Cascade：跟随一次请求，看共同依赖怎样扩大 Blast Radius

用户发出 GET。对象字节可能仍安全存在于多个设备和 AZ，但 Index 暂时无法回答对象位置，请求因此不能完成。用户发出 PUT，除了 Index，还需要 Placement 为新对象找到合格位置；Placement 又要等待 Index 恢复。

级联随后跨出 S3。AWS 官方复盘列出：S3 Console、EC2 新 Instance 启动、从 S3 Snapshot 取数据的 EBS Volume，以及 Lambda 等依赖 S3 的区域服务都受影响。AWS Service Health Dashboard 的管理控制台本身也依赖 S3，从事件开始到 11:37 PST 无法正常更新各服务状态，只能使用 Twitter 和 Dashboard Banner 沟通。

因此“状态页为什么也更新不了”不是旁枝末节。它暴露了一条共同依赖：观察和沟通故障的工具与被观察服务共享了同一受损路径。

### Decision：先恢复 Index，再恢复 Placement，没有无痛捷径

团队不能跳过完整重启和 Metadata Integrity Check。若为了更快恢复而省略安全检查，可能把暂时不可用变成错误位置、重复分配或数据一致性问题。

到 12:26 PST，Index 恢复了足够容量，GET、LIST 和 DELETE 开始服务；从 9:37 算起是 169 分钟。到 1:18 PM，Index 完全恢复。Placement 必须在 Index 可用后继续恢复，到 1:54 PM PUT 才恢复正常；事件从触发到 S3 正常运行共 257 分钟，即 4 小时 17 分钟。部分下游服务还有积压，因此恢复更晚。

这些时长不是“整个 AWS 完全停机 257 分钟”，也不是正式 SLA 结算结果；不同 API、时间段和下游服务的影响不同。它们说明完整恢复顺序由依赖关系和安全检查约束，不能用对象副本数直接推导。

### Outcome：物理冗余没有覆盖区域控制与 Metadata 的共同失败

事件没有证明 Multi-AZ 数据复制无效。恰恰相反，它证明复制只覆盖其设计故障集合：设备或位置损失。此次触发来自一个操作工具和容量保护不足，主要影响区域级 Index / Placement 的服务可用性。

如果把 257 分钟放进纯教学 Error Budget：它约为 43.8 分钟月度 99.9% 预算的 5.9 倍，约为 4.38 分钟 99.99% 预算的 58.7 倍。但这不是对 2017 S3 SLA 的正式判定，因为真实结算需要当时合同、受影响请求和排除口径。

### Aftermath：修复重点不是“再复制一份对象”

AWS 修改运维工具，让它更慢地移除容量，并加入最低容量 Guardrail；同时审计其他工具。S3 加速把服务拆成更小 Cell，以缩小 Blast Radius 并让大规模恢复更容易测试。AWS 还把 Service Health Dashboard 的管理控制台改为跨多个 Region 运行。

三项措施分别切断三个共同原因：限制一次操作能造成的容量损失，缩小共享子系统的故障范围，让故障沟通不再依赖同一 Region。它们都比“给同一边界再加一个普通副本”更针对本次机制。

## 9. Meaningful Comparison（有意义的对照）：同一份数据安全，不代表同一份服务可用

| 问题 | 设计目标 | 2017 S3 案例告诉我们什么 | 需要的额外证据 |
|---|---|---|---|
| 对象会不会丢？ | Durability、多设备 / 多 AZ 复制、校验与修复 | 官方复盘没有报告对象副本同时丢失 | 复制、校验、修复和数据损失记录 |
| 请求能不能成功？ | Availability、完整请求路径 | Index / Placement 不可用使 API 失败 | 按 API / Region 的成功率与延迟 |
| 故障能否被限制？ | Fault Isolation、Cell、Blast Radius | 区域子系统和共同工具放大影响 | 依赖图、Cell 边界和故障注入 |
| 服务多久恢复？ | RTO、Runbook、预置容量和安全检查 | 大 Region 完整重启比预期慢 | 演练结果、恢复步骤和容量余量 |
| 谁承担后果？ | SLA、Shared Responsibility、客户架构 | Provider 修复底层服务；客户仍要设计端到端连续性 | 服务条款、客户拓扑与业务影响 |

## 10. Boundary & Counterexample（边界与反例）

多副本不是越分散越好。一个要求强一致、亚毫秒延迟的数据库，把每次写入同步到远距离 Region，可能因为光纤传播、网络分区和协调而无法达到性能目标；改成异步复制又会引入非零 RPO。可靠性提高一类故障覆盖时，可能增加延迟、成本和状态复杂性。

反过来，一个无状态图片转换服务可能不需要多 Region：输入对象可重放，任务允许排队，业务 RTO 是数小时。为它建设 Active-Active 跨 Region 反而可能比中断本身更昂贵、更复杂、更容易配置错误。

所以可靠性工程不是追求最大副本数，而是在业务影响、故障集合、RTO、RPO、成本和操作能力之间选择可验证的边界。

# Industry Apprenticeship（行业学徒制）

## 11. 今天的行业问题：谁为云冗余付钱，SLA 又把什么风险留给谁？

先从玩家与资产开始：

- Cloud Provider（云服务商）建设 Region、Availability Zone、网络、服务器、存储、控制面和运维系统。
- Customer / Workload Owner（客户 / 工作负载所有者）选择 Region、Zone、实例数量、数据复制、路由、备份、部署与应用降级方案。
- Managed-service Team（托管服务团队）接管更多数据库、对象存储或消息系统的运行工作，但客户仍决定数据、权限、调用方式和端到端依赖。
- End User（终端用户）支付订阅、交易或时间，并承担服务失败带来的实际体验。

### Shared Responsibility（共同责任）为什么历史上会出现？

On-premises（本地部署）时代，企业自己购买机房、服务器、操作系统和应用。Public Cloud 把底层设施与部分平台运营交给 Provider，但没有把客户的应用设计、数据、权限和业务恢复目标一并接走。

AWS 的正式 Shared Responsibility Model 主要用于 Security 与 Compliance：AWS 负责 Cloud 本身的硬件、软件、网络和设施，客户责任随所选服务而变化；EC2 客户管理 Guest OS 与应用，而 S3 等更抽象服务由 AWS 运行更多底层层级，客户仍管理数据、分类、加密选择和权限。可靠性也必须按具体服务文档和客户架构逐层划界，不能用一句“上云以后 AWS 负责”替代。

### 谁付款？

如果客户把应用副本放在三个 AZ，通常要支付更多 Instance、Load Balancer、Storage、Database Replica、Monitoring 和可能的跨区流量。备用容量若一直空闲，看起来“利用率低”，但它购买的是故障时的静态稳定性：当一个 AZ 受损时，不必依赖控制面临时创建资源。

Provider 也为每个 AZ 的物理隔离、冗余网络、基础服务和内部备用付资本与运维成本，再通过服务价格在客户间回收。Managed Service 的价格把更多底层复制与运维打包，但客户仍为服务等级和用量买单。

### SLA 到底支付什么？

AWS 当前 EC2 SLA 提供一个具体对照：单 EC2 Instance 的 Instance-level 承诺是 99.5%；当账户把运行中的 EC2 Instance 同时部署在同 Region 两个或更多 AZ 时，Region-level 承诺是 99.99%。这不是说“两台机器数学上必然四个九”，而是产品对不同部署边界给出的合同承诺。

若未达到承诺，补救通常是未来账单的 Service Credit。它不等同于退还全部业务损失，也不替客户修复单 AZ 应用、错误部署、坏数据或共同数据库依赖。SLA 解决的是可测合同边界与补救；Architecture 解决的是用户请求是否真的有替代路径。

### 外行最容易误解什么？

最常见误解是“Provider 有多个 AZ，所以我的应用自动 Multi-AZ”。Region 提供可选择的故障隔离边界，客户或 Managed Service 必须实际使用它；复制、健康检查、路由、状态、容量和演练缺一不可。

另一个误解是“Service Credit 等于风险已经转给 Provider”。实际业务损失可能远大于底层服务费，合同还有测量、索赔和排除条款。客户通过架构、保险、合同和业务降级共同管理剩余风险。

## 12. Practitioner Metrics（从业者真正看的数字）

- **User-visible Availability**：有效请求成功率与尾延迟，不只看 VM Uptime。
- **Error-budget Burn**：失败在多快地消耗 SLO 允许的预算。
- **Failure-domain Coverage**：副本跨了 Host、Rack、Zone、Region，还是只跨了名字？
- **Common-mode Dependency Count**：DNS、Identity、Control Plane、Database、Deployment 与 Observability 中仍有多少共同路径。
- **Detection Time + Decision Time + Routing Time + Recovery Time**：RTO 被哪一步消耗。
- **RPO / Replication Lag**：切换后最多缺失或落后多少状态。
- **Failover Capacity**：失去一个故障域后，剩余位置能否承载峰值，而不是平时是否有空机。
- **Game-day Success Rate**：在受控演练中，切换是否真正完成且没有破坏数据。
- **Cost per Protected Workload**：额外实例、存储、流量、软件与运维，相对减少的业务损失。

## 13. Fact、Interpretation、Inference 与 Hypothesis

> **Fact（事实）**：AWS 官方复盘记录，2017-02-28 9:37 PST 的错误命令输入移除了过多 S3 子系统容量，导致 US-EAST-1 的 Index 与 Placement 子系统完整重启；GET / LIST / DELETE 从 12:26 起逐步恢复，PUT 到 1:54 恢复。AWS 当前文档说明 S3 Standard 等在至少三个 AZ 冗余存储对象。

> **Interpretation（解释）**：对象数据跨 AZ 存在，并不等于每条请求路径的 Metadata、Placement、控制与恢复依赖都跨同样的故障域。冗余只覆盖它明确切开的故障集合。

> **Inference（推断）**：对高可用工作负载，削弱共同依赖、预置故障容量、让数据面静态稳定、限制运维 Blast Radius，常比继续增加同一边界内的普通副本更有价值。

> **Hypothesis（仍需验证的假设）**：某个具体客户的 Multi-AZ 或 Multi-region 架构能达到声明的可用性。验证需要实际依赖图、故障相关性、健康检查、复制延迟、路由、容量、Game Day、SLO 与用户请求数据；部署图和副本数量不够。

### Evidence Boundary（证据边界）

S3 复盘由 AWS 自己发布，能直接支持触发、子系统依赖、恢复顺序和公开改进，但不披露完整内部架构、全部客户影响、独立故障率或财务损失。今天使用的是当前 AWS 区域、S3 存储类别与 SLA 文档；它们可能不同于 2017 当时的产品和合同条款。串联可用性、三副本与 Error Budget 均为透明教学模型，不是 S3 实测或 SLA 判定。

## 14. Transfer（迁移）：以后看到“我们有三个副本”，按什么顺序追问？

先定义服务结果：哪一种用户请求必须成功，允许多慢，允许丢多少数据？

再列出完整路径：入口、计算、状态、身份、配置、网络、控制面和观测工具，哪些是硬依赖，哪些可以降级？

然后给每个故障命名：Host、Rack、Zone、Region、软件部署、凭证、Metadata、Operator 或第三方；三份副本在这个故障下是否仍然独立？

最后演练切换：检测用了多久，流量怎样移动，数据落后多少，备用容量是否足够，恢复是否依赖正在故障的控制面。只有这一步完成，Replica 才从架构图上的图标变成可承诺服务。

## 16. 现在我们可以重新回答开头的问题

三台 VM 都活着却无法结账，是因为服务可靠性不是存活副本数，而是完整用户路径在目标故障下仍有独立、可达、带状态且有容量的替代路径。只要三台机器共享同一个网络、状态、控制面、配置或操作故障，它们就不是针对该故障的三次独立机会；只有检测、决策、路由和状态切换都在 RTO / RPO 内完成，冗余才成为可用性。

今天在地图上点亮了 `SYSTEM.COMPUTE.CLOUD_RELIABILITY_REGIONS_FAILURE_DOMAINS`：我们把昨天的“可行放置”推进成“可承诺服务”，学会按故障机制而不是副本数量判断冗余。下一步通向 Cloud Storage Durability, Replication & Consistency（云存储持久性、复制与一致性）：同一份状态怎样跨故障域复制，为什么“十一位九的持久性”仍不等于立即可读、无数据丢失或强一致。
