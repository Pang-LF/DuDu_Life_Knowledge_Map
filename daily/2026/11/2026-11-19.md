昨天，我们确认一个 Object 可以被可靠写入、跨故障域保存并按明确的一致性语义读取。今天沿着同一个 Object 再向用户走一步：字节即使完整地躺在服务器里，如果用户无法把名称解析成地址、网络没有到这个地址的可达路径、入口没有把请求交给健康目标，数据对用户仍然等同于不存在。

这一步必须先于 Multi-region Architecture 与 Disaster Recovery。复制出第二个 Region 只创造了潜在副本；只有 DNS、路由、负载均衡、身份和回程路径能把请求真正切过去，它才成为可用的恢复能力。

> **今天如果只记住一件事，就是：云网络不是一根“更粗就更快”的管道，而是一串相互独立的决策——名字解析成什么地址、地址是否可达、入口选择哪个健康目标、字节穿过哪些边界；其中任何一环失效，都能让仍在运行的服务器对用户等同于不存在。**

# Mastery Core（掌握核心）

## 1. Opening Puzzle（开场谜题）：服务器全绿，网站为什么仍像消失了一样？

凌晨，值班面板显示：Web Server 进程还在，CPU 和内存正常，数据库没有丢数据，存储对象也能从机房内部读到。可是全球用户打开 App，只看到“无法连接”。

团队先问“服务器是不是坏了”，却忽略了更早的问题：用户输入的是一个 Name，不是服务器内存地址。客户端必须先得到一个 IP Address，Internet Router 必须知道怎样到达这个地址，入口必须接受连接并选择一个后端，后端还必须有一条返回路径。只要其中一步失去 Reachability（可达性），健康服务器就没有机会回答。

这正是今天要重建的直觉：**Service Health 不等于 Endpoint Health；Bandwidth 很大也不等于路径存在。**

## 2. 先定义母概念：Network System（网络系统）是什么？

Network System（网络系统）让不同位置的端点交换有边界的数据单元。它至少完成五件事：

1. **Naming（命名）**：人和应用用什么稳定名称指向服务？
2. **Addressing（寻址）**：名称当前对应哪些可路由地址？
3. **Routing / Forwarding（路由与转发）**：每一跳把 Packet 交给哪个下一跳？
4. **Endpoint Selection（端点选择）**：多个实例中，哪一个应接收这次连接或请求？
5. **Transport（传输）**：字节怎样分段、确认、重传、排序并返回？

DNS、BGP、Route Table、Load Balancer 和 TCP 分别解决不同问题。它们不是五个平级新 Core，而是同一条可达链上的不同判断。先定义 Network System，才能明白为什么“DNS 正常”“路由正常”“后端健康”都是局部陈述，不能单独证明一次请求成功。

## 3. Follow One Request（跟随一个请求）：从 `photo.example.com` 到一张照片

你在手机上打开 `https://photo.example.com/a.jpg`。一个简化但足够准确的路径如下。

### 第一站：Name Resolution（名称解析）

App 先问本机或操作系统的 Stub Resolver：“`photo.example.com` 的地址是什么？”如果缓存仍在 TTL（Time to Live，有效缓存时间）内，就直接使用旧答案；否则请求交给 Recursive Resolver。递归解析器可能依次询问 Root、顶级域和该域的 Authoritative Name Server，最终得到 A / AAAA Record，也就是 IPv4 / IPv6 地址。

DNS 不是连接本身。它只是把一个名称映射成下一步可使用的信息。正确返回 `203.0.113.10`，并不证明这个地址现在可达。

### 第二站：Route Reachability（路由可达性）

客户端把目的 IP 放进 Packet。家庭网络、ISP 和其他 Autonomous System（自治网络）根据路由信息选择下一跳。在公共 Internet 上，BGP（Border Gateway Protocol）让网络发布“哪些 IP Prefix 可以从我这里到达”；在 Cloud VPC 内，Route Table 则把 Destination CIDR 映射到 Internet Gateway、NAT、Peering、VPN 或其他 Target。

路由回答的是“往哪里交下一跳”，不是“最终应用一定健康”。如果没有匹配路由、Prefix 被撤回、ACL / Firewall 拒绝，或者回程找不到路，即使目标机器开着，连接也不会成立。

### 第三站：Connection & Load Balancing（连接与负载均衡）

客户端与入口建立 TCP / TLS 连接。Load Balancer 接受流量，按 Listener、Rule、Target Group 和算法选择一个被 Health Check 判定为健康的后端。AWS 的公开 ELB 文档描述：接收请求的负载均衡节点从健康注册目标中选择后端，并用 Private IP 把请求送过去。

Health Check 也只证明被测路径和条件。例如 `/health` 返回 200，不一定证明登录依赖、数据库写入或对象权限正常；反过来，后端进程健康也不代表 Load Balancer 仍有路由能到它。

### 第四站：Data Movement（数据移动）

后端读取照片，响应被切成 Packet，经交换机、路由器、Cloud Edge、Transit / Peering、ISP 和用户网络返回。TCP 在需要时重传、排序并控制发送速率。这里才开始出现大量 Bytes；前面的 DNS 和连接建立即使数据量很小，也可能决定整次体验是否能开始。

因此一次请求不是一条箭头，而是四份可以分别成功或失败的证据：**Name Answer、Reachable Route、Healthy Selection、Delivered Bytes。**

## 4. 四个常被混淆的词

| 概念 | 它真正问什么？ | 典型证据 | 它不自动保证什么？ |
|---|---|---|---|
| Reachability（可达性） | 现在是否存在允许 Packet 到达并返回的路径？ | Route / BGP、ACL、Traceroute、Connection Success | 高带宽、低时延、应用正确 |
| Latency（时延） | 一个动作或往返需要多久？ | DNS Time、Connect Time、RTT、TTFB、P95 / P99 | 大文件吞吐、高可用 |
| Bandwidth / Throughput（带宽 / 吞吐） | 单位时间最多或实际移动多少数据？ | Link Rate、Goodput、Bytes/s | 路径存在、首包很快 |
| Availability（可用性） | 完整有效请求在时间边界内成功吗？ | End-to-end Success Rate、SLO、Synthetic Test | 字节永不丢、一定低成本 |

一个 100 Gbit/s 接口在路由被撤回时吞吐是零；一条 100 Mbit/s、20 ms RTT 的路径对网页可能比 10 Gbit/s、200 ms RTT 更快开始响应；一个低延迟 DNS Cache 也可能快速返回已经失效的旧地址。

## 5. 两个数字模型：为什么“快”必须先说清是哪一种快？

### 模型 A：1 GB 文件与 1 Gbit/s 链路

十进制 1 GB 是 8 Gbit。忽略协议、拥塞、重传和存储速度，在 1 Gbit/s 上的理想序列化下限为：

```text
8 Gbit ÷ 1 Gbit/s = 8 seconds
```

这说明 Bandwidth 对大对象搬运非常重要。但一个 2 KB API 请求并不会因为接口从 1 Gbit/s 提到 10 Gbit/s 就自动快十倍；它更可能被 DNS、连接往返、TLS、排队和应用处理时间主导。

### 模型 B：Bandwidth–Delay Product（带宽时延积）

若路径是 1 Gbit/s，RTT 为 80 ms，要让链路持续装满，理论上需要大约：

```text
1 Gbit/s × 0.08 s = 0.08 Gbit = 10 MB in flight
```

也就是发送方在收到最早确认前，约需允许 10 MB 数据同时“在路上”。这不是一次请求固定占用 10 MB，也不是所有 TCP 的实际窗口；它解释了为什么高带宽的远距离路径仍可能因 Window、Loss 或确认等待而跑不满。Bandwidth 和 Latency 是相乘关系，不是两个独立宣传数字。

## 6. DNS：为什么它既加速，也会延迟变更？

DNS 出现，是因为人类和应用需要稳定名称，而机器地址会变化；全球名称数据库也大到不能由一台服务器维护。RFC 1034 把它设计为分布式层级数据库，并明确用 Local Caching 改善性能。

TTL 是 Authoritative Record 告诉 Resolver：“这份答案最多可以不重新询问多久。”假设 TTL 为 300 秒，某 Resolver 刚在切换前一秒缓存旧地址，它仍可能合法使用旧答案接近 5 分钟。把 TTL 在切换时才从 3,600 秒改成 60 秒，不会追溯改变已经缓存的 3,600 秒答案；必须在旧 TTL 足够早过期前先降低。

AWS 当前 Route 53 最佳实践把常见建议区间写为 60–172,800 秒，并说明更短 TTL 提高变更响应，却增加 Query Volume 和 Cost；更长 TTL 通常更快、更便宜，有时也更可靠，因为 Resolver 更少跨 Internet 查询。这里不存在 universally correct TTL：它是在 Cache Stability 与 Change Responsiveness 之间选择。

DNS Failover 也有边界。Health Check 可能让 Authoritative DNS 停止返回坏端点，但客户端、OS、Resolver 和应用的多层 Cache 仍决定旧答案多久消失。DNS 是 Endpoint Discovery，不是瞬时的全局开关。

## 7. Deep Case — Meta，2021 年 10 月 4 日：服务器仍在，为什么整个公司像从 Internet 消失？

### Before：一条请求通常先到边缘，再穿过 Meta Backbone

Meta 官方复盘描述，其全球 Backbone 由数万英里光纤连接不同计算设施。用户请求先到较小的边缘设施，再经 Backbone 到大型 Data Center，数据被处理后原路返回。边缘设施还运行 Authoritative DNS，并通过 BGP 向外部 Internet 宣告这些 DNS IP Prefix 可达。

这种设计有合理的安全机制：如果边缘 DNS 不能与 Data Center 通信，它会把自己视为不健康并撤回 BGP Advertisement，避免把用户导向内部已经断开的服务。

### Pressure Builds：日常维护拥有全局改变路径的权力

工程师需要维修光纤、增加容量或更新 Router，因此会让部分 Backbone 暂时离线。系统设有 Audit Tool，原本应阻止危险命令。可是大规模网络的控制动作既是正常运维工具，也可能改变所有数据路径；这是一种高耦合的 Control Plane 权力。

### Turning Point：一个容量评估命令切断了全部 Backbone 连接

2021 年 10 月 4 日，一次例行维护中执行的命令本来用于评估全球 Backbone 容量，却意外让 Backbone 的全部连接退出运行。官方复盘说，Audit Tool 中的 Bug 没有正确阻止这个命令。Data Center 之间以及 Data Center 与 Internet 之间的连接被切断。

这里先坏的不是 DNS Database，也不是所有服务器进程；先坏的是承载这些系统相互通信的路径。

### Cascade：路由失败让正常运行的 DNS 变成不可达，DNS 失败又拿走内部修复工具

边缘 DNS 发现自己无法与 Data Center 通信，于是按设计撤回 BGP Advertisement。结果非常反直觉：**DNS Server 仍在运行，却没有外部网络知道怎样到达它。** Recursive Resolver 无法取得 `facebook.com` 等名称的地址，用户无法找到服务。

故障继续向内传播。正常的远程 Data Center 访问路径不可用，许多诊断工具又依赖 DNS。工程师既难以进入设施，也失去了平时用来调查和修复的工具。安全加固让现场接入和硬件修改故意很难，这在日常降低攻击风险，却在这次内部错误下延长恢复。

Cloudflare 从外部观测到大约 15:40 UTC 开始大量 BGP 变化，`facebook.com` 在其 Resolver 上约 15:50–21:20 UTC 不可用，约 5 小时 30 分钟。这个窗口是 Cloudflare 的 DNS 可见性观测，不等于每个国家、每项 Meta 服务或每位用户的精确停机时长。

### Decision：派人进机房恢复 Backbone，再控制回流速度

因为主要和 Out-of-band 远程访问都不可用，Meta 派工程师现场进入 Data Center，确认问题并恢复 Backbone。恢复不能简单“一键全部打开”：服务离线时，个别 Data Center 的用电下降达到数十兆瓦；若流量、缓存填充和计算负载突然回归，电力与服务可能再次失稳。

团队依靠长期的 “Storm” 演练经验分阶段增加负载。这里的决定不是购买更多 Bandwidth，而是先恢复 Reachability，再管理系统重新耦合时的负载跃迁。

### Outcome：BGP 与 DNS 恢复后，服务才重新可被找到

Cloudflare 约在 21:00 UTC 观察到 BGP 活动恢复，DNS 约 21:20 UTC 可用。Meta 表示 Backbone 恢复后服务随之回来，并谨慎控制流量增长，避免新的系统级崩溃。

官方初步复盘称没有恶意活动，也没有证据显示用户数据因此被泄露。这个事实进一步分开了 Security、Data Durability 与 Availability：数据未被攻击或损坏，服务仍可因 Reachability 消失数小时。

### Aftermath：真正的恢复边界包括维护命令、独立接入、DNS、路由和演练

Meta 表示将加强测试、演练和整体韧性，并特别考虑过去从未模拟过的“全球 Backbone 全部离线”情景。案例留下的不是“BGP 很危险”这种口号，而是更精确的审计问题：一项控制动作能否同时拿走 Primary Path、Out-of-band Path、DNS 与修复工具？

这就是今天的核心：服务器是否运行只是路径末端的状态。一个服务要存在于用户眼中，Name、Route、Selection、Transport 和 Recovery Access 都必须保持或拥有真正独立的替代。

## 8. Meaningful Comparison（有意义的对照）：DNS、Routing 与 Load Balancing 各坏一次

### 对照一：DNS 返回失败

客户端没有 IP，连接尚未开始。症状常是 `NXDOMAIN`、`SERVFAIL` 或 Resolution Timeout。直接访问已知 IP 有时可能成功，但 TLS Certificate、Virtual Host 和应用依赖仍可能让这种测试不完整。

### 对照二：DNS 返回正确 IP，但 Route 不可达

客户端知道地址，却收不到回包。症状可能是 Connection Timeout、No Route 或 Packet Loss。更换 DNS Provider 并不会修复被撤回的 Prefix；Meta 事件中，DNS 不可达正是 Backbone / BGP 级联结果，不是 DNS 记录内容写错。

### 对照三：入口可达，但 Load Balancer 没有健康 Target

TCP / TLS 可能建立，随后得到 5xx 或 Reset。此时外部 Route 正常，问题位于 Target Registration、Health Check、Backend Route、Capacity 或 Application Dependency。

这三个对照说明，故障排查不能只问“网络通不通”。要标明**在哪一层、从哪个观察点、对哪个端点、在什么时间通。**

## 9. Boundary & Counterexample（边界与反例）

更短 TTL 不总是更可靠。它让 Failover 更快被 Resolver 看见，却提高 Authoritative Query Load，并让一次 DNS / Network 故障更快暴露给所有缓存过期的客户端。更长 TTL 能让已有答案在权威服务暂时不可达时继续工作，却也延长错误地址的生命。

更多路径也不自动独立。两条 ISP Link 若共享同一 Router Configuration、光纤管道、DNS Provider、Certificate Authority 或操作账号，可能在同一事件中一起失效。Multi-region 若仍共享一个错误的 Global Deployment、Identity、DNS Control 或 Human Command，也可能只是地理复制，不是端到端恢复。

同样，Internet Egress 收费不能直接证明 Provider 的边际传输成本等于价格，也不能单凭“Ingress 免费”证明恶意锁定。公开价目表说明客户账单规则；真实成本、折扣、容量利用率、谈判权和策略动机仍需额外证据。

# Industry Apprenticeship（行业学徒制）

## 10. 今天唯一的行业问题：一个 Byte 跨过 AZ、Region 或 Internet 边界时，谁付钱，谁控制路径，谁承担失败？

先把玩家分开：

- **Cloud Provider** 建设并运营 VPC Fabric、Router、Load Balancer、Managed DNS、Gateway 与区域间 Backbone，并定义公开计量边界。
- **Customer / Application Team** 选择 Region、AZ、Subnet、Route、DNS TTL、Load Balancer、Replication、CDN 与 Failover Architecture，并支付产品账单。
- **ISP / Transit / Peering / CDN / DNS Operator** 提供 Internet 接入、互联、缓存或名称解析；合同和结算方式可能是 Transit、Settlement-free Peering、Paid Peering 或 Managed Service。
- **End User** 通过宽带或移动网络发出请求，承受端到端 Latency、Failure 和体验损失，但通常看不到内部路径。

Cloud Networking 历史上解决的是：客户不必购买每一台 Router 和每一条 WAN，就能用软件对象建立隔离网络、地址、路由、入口与安全策略。付款方主要是 Cloud Customer；受益方是需要弹性、隔离、全球可达和可观测网络的应用。常见误解是“VPC 是一台虚拟路由器”，实际上它是一组分布式转发、策略和控制对象，Provider 不公开完整内部实现。

## 11. 钱流不是一个 `$ / GB`

AWS 当前公开页面提供一个具体但会随 Region 和时间变化的例子：EC2 从 Internet 传入数据列为 `$0.00 / GB`；US East (Ohio) 传出 Internet 在全局每月 100 GB 免费额度后，前 10 TB 列为 `$0.09 / GB`；同 Region 跨 AZ 的相关流量列为 `$0.01 / GB in each direction`。这些是公开 List Price，不是所有服务、地区、私有折扣或架构的统一价格。

若一个产品每月向 Internet 发送 10 TB，透明的十进制模型在忽略 100 GB 免费额度、税和分层价差时是：

```text
10,000 GB × $0.09 / GB = $900 / month
```

这个 `$900` 不是应用完整网络账单。还可能有 Load Balancer、NAT Gateway、跨 AZ、CloudFront / CDN、Public IPv4、DNS Query、DDoS Protection、日志和专线费用；反过来，CDN Cache Hit 可能减少 Origin Egress 与 Latency。

Application Load Balancer 也不是只按 Byte 收费。AWS 当前 LCU 同时观察 New Connections、Active Connections、Processed Bytes 和 Rule Evaluations，并按当小时占用最高的维度计量。两款应用即使每月字节相同，一个频繁建立短连接、另一个维持少量长连接，也可能落在不同成本驱动项。

### 为什么 Ingress 常免费，Egress 和边界移动却收费？

**Fact** 是价目表如此规定。更谨慎的 **Interpretation** 是：把数据带入平台能促进存储与计算消费，而向外发送、跨位置复制和经过托管网络功能会占用不同资源并形成可计量服务。关于价格中有多少来自物理成本、容量稀缺、竞争策略或 Switching Cost，是 **Inference / Hypothesis**，不能仅凭价目表拆出比例。

所以比较架构时，应看 Cost per Delivered Useful Byte 或 Cost per Successful User Request，而不是只看 Egress 单价。少一次跨 AZ Hop、提高 CDN Hit Rate、复用连接或减少响应大小，可能同时改变性能、可靠性和账单；但把所有服务挤进一个 AZ 以省流量，也可能牺牲故障隔离。

## 12. Industry Vocabulary（行业词汇，第一次完整拆解）

- **DNS（Domain Name System）**：分布式名称数据库，把稳定域名映射为地址或其他 Resource Record。域名所有者 / 云客户支付注册、托管和查询，用户与应用受益。它解决“地址会变、人不记 IP”的问题；常见误解是 DNS 成功等于服务可达。
- **TTL（Time to Live）**：Resolver 可以缓存 DNS 答案的秒数。更长通常减少查询、成本和时延，更短提高变更响应；它不是端点寿命，也不是所有客户端严格同步切换的倒计时。
- **BGP（Border Gateway Protocol）**：不同 Autonomous System 交换 IP Prefix 可达信息的协议。网络运营者控制 Advertisement，Internet 参与者依靠它找到下一网络；它解决跨网络可达性，不检查网页内容是否正确。
- **Route Table（路由表）**：把 Destination Prefix 映射到下一跳 Target 的规则集合。Cloud Customer 配置逻辑路由，Provider 实现转发；有 IP 地址但没有合适 Route 仍不可达。
- **Load Balancer（负载均衡器）**：接受连接或请求，并在符合规则与健康条件的 Target 间选择后端。客户支付运行与容量计量，Provider 运营入口；它解决端点选择和故障摘除，不自动修复后端共享依赖。
- **Egress / Data Transfer Out（出站传输）**：数据离开服务、Region 或 Provider 边界时的计量类别。客户通常付款，Provider 和网络伙伴交付路径；它不等于全部网络成本，也不能单独证明 Provider 的真实边际成本。
- **Anycast（任播）**：多个位置宣告同一 IP Prefix，路由把用户带到网络上较合适的位置。它能分散入口和缩短路径，却仍依赖 Advertisement、健康判断与后端连通。

## 13. Fact、Interpretation、Inference 与 Hypothesis

> **Fact（事实）**：Meta 官方称例行维护命令意外切断全球 Backbone，Audit Tool 的 Bug 未阻止命令；DNS 边缘因无法联系 Data Center 而撤回 BGP Advertisement，DNS Server 仍运行却不可达；远程工具受影响，恢复时个别 Data Center 有数十兆瓦用电回升风险。Cloudflare 从外部观察到约 5 小时 30 分钟的 DNS 不可用窗口。

> **Interpretation（解释）**：事件不是“DNS 数据写错”或“服务器全部关机”，而是 Backbone、BGP Reachability、DNS Discovery、内部 Tooling 和 Recovery Access 的级联失效。

> **Inference（推断）**：真正独立的云恢复路径必须在控制权限、命名、路由、身份、运维接入和数据路径上审计共同故障，而不只跨地理位置复制服务器。

> **Hypothesis（仍需验证的假设）**：某个具体 Multi-region 应用在主 Region 失联时能自动、快速且低成本地切换。验证需要 Resolver Cache、BGP / Route、Health Check、Target Capacity、State Freshness、Identity、Certificate、回程路径、跨区账单和真实 Game Day 证据。

### Evidence Boundary（证据边界）

Meta 官方复盘直接支持其公开的触发、级联、恢复障碍和公司所述改进方向，但不是独立审计，也没有披露完整拓扑、所有 Guardrail、每项服务影响或财务损失。Cloudflare 的 BGP / DNS 数据是外部观察，能约束公开时间和可达性，却看不到 Meta 内部状态。AWS 与 RFC 文档支持公开协议、产品语义和当前 List Price，不披露云厂商内部网络拓扑、客户折扣、Provider Cost 或 Margin。1 GB、10 MB 与 `$900` 均为透明教学模型，不是性能或账单预测。

## 14. Transfer（迁移）：以后看到“网络慢 / 网络挂了”，怎样追问？

先固定一个 Client、一个 Name、一个 Request 和一个时间点。测量 DNS 是否从 Cache 命中、返回哪个 Record、TTL 还剩多久；不要先把 Resolver Failure 叫成 Server Failure。

再固定一个 Destination IP。检查从客户端与云内不同位置是否存在正反向 Route，BGP Prefix 是否被宣告，Firewall / ACL 是否允许；不要把高接口带宽当成 Reachability。

然后到入口。记录 Connect / TLS Time、Load Balancer Rule、Target Health、Backend Response 和 P95 / P99；不要用平均延迟掩盖部分路径或少数客户端失败。

最后跟随 Bytes 跨边界。标出 AZ、Region、NAT、Transit、CDN 和 Internet，分别记录 Throughput、Loss、Retransmission、Processed Bytes 与账单类别。只有这样，“网络问题”才会变成可验证、可修复、可计价的机制。

## 16. 现在我们可以重新回答开头的问题

服务器全绿而网站仍像消失，是因为服务器只是请求路径的最后一段。用户必须先把 Name 解析成 Address，网络必须拥有到该 Prefix 的 Route，入口必须选到可用 Target，Transport 必须把 Bytes 送达并返回。Meta 的服务器和 DNS 进程并非全部消失；全球 Backbone 断开触发 BGP 撤回，运行中的 DNS 失去 Reachability，整个服务因此无法被找到。
