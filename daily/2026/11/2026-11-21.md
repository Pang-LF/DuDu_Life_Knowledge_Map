# Mastery Core（掌握核心）

## 1. Opening Puzzle（开场谜题）：五份“保险”为什么只救回了六小时前的世界？

2017 年 1 月 31 日，GitLab.com 的工程团队面对一个看似有很多安全垫的数据库：一台 Primary、一台用于 Failover 的 Hot Standby、每日 `pg_dump`、每日 LVM Snapshot，以及其他服务器使用的 Azure Disk Snapshot。

如果只数名词，答案似乎很安心：有 Replica、有 Backup、有 Snapshot、有 Cloud Storage。可当生产数据库被误删后，团队发现 Standby 正在重建、`pg_dump` 备份根本没有成功、数据库服务器没有启用 Azure Snapshot，而可用的 LVM Snapshot 来自约六小时前。GitLab.com 最终停机约 18 小时，并永久失去了这六小时内的一部分数据库修改。

真正的问题不是“有没有五种东西”，而是：**事故发生的这一刻，哪一份状态可以被找到、读出、复制、验证、接上身份与应用，再让用户重新完成一次有效请求？**

## 2. 先定义母概念：Cloud Architecture（云架构）是什么？

Cloud Architecture 是为了交付一项指定业务功能，对以下六类能力做出的完整安排：

1. **Compute Placement（计算放置）**：代码在哪里运行，失败后哪里还有可用容量？
2. **Failure Isolation（故障隔离）**：Host、Zone、Region、控制面、部署和人员操作是否共享同一故障？
3. **State（状态）**：数据库、对象、队列和配置复制到哪里，目标端有多新、能否写入？
4. **Reachability（可达性）**：DNS、Route、Certificate、Load Balancer 与 Return Path 怎样把请求切过去？
5. **Identity & Authority（身份与权限）**：恢复环境的 Secret、Key、Role、Certificate 和人工 Break-glass Access 是否有效？
6. **Operations（运维）**：谁检测、谁决定、按什么顺序执行、怎样验证、何时中止或回切？

架构不是资源清单，而是这些部分在正常状态和故障状态下怎样共同完成同一个用户功能。Disaster Recovery 则是架构的一种能力：在预先定义的大范围破坏后，把业务功能恢复到可接受状态。

这就是它必须晚于 Placement、Reliability、Storage 与 Network 的原因。我们必须先知道每一块交付什么，才能判断恢复时缺的是哪一个接口；下一步讨论 Cloud Economics 与 Shared Responsibility，也必须先知道到底为哪条恢复路径付费。

## 3. Follow One Order（跟随一个订单）：第二个 Region 何时才算“活着”？

假设一家电商把 Primary Region 设在 A，把 Recovery Region 设在 B。灾难发生前，一位用户刚提交订单 `#8241`。我们不画一张看起来很完整的架构图，而是跟随这一份订单。

### 正常状态：订单留下了哪些状态？

用户经 DNS 到达 Region A 的入口，Identity Service 验证登录，Order Service 把订单写入 Database，Payment Adapter 记录外部支付结果，Queue 发出履约消息，Object Storage 保存发票。一次“下单成功”因此不是一行数据库记录，而是一组可能分散在不同系统、不同时间边界里的状态。

如果 Database 每 30 秒异步复制到 B，但 Queue 不跨区复制，Secret 只存在 A，DNS Failover 没有配置，即使 B 有一份订单表，它仍不能安全接管业务。它可能重复扣款、漏发货，或者根本无法启动。

### 灾难发生：恢复不是一个按钮，而是七个门

Region A 完全失联后，恢复至少经过七个门：

1. **Detect**：端到端探针确认不是某个 ISP、DNS Cache 或单个服务的局部故障。
2. **Scope**：判断是一个实例、一个 Zone、整个 Region，还是共享 Identity / Control Plane 故障。
3. **Decide**：授权者比较继续等待与切换的风险，明确 Freeze、Failover 或 Abort。
4. **Prepare State**：确认 B 的最后复制点，提升写权限，处理未完成事务、Queue 与外部系统去重。
5. **Prepare Service**：取得 Quota / Reservation，启动或扩容 Compute，加载 Configuration、Secret、Key 与 Certificate。
6. **Route**：更新或触发 DNS / Global Traffic Policy，把新连接交给 B，并允许旧缓存自然收敛。
7. **Validate**：不是看 VM 变绿，而是用真实或合成订单验证登录、下单、支付、查询和回执，持续观察错误率、延迟与积压。

这七步可以部分并行，但不能假装不存在。恢复时间是这条关键路径的实测结果，不是“有备用区”推导出的属性。

## 4. RTO 与 RPO：两个目标，两个不同的损失分母

- **RTO（Recovery Time Objective，恢复时间目标）**：灾难后，业务功能最多可以中断多久。
- **RPO（Recovery Point Objective，恢复点目标）**：恢复后，状态最多可以回退到灾难前多久。

假设订单系统每分钟写入 100 个订单，异步复制最坏落后 5 分钟。透明模型得到：

`100 orders/min × 5 min = 500 orders`

这 500 不是必然丢失的订单，而是**在 Primary 不可恢复且复制确实落后满 5 分钟时的最大状态暴露量**。如果支付提供商已经确认其中一些交易，而 Recovery Database 没看见它们，业务问题就不只是“少了 500 行”，还包括退款、对账、客服和信誉成本。

再假设恢复关键路径为：检测 3 分钟、确认范围与授权 4 分钟、提升状态与校验 6 分钟、扩容 12 分钟、路由与缓存收敛最多 5 分钟。若这些步骤按这一最保守顺序串行：

`3 + 4 + 6 + 12 + 5 = 30 minutes`

30 分钟是这个假设 Runbook 的 RTO 下限模型，不是云产品保证。实际步骤可并行，也可能因 Quota、Control Plane、Cache、人工访问、数据校验或依赖恢复而更久。它改变理解的地方在于：若业务要求 10 分钟恢复，仅把 DNS TTL 从 300 秒降到 60 秒远远不够；12 分钟扩容和 6 分钟状态准备已经让目标不可能成立。

## 5. 四种恢复策略不是四个口号，而是四种“预先完成程度”

| 策略 | 灾难前已经完成什么？ | 灾难后还必须做什么？ | 成本与风险直觉 |
|---|---|---|---|
| Backup & Restore（备份恢复） | 数据和配置有可用副本 | 配资源、部署代码、恢复数据、接通流量 | 平时成本最低；RTO / RPO 通常更长，恢复路径最多 |
| Pilot Light（引火灯） | 核心状态和少量基础设施常驻 | 创建其余服务、扩容、切流 | 为连续复制付费，但仍依赖大量控制面动作 |
| Warm Standby（温备） | 一套缩小但能处理请求的完整环境在运行 | 扩容并接管完整流量 | 更高 Idle Capacity；恢复步骤更少 |
| Multi-site Active/Active（多站点双活） | 多个 Region 已经服务真实流量 | 隔离坏 Region，让其余 Region 吸收流量 | RTO / RPO 可更低，但写冲突、容量、发布和运维复杂度最高 |

AWS 当前 Well-Architected 指南给出的典型数量级是：Backup & Restore 的 RPO 以小时、RTO 在 24 小时以内；Pilot Light 是分钟级 RPO、数十分钟 RTO；Warm Standby 是秒级 RPO、分钟级 RTO；Active/Active 可接近零 RPO、RTO 潜在为零。**这些是架构策略的指导范围，不是任何具体工作负载的保证。**真正值仍要由业务状态、依赖、容量和演练证明。

一个重要反例是：Active/Active 不会自动保护错误删除或数据污染。若错误写入被实时同步到所有 Region，“复制更快”反而会让错误更快扩散。Point-in-time Recovery、Versioning、隔离的 Backup 与恢复验证仍然必要。

## 6. Main Case（主案例）：GitLab 2017——资源存在，恢复路径却没有成立

### Before

GitLab.com 使用一台 PostgreSQL Primary 和一台 Hot Standby。团队还安排了每日 `pg_dump` 上传 S3、每日 LVM Snapshot，以及部分服务器的 Azure Disk Snapshot。表面上，数据保护机制不止一种。

### Pressure Builds

1 月 31 日晚，Spam 与一个后台删除任务共同增加数据库负载。Secondary 的复制越来越落后，Primary 已经删除了它需要的 WAL Segment；因为没有 WAL Archiving，团队必须手工清空 Secondary 的数据目录并重新做 `pg_basebackup`。

这个阶段已经暴露三种压力：运行负载使复制失效；恢复步骤需要破坏旧 Secondary；Runbook 没有清楚解释 `pg_basebackup` 可能静默等待。一个原本承担 Failover 的副本，在重建期间不再是可用恢复路径。

### Turning Point

约 23:30 UTC，一位工程师以为自己在 Secondary 上删除目录，实际命令运行在 Primary。命令在一两秒后被终止，但约 300 GB 数据已经被删除，只剩约 4.5 GB。

### Cascade

Primary 与 Secondary 都不能恢复服务。团队寻找 `pg_dump` 时发现 S3 Bucket 是空的：备份任务使用 PostgreSQL 9.2 工具连接 9.6 数据库而失败，错误邮件又因 DMARC 配置被拒收。Azure Snapshot 没有启用在数据库服务器上。每天创建的 LVM Snapshot 本来主要服务 Staging，不是经过验证的 DR 产品；幸运的是，一位工程师约六小时前手工创建过一份。

注意这里的因果层次。**事实**是公开复盘记录了这些失败和配置；**解释**是它们共同说明 Backup Count 不等于 Recoverable State；**推断**是缺少所有权与定期 Restore Test 让多项失败长期不可见；**不能证明的假设**是任何单一云或数据库产品本身导致了事故。

### Decision

团队选择六小时前的 Staging LVM Snapshot，因为另一个可用 Snapshot 接近 24 小时。恢复需要把 Staging Database 复制回 Production，另建数据库提取 Webhook，再调整 Sequence 以避免重复 ID，最后逐步开放服务。

### Outcome

GitLab 报告从 Staging 向 Production 复制数据约用了 18 小时，主要瓶颈是约 60 Mbit/s 的廉价 Network Disk，而不是 CPU 或普通网络链路。GitLab.com 约停机 18 小时，丢失了 17:20 到 23:30 UTC 的部分数据库状态；公司估计至少影响约 5,000 个 Project、5,000 条 Comment 和约 700 个 User Account。Git Repository 与 Wiki 存在另一条存储路径，服务中断时不可用，但没有随数据库修改一起丢失。

### Aftermath

GitLab 把改进从“别再输错命令”扩展到恢复系统：备份监控、Point-in-time Recovery / Continuous Archiving、每小时 LVM Snapshot、数据库 Azure Snapshot、自动 Restore Test、更清楚的 Replication Runbook，以及明确的数据持久性 Owner。公司公开总结的方向不是让人永不犯错，而是让错误可以被快速、低影响地恢复。

## 7. 数字为什么改变理解？

### 六小时不是一个抽象 RPO

六小时表示恢复点之后发生的数据库修改需要重建或永久丢失。5,000 个 Project、5,000 条 Comment 与约 700 个 Account 不是“总数据库的百分比”，而是公司当时对受影响对象的粗略估计。它说明 RPO 应由业务对象表达：订单、支付、账户和权限比“GB 落后量”更接近真实损失。

### 18 小时不是 Copy Time 的同义词

GitLab 分别写到数据复制约 18 小时、服务停机约 18 小时、恢复本身超过 18 小时。这些边界接近但不完全相同。复制吞吐、Webhook 恢复、Sequence 修正、验证和逐步开放都属于恢复路径；不能把单一文件复制时长当成完整 RTO。

### 60 Mbit/s 为什么成为决定性数字？

如果只做理想换算，300 GB 十进制数据为 2,400 Gbit，在 60 Mbit/s 上的序列化下限约为：

`2,400,000 Mbit ÷ 60 Mbit/s = 40,000 s ≈ 11.1 h`

实际复制约 18 小时，合理地还会包含存储限速、协议、I/O Pattern、校验和其他开销。这个模型不是对 GitLab Transfer 的独立复算，却揭示一个关键事实：**平时为了节省 Staging Storage 成本选择的低吞吐，在灾难时成为 RTO 的硬下限。**

## 8. 有意义的对照：同样叫“备用”，为什么恢复能力完全不同？

把两套系统放在一起：

- 系统甲有三个 Replica，却共享同一删除权限；从未做过隔离 Restore，备用容量只有峰值的 20%，Secret 只在 Primary，DNS Failover 只写在文档里。
- 系统乙只有一个 Warm Standby，但它有独立权限边界、持续复制、Point-in-time Backup、预留容量、自动化切流和季度 Game Day，且每次记录实际 RTO / RPO。

不能仅凭描述断言乙一定胜过甲；故障类型与目标仍然重要。但对“Region 完全失效且 Primary 状态不可用”这个命名场景，乙提供了更多直接证据。副本数量是输入，**经过演练的业务恢复结果才是能力。**

## 9. Industry Apprenticeship（行业学徒制）：谁为“平时不用”的恢复能力付钱？

今天只回答一个行业问题：**Compute、State、Network、Identity 与 Operations 怎样成为可演练的 Multi-region Recovery System，Idle Capacity、Replication、Transfer 与 Game Day 又由谁付款？**

### 付款方与受益方

Cloud Provider 投资 Region、Network、Storage、Control Plane 与托管服务的底层冗余，并把可用能力产品化。Customer 仍要为自己的 Recovery Architecture 选择并支付资源：

- Recovery Region 中常驻或预留的 Compute / Database Capacity；
- Cross-region Replication、Destination Storage、Backup 与 Version Retention；
- Cross-region Transfer、Failover 后的 Internet Egress、DNS / Load Balancer / Gateway；
- Infrastructure as Code、Observability、Runbook、On-call、Audit 与 Game Day；
- 演练期间的双写、影子流量、环境占用和业务协调。

最终受益者是业务与用户，但付款并不只出现在故障当天。Warm Standby 的价值恰恰来自平时持续支付一份看起来“低利用率”的选择权。

### 一个透明成本模型

假设 Primary 峰值需要 100 个 Compute Unit，Warm Standby 平时保留 30 个、灾难后扩到 100 个；每 Unit 的透明假设价格为 `$0.10 / hour`。忽略折扣、存储、网络、数据库、软件和税：

`30 × $0.10 × 730 hours ≈ $2,190 / month`

这 `$2,190` 不是浪费的同义词，而是 30% 预热容量的显性成本。如果没有 Capacity Reservation，灾难时能否从 30 扩到 100 仍需验证；如果预留完整 100 个，静态 Compute 成本模型变成约 `$7,300 / month`，但缩短了“等待供应”这条恢复路径。

决策不能只比较 2,190 与 7,300。还要比较：业务每小时中断损失、RTO 目标、事故概率、数据丢失成本、演练频率、复杂度引入的新故障，以及 Active/Active 的持续工程负担。公开 List Price 可以帮助建模，却不能揭示 Cloud Provider 成本、Customer 私有折扣、真实 Incident Loss 或 Margin。

### 术语第一次出现时要说清楚

**Game Day（故障演练日）**不是演示 Backup Dashboard，而是在受控条件下让一段真实恢复路径执行：故意移除依赖或宣告 Region 不可用，让团队完成 Detection、Decision、State Promotion、Capacity、Identity、Routing 与 Validation。历史原因是纸面 Runbook 和未恢复过的 Backup 会发生 Drift；付款方通常是 Customer 的工程与业务团队，Cloud Provider 可能提供工具；受益方是需要连续服务的用户；它解决“我们以为能恢复”和“我们实测能恢复”的差距。常见误解是演练一定要破坏全部 Production——范围可以逐步扩大，但必须足以验证关键假设。

## 10. Evidence Boundary（证据边界）

- GitLab 的复盘是公司公开的一手叙述，直接支持时间、配置、恢复步骤、粗略影响与改进项目，但不是独立审计，也不能重建每一条内部状态。
- GitLab 2017 的 Azure、S3、PostgreSQL 和自建运维组合不代表今天任何云服务的默认行为，也不证明 Multi-region 必然优于单 Region。
- AWS Well-Architected 文档给出当前策略语义与典型 RTO / RPO 范围，不是具体工作负载 SLA；实际结果取决于应用、状态、依赖、配额、容量和演练。
- 500-order 暴露、30-minute 恢复、300 GB / 60 Mbit/s 和 Warm Standby 月成本都是透明教学模型；只有 GitLab 披露的约 300 GB、约 60 Mbit/s 和约 18 小时属于案例事实，换算与假设价格不是实测账单。
- 公开资料不披露 GitLab 当时的完整合同成本、每项业务损失或所有安全控制，也不披露 AWS Provider Cost、客户私有折扣与 Margin。

## 11. Transfer（迁移）：以后怎样审查一份 DR 方案？

面对任何“我们有跨区容灾”的陈述，按这个顺序追问：

1. 恢复的精确业务功能是什么，哪些订单、支付、账户或数据对象构成成功？
2. 命名的 Disaster 是 Host、Zone、Region、数据污染、身份失效，还是人员 / 控制面共同故障？
3. RTO 与 RPO 各自用什么业务分母定义？
4. Compute、State、Network、Identity、Configuration 与 Operations 在 Recovery Site 分别处于什么状态？
5. 哪些步骤依赖故障区域的 Control Plane、Credential、人员或网络？
6. 最近一次 Game Day 的实际 Detect、Decide、Restore、Route 与 Validate 时间是多少？
7. 谁持续支付 Idle Capacity、Replication、Transfer、Testing 和 Complexity，失败后谁承担剩余损失？

## Teach-back（20–30 分钟讨论）

## 13. 现在我们可以重新回答开头的问题

GitLab 拥有多种保护机制却只救回六小时前的世界，因为这些资源没有共同构成一条经过验证的恢复状态转换：Standby 在重建，逻辑备份静默失败，错误通知没有到达，数据库没有 Azure Snapshot，而可用 LVM Snapshot 位于慢速 Staging Storage。名字很多，能在事故中完成 Find、Read、Move、Restore、Reconnect 与 Validate 的路径只有一条。

今天在地图上点亮了 `SYSTEM.COMPUTE.CLOUD_ARCHITECTURE_INTEGRATION_DISASTER_RECOVERY`：我们把 Placement、Failure Domain、Storage、Network、Identity 与 Operations 合成了一个可演练的业务恢复系统。下一步通向 Cloud Economics & Shared Responsibility Integration（云经济学与共同责任整合）：当云把基础设施能力产品化以后，哪些风险由 Provider 吸收，哪些仍由 Customer 架构、合同和运营承担，什么时候 Cloud 降低的是总成本，什么时候只是改变账单形状。

# Knowledge Expansion（知识拓展，不自动点亮）

今天随 GitLab 事件接触了 PostgreSQL WAL、LVM Snapshot、DMARC、Point-in-time Recovery、Sequence、Webhook、Warm Standby 与 Game Day。它们都服务于“恢复是一条经过演练的状态转换”这个 Anchor Concept，没有分别点亮数据库、邮件认证或安全节点。Cloud Placement、Reliability、Storage、Network 与 Systems Integration 只记录 review / transfer，不自动升级 mastery。

# Connection Preview（连接预览，不正式教授）

- **Cloud Economics & Shared Responsibility（云经济学与共同责任）**：Provider 的 Region 冗余不会替 Customer 自动完成应用级恢复；产品边界决定钱与风险如何分配。
- **Cybersecurity & Ransomware Recovery（网络安全与勒索恢复）**：实时复制可能同步恶意加密或删除，隔离 Backup 与恢复身份成为关键。
- **Distributed Databases（分布式数据库）**：Active/Active 写入必须处理冲突、时钟、Quorum 与分区选择。
- **AI Infrastructure（人工智能基础设施）**：Checkpoint、Model State、Dataset、GPU Capacity 与 Network Fabric 决定训练任务是否能跨故障域恢复。
